## 问题 {#problem}

开发者越来越多地同时使用多个 AI Agent：Claude Code、Codex、Cursor、ZCode、Grok Build。每个 Agent 都有自己的记忆，范围限定在一个仓库、一台机器或一个云端账户。换一个工具或项目，就得从零开始。这些记忆难以查看，难以纠正，其他 Agent 看不到，还常常被悄悄清除（例如 Claude Code 默认在 30 天后删除本地会话记录）。

与此同时，这些 Agent 都会把纯文本、可解析的会话记录写到本地磁盘，也都能与本地的 [MCP](https://modelcontextprotocol.io) server 通信。Origin 正是建立在这两点之上：它把本机所有 Agent 会话归档进同一个本地库，再通过同一个 MCP server 把这个库提供给每个 Agent。

长远的方向，是一个长期陪伴一个人的 AI：记忆、知识以及对这个人的理解，都能跨越工具和模型代际延续下去。Origin 从这个核心做起。

## 范围 {#scope}

**当前目标——一份通过 MCP 提供的跨 Agent 个人记忆：**

- 把 Claude Code、Codex、Cursor、ZCode、Grok Build 的本地会话归档进同一个只追加的库；人带来的其他任何东西，只要写成*事件行*（一种任何脚本都能写的格式）放进它自己的目录或者发给它的中枢，其会话也一并归档（见[你自己的来源](#your-own-sources)）。Origin 像读取 Agent 的记录一样读取它们；写入它们的程序在 Origin 之外，随 Origin 一起发布的 OpenClaw 插件也是如此。
- 把 Agent 为自己保存的记忆（Claude Code、ZCode 和 Grok Build 的记忆文件）导入为条目，让一个 Agent 记住的内容也能到达其他 Agent。
- 让任何 Agent 都能通过 MCP 检索归档、浏览时间线、把任何回答展开到它的原始来源，并记录持久的条目（记忆 / 知识 / 认知）。
- 让人通过 `origin` CLI 或管理界面查看、纠正和遗忘条目，无论是在自己的中枢上，还是用 `origin ui` 在自己的机器上；遗忘必须持久生效，直到这个人恢复他遗忘的内容。
- 一个人常常在多台机器上运行 Agent（笔记本、服务器、云端 Agent）。每台设备都保有一份完整的、属于自己的记忆；可选的自托管**个人中枢**把每台设备写下的内容汇集到一个库中，让任何地方的 Agent 都能找到。磁盘空间不多的机器也可以改为中枢的**中继**（relay），它不保有自己的记忆。

达成目标的标志是：在你任何一台机器上，从任何一个已接入的 Agent 问“上周在项目 X 里我决定了什么，为什么？”，都能得到附带来源的回答，而且被遗忘的条目除非你恢复它，否则永远不会再回来。

**目前明确不做：** 多租户托管（Origin 只服务一个人，每个人运行自己的一份）、由本项目运营的托管服务、端到端加密、设备之间互相拉取对方的数据、不经过中枢的点对点同步、实时协作、自己的中枢或机器上供主人使用的管理界面之外的任何 Web 界面（没有公开页面、没有分享、没有多账户）、屏幕 / 邮件 / 浏览器采集、知识图谱、向量检索、主动提醒，以及任何对模型 API 的调用。

## 记忆、知识与认知 {#memory-knowledge-and-cognition}

Origin 区分三类持久条目。每个条目都带有自己的来源，并且可以被纠正或遗忘。

| 类型 | 含义 | 示例 |
|---|---|---|
| `memory` | 发生过什么（情景记忆） | “10 月 20 日，为了保持代码简单，我们决定在首个版本发布前不做 schema 版本管理。” |
| `knowledge` | 稳定的事实与关系 | “项目 A 依赖库 B。” |
| `cognition` | 关于这个人的模型：偏好、方法、目标、边界 | “偏好不带署名 trailer 的提交信息。” |

## 核心对象 {#core-objects}

| 对象 | 含义 | 关键字段 |
|---|---|---|
| **Source**（来源） | 某个 Agent 的适配器：`claude-code`、`codex`、`cursor`、`zcode`、`grok`；或者人自己的一个来源，按事件行读取，以它的目录命名（见[你自己的来源](#your-own-sources)） | id、Agent 版本、发现根目录 |
| **Raw**（原始镜像） | 原始记录文件的只追加镜像，或适配器从数据库写出的记录的只追加镜像，以 zstd 帧存储 | 来源、原始路径、代次、字节 / 行游标、尾部哈希（生成的来源存的是它的令牌）、已封存的帧 |
| **Event**（事件） | 规范化后的对话事件：用户消息、助手消息、工具调用、工具结果；或者 Agent 保存的某个记忆文件的一个版本（见[原生记忆](#native-memories)） | id、来源、会话、时间戳、项目、cwd、git 分支、角色、类型、正文、原始定位；对输入而言，还有它的作者和说话人（派生数据，见[作者](#authors)） |
| **Entry**（条目） | 一条持久的 `memory` / `knowledge` / `cognition` 陈述 | id（`ent_…`）、类型、正文、置信度、作者、项目、来源（事件 id + 引文）、supersedes、root（它的第一个版本）、valid_from / valid_to、created_at、origin（写入它的库）；状态（`active` / `superseded` / `forgotten`）由推导得出，从不存储；`imported`（这个版本是否派生自原生记忆）同样如此 |
| **Proposal**（提议） | Agent 提出、交给本人接受或拒绝而不由它直接写下的条目（见[提议](#proposals)）；派生自 Agent 的记录，可重建 | id（`prp_…`）、产生它的会话和事件、类型、正文、置信度、项目、valid_from / valid_to、note、来源（事件 id + 引文）；状态（`pending` / `accepted` / `rejected`）由推导得出，从不存储 |
| **Thread**（线索） | 同一项目中属于同一件工作的那些会话，可以出自一个或多个 Agent，由跟随链接和工作分支连在一起（见[线索](#threads)）；派生数据，可重建 | id（`thr_…`，取自它的第一个会话，即根会话）、它的会话、它的项目和标题（取自根会话） |
| **Recall**（召回） | Origin 在会话开始时或随提示，不经询问交给 Agent 的内容（见[召回](#recall)） | id（`rcl_…`）、时间、origin（进行召回的库）、Agent、会话、时机、项目和目录、提示的哈希、预算和 token 数；每一项的排名、层、条目、会话、线索或事件 id、分数和大小，事件还有它的摘录从哪里开始 |
| **Tombstone**（遗忘记录） | 一次遗忘或一次恢复的记录 | id（`tmb_…`）、目标（遗忘的目标是条目或事件 id；恢复的目标是一次遗忘的 id）、原因、作者（已知时）、时间、origin（创建它的库）；对遗忘而言，还有它在每个库中覆盖的内容 |

每条**输入**，即对话中人这一侧的事件（角色 `user`、类型 `message` 或 `meta`；工具结果由它的类型说明），都有一个**作者**，取以下四种之一：

- `owner`：它的来源知道是这份记忆的主人写的；
- `person`：是人写的，但不知道是不是主人：别人，或者没人说明是谁的说话人；
- `agent`：是 Agent 写的，例如父 Agent 给子 Agent 的提示，或者一个 Agent 发给另一个 Agent 的消息；
- `system`：由 Agent 的运行时或某个程序生成：任务通知、压缩摘要、提醒、命令回显及其输出、中断标记、定时运行和无界面运行。

输入还可以有一个**说话人**：来源向人展示的名字或标签（`Alice`、`Speaker 2`、某个 Agent 的显示名），绝不是不透明的 id。作者记录的是谁写了这条输入，而不是它有多可信：Origin 原样保存每条输入，不识别任何人（没有人员名单，也没有任何平台的 id），并对每个来源使用同一条规则：只有来源知道某条输入是主人写的，它才属于主人。

## 数据流 {#data-flow}

```
agent session logs on disk ──scan──▶ Raw (append-only mirror)
                                        │ deterministic adapter parsing (no LLM)
                                        ▼
                                  Event store (SQLite + FTS5) ◀── Entries · Tombstones
                                        │
 agents ◀── MCP (stdio): brief · search · timeline · changes · digest · get · sources · follow · remember · propose · correct · forget
 agents ◀── hooks: origin recall (session start · prompt): a brief, and the entries and past messages a prompt matches
 agents ──▶ hooks: origin sync --hook (turn end · sub-agent · compaction): the transcript to ingest
 people ◀── CLI `origin`: sync · status · timeline · digest · search · show · entries · correct · forget · forgotten · restore · recall · recalls · proposals · accept · reject
 people ◀── admin UI (hub, /admin): overview · sessions · recalls · search · entries · proposals · remember · correct · accept · reject · forget · restore · tokens
 people ◀── origin ui (device, 127.0.0.1): overview · sessions · recalls · search · entries · proposals · remember · correct · accept · reject · forget · restore
```

使用个人中枢时，每台设备都保有一份完整的、属于自己的库，离线时也照常可用。它把原始镜像发送给中枢（由中枢用同样的适配器解析），也把自己写下的条目和遗忘记录（遗忘与恢复）发送给中枢；它从中枢收到的只有遗忘记录。设备上的 Agent 使用本地的 `origin mcp`，它根据设备自己的库作答，并合并中枢的回答；云端 Agent 则使用中枢的 HTTP 端点：

```
agents on A ──▶ origin mcp ──▶ store A ──raw mirrors · entries · tombstones──▶ ┐
                    │             ▲                                             │
                    │             └──────────────── tombstones ─────────────────┤
                    └──────── reads, merged (MCP over HTTP) ───────────────────▶ hub store ◀── MCP over HTTP ── cloud agents
agents on B ──▶ origin mcp ──▶ store B ── (as for device A) ───────────────────▶ ┘
```

中继（见[中继](#relays)）没有可以据以作答的库。它直接从 Agent 的记录文件读取新增的行，发送给中枢；它的 `origin mcp` 把每一次工具调用都交给中枢：

```
agent logs on C ──new complete lines, read after C's cursors──────────────────▶ hub store
agents on C ──▶ origin mcp ──── every tool call (MCP over HTTP) ──────────────▶ hub store
```

## 不变量 {#invariants}

这些是产品层面的保证。每一条都必须有测试覆盖，代码注释按编号引用它们。

1. **溯源。** 每个条目至少引用一个事件；每个事件都指向某个 Raw 文件中的某一行。任何回答都能一路展开到原文。中继不保存事件，所以经由它写入的内容在它的中枢上校验，溯源也在中枢上解析。
2. **有记录的遗忘。** 执行 `forget` 之后，它的目标及其连带内容立即从该库的所有查询中消失，并在这次遗忘到达其他每个库时从那里消失，而且一直不再出现，直到主人恢复这次遗忘：重新同步、之后才到达的版本和副本，以及遗忘记录到达的先后顺序，都不会让它们回来。每一次遗忘和每一次恢复都连同原因保存为一条记录；遗忘记录会到达每一个库，并且只增不减。
3. **只追加。** Raw 镜像和事件永远不会被改写：镜像的内容（即其未压缩的字节）只会增长，一行一旦采集就永远不变，无论它以何种形式存储（见[原始镜像](#raw-mirrors)）。条目通过取代（`supersedes`）来变更，从不原地修改。
4. **你的数据，留在你的机器上。** 所有数据都存放在你控制的机器上：你的各台设备上的 `~/.origin/`，以及可选的你自己的中枢，如果你为它配置了存放原始镜像的存储桶，也包括这个存储桶。Origin 从不调用第三方服务；唯一的网络流量发生在你的设备和你的中枢之间，以及你的中枢和它的存储桶之间。
5. **单一入口。** 无论来自哪个界面，每一次读写都经过同一组 core 操作：Agent 使用 MCP（所在设备的 `origin mcp`，或中枢的 HTTP 端点）；人使用 CLI 或管理界面（自己中枢上的，或设备上的 `origin ui`）。写入发生在发起它的那个库中——在设备上就是先写入设备自己的库（中继没有自己的库，所以它的写入发生在它的中枢上）——再由复制通过同样的操作应用到其他库。中枢的复制 API 在你自己的各个库之间传输原始镜像、条目、遗忘记录和召回，它既不是 Agent 的入口，也不是人的入口。

## 设计原则 {#design-principles}

- **内核不含 LLM。** Origin 从不调用模型 API。它只负责归档、规范化、建立索引、存储和提供数据。分析发生在提问的那个 Agent 里——它本身就是一个能力很强的模型。Agent 通过 MCP `remember` 保存它学到的东西，或者用 `propose` 把它提议给本人审阅；人通过 CLI 或管理界面纠正和遗忘，并接受或拒绝提议。用模型清理、分析和整合记忆，是 Origin 之外的 Agent 的工作：它们通过 MCP 工具读取记忆，并把发现的内容提议出来（见[提议](#proposals)）。
- **确定、容错的适配器。** 每个来源都有一个纯粹、确定性的解析器。Agent 的记录格式变化频繁，所以适配器会记录 Agent 版本，跳过无法解析的行并统计失败次数，绝不中止采集。
- **以 MCP 作为互通点。** MCP 是所有目标 Agent 唯一共有的接口。其中几个 Agent 还会读取 Claude Code 的 MCP 配置，所以一次注册就能覆盖不止一个 Agent。
- **小而保守的管理界面。** 管理界面，无论是中枢上的，还是设备上的 `origin ui`，都只供它的主人使用。页面在服务器端由一个对每个值都做转义的模板渲染，外加一点可选的脚本。它的样式表、字体和图标来自 OpenLinkOS 设计系统（`@openlinkos/ui`），在构建时复制进这个包；不从别处加载任何东西，也没有打包工具。CLI 能做的它都能做，但不做任何会破坏不变量的事：不原地编辑或删除；被隐藏的文本只出现在隐藏它的那次遗忘自己的页面上，只给它的主人看，主人可以在那里恢复它。
- **小而可运行的增量。** 每个来源适配器都单独交付、单独可用；设计只深入到当前增量所需的程度。

## 包 {#packages}

pnpm workspace，TypeScript（strict、ESM、NodeNext），Node.js ≥ 22.16（需要 `node:zlib` 的 zstd 和 `node:sqlite` 的在线备份）。`core`、`adapters`、`admin` 和 `openclaw` 只使用 Node 内置模块；`mcp` 依赖官方的 [MCP TypeScript SDK](https://github.com/modelcontextprotocol/typescript-sdk) 和 zod。中枢及其管理界面使用 Node 内置的 `node:http`。

| 包 | 路径 | 职责 | 依赖 |
|---|---|---|---|
| `@openlinkos/origin-core` | `packages/core` | 存储、schema 与迁移、采集（本地与远程）、中继、条目、遗忘、主人的设备和 Agent（令牌、OAuth 授权、等待批准的设备）、管理密码与用户名、会话、审计日志、查询 | — |
| `@openlinkos/origin-adapters` | `packages/adapters` | 每个 Agent 一个确定性解析器，另有一个解析事件行，即人自己带来的来源所用的格式 | core |
| `@openlinkos/origin-mcp` | `packages/mcp` | MCP 工具；基于 stdio 和无状态 HTTP 的 server，已接入中枢的设备上的 server（它把中枢的回答合并进自己的回答），以及中继上的 server（它把每一次工具调用都交给中枢） | core |
| `@openlinkos/origin-admin` | `packages/admin` | 管理界面，供中枢和 `origin ui` 使用：服务器端渲染的页面、JSON API 及其静态资源；中枢的公开首页；以及中枢的 OAuth 端点 | core |
| `@openlinkos/origin` | `packages/cli` | `origin` 命令，包括 `origin mcp`、`origin serve`（中枢）、`origin ui`、设备或中继与中枢之间的同步（以及经浏览器批准的接入）、中枢的 S3 客户端，以及它获取客户端元数据文档的组件 | core, adapters, mcp, admin |
| `@openlinkos/origin-openclaw` | `packages/openclaw` | OpenClaw 的插件，由它的 Gateway 加载：把 Gateway 上各个 Agent 的会话写成事件行，写入某个来源的目录或发往中枢，并把 Origin 的读取工具交给这些 Agent，由它转发给中枢的 `/mcp` | — |

六个包以同一个版本号一起发布到 npm。用户安装 `@openlinkos/origin`，`core`、`adapters`、`mcp` 和 `admin` 随之安装；1.0 之前，这四个包属于内部实现，它们的 API 可能在任何版本中改变。`@openlinkos/origin-openclaw` 则用 OpenClaw 自己的命令安装进 OpenClaw。

`core` 不得依赖任何其他包，`openclaw` 也不得：它运行在 OpenClaw 里，只通过它写出的事件行，以及为它的读取工具通过 HTTP 访问中枢的 MCP 端点，与 Origin 打交道；`mcp` 和 `admin` 都不得依赖 `adapters`：CLI 以回调的形式把采集注入各个 server，中枢和 `origin ui` 的 HTTP server 位于 CLI 中，并由它挂载管理界面的请求处理函数。适配器实现 `core` 中的 `SourceAdapter` 接口：

```ts
interface SourceAdapter {
  id: string; // 'claude-code' | 'codex' | 'cursor' | 'zcode' | 'grok', or a source of one's own
  displayName: string;
  version(): string | null; // agent version, if known
  discover(): Promise<SourceFile[]>; // { absPath, relPath, compression?: 'zstd', generated? }
  locate?(absPath: string): SourceFile | null; // the file discover() would list at absPath, or null
  parseLine(line: string, ctx: ParseContext): ParsedLine | null; // deterministic; throws on malformed input
}
// ctx: { absPath, relPath, lineNo, fileMtimeMs, readLine(n) }; readLine returns an earlier line of
// the same file as ingested, for an adapter that needs, say, a file's first line on a hub.
// generated: { token, mtimeMs, next(last, maxBytes) } for a source that is not a log file, such as
// a database: the adapter writes the lines (see Generated sources).
// locate: pure, so the file need not exist; for one file named from outside, such as the transcript
// an agent's hook names, with the relPath discover() gives, so that a file has one mirror however
// it is found.
```

## 存储 {#storage}

```
~/.origin/                 # or $ORIGIN_HOME
├── origin.db              # SQLite (WAL)
├── raw/<source>/...       # append-only mirrors of the original log files:
│                          #   <mirror>.zst (sealed zstd frames) and <mirror>.tail (open tail)
└── sources/<name>/...     # your own sources: files of event lines, which Origin reads and never writes

s3://<bucket>/<prefix>/    # optionally, on a hub: its sealed frames, one object per frame
└── <mirror>.zst/<offset>
```

| 表 | 内容 |
|---|---|
| `raw_file` | 每个镜像文件代次一行，带有它的采集游标 |
| `raw_chunk` | 每个镜像已封存的帧：首行行号、行数、在内容中和在 `.zst` 文件中的偏移量与长度。触发器拒绝更新和删除 |
| `event` | 规范化后的事件，以它们到达本库的次序（`seq`）为键 |
| `event_block` | 每一块 4,096 个连续到达的事件中最晚的时间戳，以及到这一块为止最晚的时间戳（派生数据，由触发器维护） |
| `event_author`, `session_kind` | 每条输入是谁写的，以它的事件的 `seq` 为键：它的作者、说话人，以及决定作者的字段；以及某一行声明为子会话（Agent 的）或无界面运行（程序的）的会话，连同那个字段（派生自原始行，可重建；见[作者](#authors)） |
| `message_fts`, `event_fts`, `event_cjk` | 事件的检索索引：`message` 事件的完整 trigram 索引、只记录哪些事件含有每个 trigram 的全部事件索引，以及 CJK 二元组索引（见[检索与时间线](#search-and-timeline)） |
| `session` | 基于可见事件的逐会话聚合（派生数据，可重建），其中包括它的 git 分支，即它的多数事件所记录的分支；以及取自带有标题的行的会话标题，并记录它是否由用户给出 |
| `project_root`、`session_place`、`place_head` | 一个目录属于哪个主工作树，以及一个会话解析到哪个项目。`place_head` 记下每个会话或路径的最新一行。由 `places.jsonl` 和本机上的解析填写，从不改写事件（见[项目](#projects)） |
| `session_follow` | Agent 声明的跟随链接，每条记有跟随的会话、它所接续的会话、链接 id，以及携带它的事件（派生自工具结果；见[线索](#threads)） |
| `session_thread` | 与其他会话同在一条线索中的会话，每个都记有它的线索 id（派生数据，可重建） |
| `session_parent` | 某一行声明哪个会话是另一个会话的子会话（子 Agent 或工作流步骤）：它的父会话、方式（`subagent` 或 `workflow`）、行中写明时的工作流运行分组和名称，以及决定这一事实的字段（派生自原始行；见[父会话](#parent-sessions)） |
| `proposal`、`proposal_source` | Agent 提出的提议，每条带有它派生自的会话和事件，以及它引用的事件和引文（派生自工具结果，可重建；见[提议](#proposals)） |
| `sync_log` | 每次同步运行一行 |
| `entry`, `entry_source`, `entry_fts` | 条目、条目引用的事件（含引文），以及条目的 FTS5 索引。每个版本记录它的 `root`（第一个版本，写入时确定）和它的 `origin` |
| `imported_entry` | 本库从原生记忆派生出的条目版本（见[原生记忆](#native-memories)），它们从不发送给其他库 |
| `tombstone`, `forgotten_entry`, `excluded_event` | 遗忘与恢复，每条都有一个全局 id（`tmb_` 加随机十六进制，与 `ent_` id 相同）和它的 `origin`；以及本库中被隐藏的内容，每个被隐藏的条目和事件都记有一次覆盖它的、生效中的遗忘 |
| `tombstone_effect` | 每次遗忘在本库中覆盖的内容，一个条目或事件可以被多次遗忘覆盖：按它的目标经规则得出、按它的中枢所列、按发送它的设备所报，或按规则 3（见[遗忘](#forgetting)） |
| `tombstone_meta` | 每条遗忘记录的作者（已知时） |
| `recall`, `recall_item` | 本库进行的每一次召回，以及它交出了什么，只记 id，从不记文本，另记每条过往消息的摘录从哪里开始（见[召回](#recall)）；触发器拒绝更新和删除 |
| `change_log` | 本库写入或收到的条目和遗忘记录的只追加序列（序号、类型、id、origin、时间），由触发器填写；触发器拒绝任何更新和删除。复制游标指向这个序列 |
| `api_token` | 中枢访问令牌，每个都是主人的一台设备或一个 Agent 的凭据：名称（设备的令牌即设备名）、类型（`device` 或 `agent`）、预设权限（`readwrite`，Agent 还可以是 `readonly`）和 SHA-256 哈希，从不保存令牌本身 |
| `oauth_client`、`oauth_code`、`oauth_grant`、`oauth_token` | 作为 `/mcp` 的 OAuth 授权服务器的中枢（见[访问](#access)）：注册过的客户端，或者中枢获取过其元数据文档的客户端，以及何时再次获取；一次性授权码；主人批准的授权，每个都是一个带有名称、预设权限和到期时间的 Agent；以及它们的访问令牌和刷新令牌。授权码和令牌只以 SHA-256 哈希的形式保存 |
| `device_request` | 等待主人在管理界面中批准的设备（见[从设备使用中枢](#using-a-hub-from-a-device)）：设备码的哈希、主人输入的验证码、设备的名称、它请求的时间和来源，以及主人的决定 |
| `setting` | 少量键值状态，只属于各自的库，从不复制：库的名称和模式、设备的复制游标及其上次与中枢同步的时间、中继上每个来源文件的一个游标，以及中枢上管理密码的 scrypt 哈希、主人的用户名和存放其已封存帧的存储桶（如果有） |
| `admin_session` | 中枢管理界面的会话：会话 id 的哈希、它的 CSRF 令牌和各个时间戳（`origin ui` 把会话保存在内存中） |
| `audit_log` | 管理操作的只追加记录，记有操作者、渠道（`ui`、`cli` 或 `api`）、id 和数量，从不包含内容；触发器拒绝任何更新和删除 |

- 存储使用 Node 内置的 `node:sqlite`，因此没有需要编译的原生模块。多个进程可以共享同一个数据库（CLI，以及每个 Agent 会话各一个 MCP server）；WAL 模式和 busy timeout 负责处理这种情况。
- `session` 是派生数据，可以从 `event` 重建；按来源的汇总（`origin status`、管理界面的概览）从它读取。`session_follow` 和 `session_thread` 也是派生数据，来自事件和会话，`rebuildThreads()` 会从头重新推导它们；`proposal` 和 `proposal_source` 同样是派生数据，`rebuildProposals()` 会从事件重新推导它们。检索索引也是派生数据，由触发器保持同步：`message_fts` 和 `event_fts` 是外部内容（external-content）表（`message_fts` 的内容是消息事件的视图 `event_message`），`event_cjk` 没有内容表，通过核心在每个连接上注册的函数填写。`rebuildSearchIndexes()` 从事件和条目重建所有这些索引以及 `event_block`。`event_author` 和 `session_kind` 派生自原始行，原始行里有事件没有保留的内容，所以 `rebuildAuthorship()` 会像采集时那样重新解析原始镜像来推导它们，并随之重新推导线索；事件从不改动。`session_parent` 也以同样的方式派生，来自镜像行已经写明的父会话，这次重建会再次记录这些链接；它不会丢掉 `places.jsonl` 的一行所添加的父会话，也从不改写事件或已存的标题。`project_root`、`session_place` 和 `place_head` 是解析后的项目（见[项目](#projects)）。建立它们的迁移不写入任何行，也不读取文件。版本 10 会读取在这些表出现之前就已经镜像的 `places.jsonl` 行。本 Origin 不认识的版本原样留在镜像里，解析时跳过并记一条警告；以后认识它的格式会再调用一次 `reparsePlaces`。读取使用 `session_place`，不改写 `event.project`。
- **到达次序。** 事件以及随之的检索索引都以 `seq` 为键，即事件到达本库的次序：FTS5 保存相邻键之间的差值，所以连续的键能让索引保持很小。同步时按修改时间从旧到新采集找到的文件，设备也按最后更新的先后把文件推送给中枢，所以到达次序尽可能地跟随时间；但它并不是时间次序，例如中枢可能在收到较新的会话很久之后，才收到某台设备的旧会话。因此，一个触发器为每一块 4,096 个连续到达的事件记录其中最晚的时间戳，以及到这一块为止最晚的时间戳（`event_block`）。按从新到旧的查询从最后到达的事件开始读取索引，分成几条由连续的块组成的链（某一块比它之前的链新一天以上时，就开始一条新链），总是从未读部分可能含有最新事件的那条链读取，一旦没有链可能含有比所需事件更新的事件，就立即停止。一个窄的 `(seq, ts)` 索引无需读取事件就能给出它的时间戳。
- **大小。** 在一个有两百万个事件、平均每个事件约 800 个字符文本的库上，数据库每个事件约占 2,550 字节：事件本身 1,360，它的索引 205，`event_fts` 500，`message_fts` 460，`event_cjk` 20。而所有事件的完整 trigram 索引单独就要每个事件约 2,350 字节。
- **备份。** `origin backup <dir>` 先用 SQLite 的在线备份一次性复制数据库，即使其他进程正在写入，也能得到一致的快照；然后按这个快照记录的状态复制原始镜像：该目录中还没有的已封存帧，以及每个开放尾部（续写；如果此后已有帧从它封存，则重新写入）。尾部从正在使用的库中读取，那里它可能已经被封存，但镜像的内容只会增长，所以读到的内容相同（见[备份](guide/privacy.md#backing-up)）。如果中枢把已封存的帧保存在存储桶中，这些帧会被复制进备份，并按磁盘上的布局排列，所以备份从不依赖存储桶；备份中的数据库随后不再记录这个存储桶。
- **中继的库**没有 `raw/` 目录，它的数据库中也没有事件、镜像文件、条目或遗忘记录：只有 `setting`（它的名称、模式和游标）和它的同步日志（见[中继](#relays)）。
- **库的名称。** 每个库都有一个名称，保存在 `setting` 中：在设备上就是设备名，中枢则把自己的库叫作 `hub`。条目和遗忘记录把写入它们的库的名称记为 `origin`，设备也以自己库的名称为中枢所知。库在第一次需要名称时被命名：`origin serve` 把它命名为 `hub`；其他命令使用 `ORIGIN_DEVICE` 或主机名。库一旦写入过条目或遗忘记录，就保持这个名称不变；它从原生记忆派生出的条目不算在内，因为它从不发送这些条目。
- **格式版本。** 数据库记录库的格式版本，打开一个较旧的库时会就地把它升级到最新版本；较新的 Origin 写过的库会被拒绝（见[迁移](#migrations)）。由已有表推导出的表，只要缺少相应的行，就会在打开数据库时据已有的表补全：遗忘记录如果在写入时没有 `tombstone_effect` 和 `tombstone_meta`（由 Origin 0.1 写下，或由仍在运行的旧版本进程写下），就依据 `forgotten_entry`、`excluded_event` 和规则补上。数据库、`raw/` 下的镜像，以及中枢存储桶中已封存的帧是一个整体：不要只删除或替换其中之一。

### 原始镜像 {#raw-mirrors}

镜像保存一个文件某一代次已采集的字节（对生成的来源，是它的适配器写出的行），即它的*内容*，而且只包含完整的行。它以压缩形式存储在两个以镜像命名的文件中：

- `<mirror>.zst`：**已封存的帧**，彼此独立的 zstd 帧（级别 3，带校验和），每帧包含若干完整的行，依次追加。`raw_chunk` 记录每一帧：首行行号、行数、在内容中的偏移量和长度，以及在文件中的偏移量和长度。读取一行只需解压包含它的那一帧。
- `<mirror>.tail`：**开放尾部**，最新的若干行，未压缩。

内容就是解压后的各帧，后接尾部，二者都以数据库的记录为准（帧以 `raw_chunk` 为准，结尾以 `raw_file.bytes_ingested` 为准）；对 `raw/` 的每一次读写都经过同一个模块（`core` 中的 `mirror.ts`）及其帧存储，帧存储把已封存的帧保存在 `<mirror>.zst` 中，或保存在中枢的存储桶中（见[帧存储](#frame-stores)）。行号、游标、重写代次、尾部哈希和事件 id 都以内容为准，就像对文件的普通副本一样。

- **名称。** 镜像以它的文件相对于来源根目录的路径命名：本库自己的文件为 `<source>/<relPath>`，中枢上设备的文件为 `devices/<device>/<source>/<relPath>`，第一代之后的每一代再加上 `.g<n>`。同一来源的两个文件可能有相同的相对路径，例如某个 Agent 的目录挪动前后的文件，或者某台设备自己的来源与用它的令牌追加到中枢的行；名称比较时不区分大小写，因为文件系统可能也不区分。先到的文件取得这个名称，后来的文件得到一个自己的名称：在原名称最后一部分的扩展名之前加上 `.~` 和它的原始文件路径（它的原始路径，在中枢上则是 `@<device>:<path>`）的 SHA-256 的前 12 个十六进制字符，例如 `proj/s1.~3f9a1c2b4d5e.jsonl`，所以一个文件的名称始终相同，也永远不会写进另一个文件的镜像（不变量 3）。适配器得到的相对路径，以及设备推送的相对路径，都是文件自己的，不带这个标记。
- **以前共用的镜像。** 早期版本让这样的两个文件共用一个镜像，后一个文件的行替换了前一个文件在其中的行，所以前一个文件的某些事件找不到原始行，或者找到的是另一个文件的行。持有这样一对文件的库保留它们的行和共用的镜像不变，任何库都不会封存共用的镜像。在设备上不会再丢失任何内容：两个文件都不再向共用的镜像追加，各自在下一次有新行时，以新的一代接着记录，使用自己的镜像，并从头重新读取，而已存储的事件保留它们原来的行。设备随后把这些新的一代推送给中枢，中枢也把它们分开镜像；早期版本的设备推送到中枢上共用镜像中的内容，照旧写在那里。
- **封存。** 尾部不到 1 MiB 时，新的行追加到尾部。如果某次追加会让尾部达到或超过 1 MiB，就改为把尾部和新的行一起封存：它们被切成若干帧，每一帧在内容达到 1 MiB 后的第一个换行处结束（更长的行单独占一帧，最后不足半 MiB 的部分并入前一帧），这些帧追加到 `<mirror>.zst` 并刷到磁盘，`raw_chunk` 在推进游标的同一事务中记录它们。这个事务提交、预写日志刷到磁盘之后，再用一个很短的事务清空尾部。一个文件一小时没有增长，多半已经结束，所以它的尾部也会被封存，无论大小：在设备上由该来源的下一次同步完成，在中枢上由每 10 分钟一次的检查完成；之后追加的行会开始一个新的尾部。
- **这里的“只追加”是什么意思。** 内容只会增长，一行的字节永远不变（不变量 3）。在磁盘上，`<mirror>.zst` 只会增长，其中的帧永远不会被改写（`raw_chunk` 拒绝更新和删除）；`<mirror>.tail` 只会被追加，唯一的例外是其中的行进入帧之后它会被清空。封存把行从尾部移入帧，而不改变内容。
- **崩溃安全。** 两个文件中超出数据库记录的字节都不属于镜像：读取时永远不会读到它们，对这个镜像的下一次写入会在追加之前丢弃它们。如果在帧写入之后、事务提交之前崩溃，会留下一个没有记录的帧；它会被丢弃，而那些行仍在尾部，会再次被封存。如果在提交之后、尾部清空之前崩溃，尾部中会留下已经进入帧的行；数据库记录的尾部为空，所以它们会被忽略，随后被丢弃。两种情况都不会丢失或重复任何一行。如果某个文件比数据库记录的短，说明数据已经丢失，Origin 会拒绝向这个镜像追加，而不是破坏来源追溯（不变量 1）。如果读取时发现尾部被另一个进程的封存清空，就重新读取。
- **大小。** 在 171 MiB 按真实形态生成的 Claude Code 合成记录上（大型工具结果、约占四分之一字节的 base64 截图、中英文文本），文件停止增长之后，镜像占 35 MiB（4.9 倍；刚导入时每个文件都还有开放尾部，占 52 MiB）。采集耗时增加约 15%，随机读取一行原始记录平均需要 1.5 ms，而扫描整个未压缩镜像需要 6.8 ms。

### 帧存储 {#frame-stores}

已封存的帧只写一次、永不改变，很适合对象存储，而在中枢上它们占据了大部分空间。帧保存在哪里由*帧存储*决定：`mirror.ts` 决定帧是什么并在 `raw_chunk` 中记录它们，帧存储则按 `raw_chunk` 记录的偏移量保存它们的字节，就好像它们被依次追加到每个镜像的一个文件中。一个库使用以下两种之一（`core` 中的 `frames.ts`）：

- **在磁盘上**：默认方式，也是设备唯一使用的方式：镜像的帧就是上文所述的 `<mirror>.zst`，逐字节相同。
- **在存储桶中**：用于配置了存储桶的中枢（见[个人中枢](guide/hub.md)）：每帧一个对象，通过一个只有两个同步操作的对象存储接口，`put(key, bytes)` 和 `get(key)`。`core` 不发起任何网络请求，所以对象存储由 CLI 提供：一个面向 MinIO 或任何其他兼容 S3 API 的存储的 S3 客户端，用 `node:crypto` 计算 AWS Signature Version 4，使用内置的 `fetch`，支持路径式（path-style）和虚拟主机式（virtual-hosted）URL，只对单个对象执行 `PUT` 和 `GET`。

无论哪种方式，开放尾部都留在磁盘上：每个尾部都不到 1 MiB，仍在增长，并在封存后被清空。

- **键。** 镜像的帧中偏移量为 `<offset>` 的那一帧是对象 `<prefix>/<mirror>.zst/<offset>`，路径各段之间用 `/` 分隔，偏移量至少写成 12 位十进制数，例如 `hub/devices/laptop/claude-code/proj/a.jsonl.zst/000000412345`。键由 `raw_chunk` 的记录推导而来，偏移量也就是 `<mirror>.zst` 中的偏移量，所以无论帧由哪种存储保存，数据库都完全相同：不需要修改 schema，而且一个镜像较早的帧可以在磁盘上、较新的帧在存储桶中。
- **崩溃安全。** 帧在记录它的事务提交之前上传，尾部则在那之后才被清空，与磁盘上的做法相同。如果在上传之后、提交之前崩溃，会留下一个没有任何记录的对象：没有读取会请求它，它的那些行仍在尾部，下一次封存会在同一个偏移量、也就是同一个键下写入这些行的帧，从而替换它。对象永远不会被删除（不变量 3），同一个键只有在替换这样的对象时才会被再次写入。无法上传的帧会让它所在的事务失败，所以它的行留在尾部，设备的推送会被拒绝，直到存储桶恢复。`<mirror>.zst` 中超出数据库记录的字节——中枢使用存储桶之前、一次从未提交的写入留在磁盘上的——会在下一帧写入存储桶之前被截掉，所以这个文件中永远只有数据库记录的帧。
- **读取。** 一帧先从内存读取，其次从 `<mirror>.zst` 读取（如果文件中有这一帧，即中枢使用存储桶之前封存的帧），最后从存储桶读取。中枢在内存中保留最近写入或读取的帧，最多 32 MiB：至少 32 帧，通常超过一百帧，因为一帧 1 MiB 的行压缩后只占 200 到 300 KiB。这足以覆盖那些被反复读取的帧，例如设备正在推送的镜像的最新一帧，下一次推送会读取它来计算尾部哈希。存储桶中没有的帧就是缺失的，它的行也是缺失的（不变量 1）；无法连接存储桶则是一个错误，绝不会被当作缺失的行，因此适配器解析推送来的行时，绝不会拿不到它所请求的前面的行。
- **同步传输。** `node:sqlite` 是同步的，而帧在写事务中写入和读取（封存时，以及适配器解析设备推送时调用 `readLine`），所以对象存储也是同步的。S3 客户端在一个 worker 线程中运行 `fetch`：调用线程把请求发给它，用 `Atomics.wait` 阻塞，直到 worker 发回响应，再用 `receiveMessageOnPort` 取出响应。每个请求都有超时（默认 30 秒）；因网络错误而失败，或被存储回答为繁忙或服务器错误的请求，最多尝试三次。代价是：每次传输期间中枢的事件循环都处于停顿状态，而在封存时，中枢在传输期间一直持有写锁。在局域网中一帧只需几毫秒（向同一台机器上的测试服务器上传 256 KiB 约需 2 ms，其中 worker 线程带来的开销约 0.15 ms），但缓慢或无法连接的存储桶会让中枢在每个请求上停顿，最长可达超时时间。中枢只在推送来的数据块让尾部封存时上传一两帧，并每 10 分钟为每个空闲的镜像上传一帧。
- **库使用的存储桶。** 库第一次使用某个存储桶和前缀时，会把它们记录在 `setting` 中（`raw.bucket`）。此后它拒绝任何其他存储桶，`origin serve` 没有它就拒绝启动，其他命令则从环境变量中读取它；如果它们需要存储桶中的帧而存储桶没有配置，就会失败，并给出需要设置什么的提示。端点不会被记录，所以可以改变。请为每个库使用各自的前缀：两个库如果写入同样的键，就会相互替换对方的帧。
- **把帧移入存储桶。** 中枢使用存储桶之前封存的帧仍留在 `<mirror>.zst` 中，并从那里读取。`origin raw upload` 把它们按上述的键上传，所以再次运行、或在中断之后运行，都不会重复上传任何东西：每一帧在上传前都会被检查（它必须能带着校验和解压成 `raw_chunk` 记录的大小），上传后再从存储桶读回校验；存储桶中已有相同字节的帧则保持不变。它在事务之外运行，所以不像中枢那样每次传输都阻塞等待：它从调用线程发出请求，默认一次传 8 帧，可用 `--concurrency` 调整。某一帧校验失败时，会报告该帧并保留存放它的文件，其他镜像照常继续；出现会让每一帧都失败的错误（例如存储桶无法访问）之后，不再开始新的帧。它列出每一帧都已在存储桶中校验过的 `<mirror>.zst` 文件，`--remove` 会在一个文件的所有帧都校验过后立即删除它。这只是移动帧而不改变它们，所以每个镜像的内容保持不变（不变量 3）。它可以在中枢运行时执行。

### 迁移 {#migrations}

库把它的格式版本记录在数据库文件头中，即 `PRAGMA user_version`：SQLite 为应用程序保留了这个整数，在任何表存在之前就能读取它，它与它所描述的改动在同一个事务中写入，备份也会随数据库一起复制它。Origin 0.1.0 没有记录版本，所以没有版本的库如果有 0.1.0 的那些表，就是版本 1，即 0.1.0 的 schema，否则就是一个新库。打开一个库时（`core` 中的 `migrations.ts`），会把它升级到最新版本：

- **新库**在一个事务中得到当前的 schema 和最新的版本。
- **较旧的库**按顺序执行它缺少的每一个迁移，每个迁移各在一个自己的写事务（`BEGIN IMMEDIATE`）中执行，这个事务也记录它的版本。拿到锁之后会重新读取版本，所以当多个进程同时打开这个库时（CLI，每个 Agent 一个 MCP server），其中一个执行每个迁移，其他进程等待（最多 5 分钟），随后发现它已经完成。失败的迁移连同它的版本一起回滚，错误信息会指出是哪一个；它之前的迁移所做的改动保留，下次打开时会再次执行它。
- **较新的 Origin 写过的库**在其中任何内容改变之前就被拒绝，并提示升级。
- **只为执行命令而打开。** CLI 只在一个命令的参数有效之后才打开库：打印它的用法，或者拒绝它不接受的参数，都不会改动库。

迁移完成之后，schema 中的幂等语句会照常在每次打开时执行，所以新的表、索引、视图或触发器，只要已有数据不需要从中得到什么，就无需迁移即可出现。

| 版本 | 改动 |
|---|---|
| 1 | 首个发布版本 0.1.0 的 schema，不记录版本 |
| 2 | `session.title_manual`：会话的标题是否由用户给出 |
| 3 | 数据：Claude Code 会话的标题，取自已经镜像、但 0.1.0 跳过了的 `ai-title`、`custom-title` 和 `summary` 行。只重新解析含有这几个名称之一（`"ai-title"`、`"custom-title"`、`"summary"`）的行，在设备和中枢上都是如此（`raw/devices/<device>/claude-code/…`） |
| 4 | 数据：库在能读懂记忆流之前镜像下来的记忆流的事件和条目，比如 0.2 的中枢收到较新版本的设备发来的记忆流时就是这样。Claude Code、ZCode 和 Grok Build 在 `memory/` 下的镜像，每一行都会被解析，存下它的事件，并派生它的条目（见[原生记忆](#native-memories)） |
| 5 | 线索（见[线索](#threads)）：`session.git_branch`，根据事件填写；`session_follow` 和 `session_thread`，根据库中已有的内容推导；以及指向线索的召回项，这是 `recall_item` 原来的约束不允许的：SQLite 无法就地修改约束，所以这张表连同它的行、索引和触发器被重新建立 |
| 6 | 提议（见[提议](#proposals)）：`proposal` 和 `proposal_source`，从库中已有的、含有 `propose` 结果的工具结果推导，例如设备先于中枢升级时中枢已经收到的那些 |
| 7 | 设备和 Agent（见[访问](#access)）：`api_token.kind` 和 `api_token.preset`。每个令牌保留它原来能做的（`readwrite`）；如果中枢保存着只有设备才会以它的名称发送的内容（从设备磁盘推送来的、路径为绝对路径的文件，或者它写下的条目、遗忘记录或召回），或者它从未被使用过，它就是设备的令牌，因为以前令牌都以设备命名；否则是 Agent 的令牌。`audit_log` 连同它的行和触发器被重新建立，使它的渠道可以是 `api` |
| 8 | 作者（见[作者](#authors)）：`event_author` 和 `session_kind`，通过重新解析原始镜像中可能含有输入、或说明会话是什么的那些行来推导，设备和中枢都是如此（`raw/devices/<device>/…`，已封存的帧通过它的帧存储读取）；这样的行产生了库中没有的事件时（例如适配器新学会读取的事件：Claude Code 在 Agent 忙碌时排队的提示），会补上这个事件，并重新聚合它的会话。如果库中保存的某次遗忘以这样的事件为目标（例如中枢保存了设备对一个中枢当时还读不到的事件的遗忘），它会立即被隐藏；又因为设备不保存在本地什么也不覆盖的遗忘，设备会在下一次同步时把中枢的遗忘记录全部重新拉取一遍（`setting` 中的 `tombstones.pull-again`），让先在中枢上做出的、针对这样的事件的遗忘也覆盖它（不变量 2）。内置来源的适配器是必需的；人自己的来源在用它的适配器打开库时解析（CLI 总是这样打开），否则保留由类型和正文得出的作者。线索会重新推导，因为 R2 只计入主人的对话（见[线索](#threads)）；版本 5 是从分支上的每个会话推导的。它会报告进度，并与它的版本在同一个事务中执行，所以中断的升级会让库停留在版本 7 |
| 9 | 项目（见[项目](#projects)）：空的 `project_root`（每个设备一行）、`session_place` 和 `place_head`。升级不写入任何行，也不读取文件。设备在解析工作树并追加 `places.jsonl` 时填入它们 |
| 10 | 父会话（见[父会话](#parent-sessions)）：`session_parent`，通过重新解析已经写明父会话的镜像行来填写，设备和中枢都是如此。它不打开 ZCode 的数据库，也不打开 Grok Build 的会话目录，并且除非镜像行已经带有 workflow 对象，否则不会发明工作流运行的分组。`session_parent` 建好之后，在项目表出现之前就镜像下来的 `places.jsonl` 行会被读进这些表。本 Origin 不认识的 `v` 原样留在镜像里，解析时跳过并记一条警告；以后哪个格式开始认识它，就在那个格式的迁移里再调用一次 `reparsePlaces`。`project_root` 每个设备一行，所以两台设备上的同一条路径不会互相覆盖，`place_head` 记下每个会话或路径的最新一行。线索会重新推导，因此子会话会加入父会话的线索，链接工作树里的会话会加入主检出所在的分支。它会报告进度，并与它的版本在同一个事务中执行，所以中断的升级会让库停留在版本 9 |
| 11 | 作为过往消息的召回项（见[召回](#recall)）：`recall_item.excerpt`，即消息的摘录从哪里开始，以及 `recall_item` 原来的约束不允许的层 `messages` 和类型 `event`；这张表像版本 5 那样重新建立，连同它的行（其 `excerpt` 为空）、索引和触发器 |

**什么时候需要迁移。** 除了已有数据不需要从中得到什么的新表、索引、视图或触发器之外，对库格式的任何改动都需要迁移：新增、重命名或删除列，修改约束，修改触发器或视图（`IF NOT EXISTS` 会保留旧的），需要为已有数据填写的派生行，或者因为适配器现在能从镜像的行中读出更多内容而需要重新解析这些行。*schema 迁移*就地修改表；*数据迁移*根据库中已有的内容（包括原始镜像）修改或填写行。两者都要保持不变量：原始镜像和事件永远不会被改写（不变量 3），被遗忘的内容保持被遗忘（不变量 2）。`core` 没有适配器，所以对于需要重新解析镜像中的行的数据迁移，由打开库的进程传入适配器；CLI 正是这样做的，并且在它执行第一个迁移之前，还会先设置好库的帧存储，以便中枢读取存储桶中的帧。

**编写迁移。** 在 `migrations.ts` 的 `MIGRATIONS` 中添加一个版本号为下一个版本的 `Migration`，把 `schema.ts` 改成新的结构，使新库和升级后的库最终完全相同，并在上表中添加它的一行。已经发布的迁移永远不再修改；修正就是一个新的迁移。请在它之前那个版本的库上测试它：测试从 0.1.0 或 0.4.0 的 schema（`packages/core/test/fixtures/schema-0.1.0.sql`、`schema-0.4.0.sql`）构建一个那个版本的库，升级它，再把它的 schema 与新库的 schema 进行比较。

## 采集 {#ingestion}

`origin sync`（以及 MCP server，见下文）会运行每个适配器的 `discover()`，包括内置的适配器和人自己的来源的适配器（见[你自己的来源](#your-own-sources)）；Agent 的 hook 则只采集它指明的那一个文件（见[实时采集](#live-ingestion)）。自上次采集以来大小和尾部都没有变化的文件会被跳过，不需要获取写锁。有变化的文件，其新增的行在 `BEGIN IMMEDIATE` 事务中采集，每个事务最多 1 MiB 的行（更长的单行独占一个事务），因此来自不同进程的并发同步会被串行化，绝不会把同样的字节采集两次；即使在导入大量积压数据时，也没有进程会长时间占用写锁：

1. **游标。** 每个 `raw_file` 行记录 `bytes_ingested`、`lines_ingested` 和 `tail_hash`（最后采集的 4 KB 的 SHA-256）。游标在写锁之下读取，并且只读取游标之后的字节。
2. **改写检测。** 如果文件变小了，或者尾部不再匹配，说明它是被改写而不是被追加。Origin 会开启一个新的*代次*，使用全新的镜像，并保持旧镜像完好无损（不变量 3）。
3. **只取完整行。** 截至最后一个换行符的字节会被追加到镜像中（见[原始镜像](#raw-mirrors)）；末尾不完整的行留待下一次同步。镜像的内容始终等于其代次已采集的字节，因此被中断的同步遗留在游标之后的字节，会在追加之前被丢弃（不变量 1）。
4. **解析与插入。** 每一行都经过 `parseLine`；失败只计数，不致命。事件以 `<source>:<native-id>[#<block-index>]` 为 id、用 `INSERT OR IGNORE` 插入，这使同步具有幂等性（不变量 3）。每个事件都保存它的镜像文件和行号（不变量 1）。输入的作者从同一行得出，随它一起保存；声明某个会话是子会话或无界面运行的行也会被记录（见[作者](#authors)）。写明某个会话的父会话的行也会记录这条链接（见[父会话](#parent-sessions)）。记忆流中的一行还会产生一个条目的版本（见[原生记忆](#native-memories)），含有 `follow` 结果的工具结果产生一条跟随链接（见[线索](#threads)），含有 `propose` 结果的工具结果则产生一条提议（见[提议](#proposals)）。
5. **收尾记录。** 受影响的会话被重新聚合，它们的线索也随之更新，游标在同一个事务中前移，并由一行 `sync_log` 记录这次运行。一行也可能带有它所属会话的标题（`sessionTitle`）：最新的标题替换之前的标题，但 Agent 生成的标题永远不会替换用户给出的标题（`manualTitle`）。

**压缩的来源。** 适配器可以把文件标记为 `compression: 'zstd'`。Origin 随后使用 Node 内置的 zstd，采集并镜像解压后的内容，因此游标、行号和原始行的工作方式与普通文件相同。压缩文件只写入一次，所以自上次采集以来没有变化时会被跳过，并且每个压缩文件都在单个事务中采集。

**生成的来源。** 有些 Agent 把会话存在数据库里，并且原地修改其中的行：回复流式输出时会改，过了很久也还会改；或者把会话的标题保存在一个每一轮都重写的文件里（Grok Build 的 `summary.json`）。对这样的来源，适配器把它的每一路内容（例如一个会话）标记为 `generated`：Origin 不读文件，而是向适配器要已镜像的最后一行之后的行，每次最多约一个事务的量，一直要到没有为止，然后像文件的行一样镜像和采集它们。适配器在一条记录不会再变时（例如一条消息完成之后）才把它写出，而且只写一次，所以内容只会增长（不变量 3），也不需要检测改写；已镜像的最后一行告诉适配器从哪里接着写，它自己不保存任何状态。写出之后又改变的记录不会再写一次：它被镜像的那一行，就是它的事件所来自的版本（不变量 1）。每一路内容还有一个令牌，可能有新行时就会改变；令牌和游标存在一起，占用文件尾部哈希的位置，令牌没变的内容会被直接跳过，不去问适配器。中枢像接收其他镜像一样接收这些镜像，并用同一个适配器解析。

**多个进程。** CLI、每个 Agent 会话各一个的 MCP server，以及 Agent 的 hook，可能同时使用同一个库。读操作从不等待写操作（WAL）。写操作最多等待写锁 10 秒（busy timeout）；由于同步只为有变化的文件获取写锁，并且每次只持有一个有上限的事务，所以即使另一个进程正在导入大量积压数据，一次同步或一次 `remember` 最多也只需等待大约一个这样的事务。每次检查点之后，预写日志会被截断到 64 MiB（`journal_size_limit`），所以大量导入不会留下几个 GB 的日志。

**在中继上**，本地不采集任何内容：每个文件新增的完整行以同样的方式读取（游标、改写检测、解压后的内容、生成的行），然后发送给中枢，由中枢按本节所述采集（见[中继](#relays)）。

### 实时采集 {#live-ingestion}

同步靠查看来发现新的行：`origin sync`，以及 `origin mcp` 在工具调用之前和它的 Agent 运行期间每分钟一次（见 [MCP server](#mcp-server)）。Claude Code 和 Codex 还能告诉 Origin 何时可能有新的行：它们的 hook 会在一轮结束时（`Stop`）、子 Agent 停止时（`SubagentStop`），以及 Claude Code 在压缩之后（`PostCompact`）运行一条命令，并在标准输入上给出一个事件，其中指明了会话的记录文件。`origin agents connect` 会添加这样的 hook，它们在后台（`"async": true`）运行 `origin sync --hook <agent>`，所以 Agent 从不需要等待它们（它添加的 hook 见[召回](#recall)）。这样，会话新增的行在每一轮结束后片刻就进入库，随即进入中枢。

- **一个文件，同样的规则。** hook 读取事件中的 `transcript_path`，遇到 `SubagentStop` 时还读取子 Agent 自己的 `agent_transcript_path`。每个路径都经过其适配器的 `locate`，得到 `discover()` 列出的那个文件，因此无论以哪种方式找到，一个文件都只有一个镜像；然后用 `syncFile` 采集：执行上面的各个步骤，只针对这一个文件，从它的游标开始，使用同样有上限的事务，包括改写检测、封存、标题、原生记忆、线索和会话聚合。只有读到了行，才会用一行 `sync_log` 记录这次运行；封存闲置镜像的尾部留给完整的同步去做。
- **是信号，而不是交付。** Agent 异步写入它们的记录文件，所以 hook 运行时，这一轮的最后几行可能还没写下。和往常一样只读取完整的行：还没写下的内容由下一个 hook 读取，或者由 MCP server 每分钟一次的查看读取（它仍作为后备），Agent 离开时还有 server 的最后一次同步。
- **从不妨碍 Agent。** hook 只加载核心、适配器和中枢客户端，以便快速启动。它最多等待 3 秒获取写锁；无论出了什么问题，它都不在标准输出上打印任何内容，在标准错误中说明原因，并以 0 退出。不是 hook 事件的输入、适配器无法定位的路径、不存在的文件，以及它不认识的 Agent，都会被忽略，这时它连库都不打开。并行会话和子 Agent 的 hook 可能同时运行：写锁，以及在写锁之下重新读取的游标，会把它们串行化，所以每一行只采集一次。
- **到中枢。** 在已接入中枢的设备上，采集到行的 hook 随后会推送这个文件新增的镜像字节，与同步推送每个镜像的方式相同，只是先向中枢查询这一个文件的游标；它等待中枢最多 3 秒。没有发出的内容，以及这期间写下的条目、遗忘记录和召回，留待下一次同步；由于文件已经变化，MCP server 的下一次查看就会同步。在中继上，hook 把这个文件新增的完整行直接发送给中枢，与中继同步时发送每个文件的方式相同（见[中继](#relays)），同样以 3 秒为限。
- **会话结束时不运行。** `SessionEnd` 不设 hook：Claude Code 给所有 `SessionEnd` hook 共 1.5 秒，Codex 给 1 秒，不够连上中枢；而会话的最后几行，会由 MCP server 的最后一次同步，或者下一个 hook 或同步读取。
- **其他 Agent。** Cursor、ZCode 和 Grok Build 没有采集 hook：ZCode 和 Cursor 编辑器把会话存在数据库里，Origin 把它们当作生成的来源读取；Grok Build 的会话是目录，其中的标题文件会被原地重写。它们新增的行仍像以前一样靠查看发现（见[待解决的问题](#open-questions)），人自己的来源新增的行也是如此。

### 你自己的来源 {#your-own-sources}

人的工作也发生在 Origin 的适配器看不到的地方：其他 Agent 运行时、聊天工作区、通知流、笔记流水线。Origin 没有为每一种都写一个适配器，而是读取它自己的一种格式，**事件行**：UTF-8 的 JSONL，每行一个事件，由写入它的东西不断追加（字段与规则见 [sources.md](sources.md#your-own-sources-event-lines)）。写入者在 Origin 之外：一个轮询或订阅某个服务的脚本追加行，而 Origin 自己不发起任何网络调用（不变量 4），像读取 Agent 的记录一样读取它们。随 Origin 一起发布的唯一一个写入者，即它的 OpenClaw 插件（`packages/openclaw`，见[接入 OpenClaw](guide/openclaw.md)），也不例外：它运行在 OpenClaw 的 Gateway 中，Origin 只通过它写出的行认识它。它交给 OpenClaw 的 Agent 的读取工具，像任何 Agent 一样调用中枢的 `/mcp`（见 [MCP server](#mcp-server)）。

- **目录就是注册。** 库的主目录下 `sources/` 中的每个目录（`~/.origin/sources/<name>/`），或者指向某个目录的链接，都是一个来源，其 id 就是目录名，前提是这个名称由 2 到 32 个小写字母、数字和连字符组成、以字母开头，既不是内置来源的 id，也不是 `origin`、`hub`、`local`、`all` 和 `devices` 之一（`devices` 用于中枢存放其设备文件的镜像，即 `raw/devices/…`）。其他名称的目录会被忽略，每次同步在标准错误上给出一条警告（`origin mcp` 只警告一次）。没有来源表：CLI 每次列出它的适配器时都会列出这些目录，所以新目录会在下一次同步时被读取；删除的目录不再被读取，而已归档的内容保留。
- **同一个适配器。** 每个这样的来源都由事件行适配器（`adapters` 中的 `createLinesAdapter`）读取，它的文件是目录下任意深度的 `.jsonl` 文件，隐藏文件除外，最旧的在前；它的 `locate` 指向同样的文件，所以单个文件也可以单独采集（`syncFile`）。目录中的 `VERSION` 文件给出写入这个来源的程序的版本，它的事件把这个版本记录为 Agent 版本。此后的采集与上文相同：游标、重写检测、`raw/<name>/` 下的镜像、封存、标题、会话汇总、按 `branch`（规则 R2）和跟随链接形成的线索、提议，以及变更流；召回能看到它的项目中任何来源的会话，依据 `cwd` 或 `project`。
- **解析。** 与每个适配器一样纯粹、确定：一行是一个事件，`<source>:<id>`；不是有效事件的行是解析错误，会被计数、从不致命，并且留在镜像中（不变量 1）。`memory` 事件会被拒绝：原生记忆只来自 Agent 保存的记忆文件。
- **跨库。** 设备像推送任何镜像一样推送它自己的来源的镜像，中继也像发送任何记录的行一样发送这些文件的行（见[复制](#replication-raw-mirrors-entries-and-tombstones-up-tombstones-down)和[中继](#relays)）。对于任何不是内置来源、而名称又可以作为人自己来源名称的文件，中枢都用事件行适配器解析，无论它自己有没有这样的目录。
- **在中枢上，没有设备。** 不在这个人任何设备上运行的写入者，例如机器人、云端的运行时或流水线，用自己的令牌通过 `POST /v1/sources/<name>/lines`（见 [HTTP 接口](#http-interface)）向中枢追加事件行。中枢把它们追加到它为该来源的文件 `path` 保存的镜像中，视为令牌所属设备发送的内容（`@<device>:<path>`），走的是设备推送镜像时的同一条采集路径：`appendRemoteLines` 在该文件最新一代的中枢游标处，用 `appendRemote` 每次追加 1 MiB 的行，所以游标、封存、解析和计数都相同。投递至少一次：事件 id 已在库中的行照样追加到镜像中，因为镜像记录的是发送过来的内容（不变量 3），但它不会新增事件，而是计为重复。
- **没有 hook。** 没有什么会告诉 Origin 某个来源有了新的行：它们靠查看发现，由 `origin sync`（`--source <name>` 只读一个来源）发现，或者在 Agent 运行期间由 `origin mcp` 每分钟发现一次。

### 作者 {#authors}

一条输入是谁写的（见[核心对象](#core-objects)）是它所在那一行的事实，只有它的来源能说清。适配器从它的 Agent 为此写下的字段中读取，按消息、也按会话，以下规则中第一条适用的规则决定作者：

1. **它的会话。** 某一行可以声明一个会话是**子会话**，它的提示由 Agent 写成（子 Agent、工作流的一个步骤），或者是**无界面运行**，由某个程序启动。子会话的每条输入都属于 Agent，无界面运行的每条输入都属于系统，不论输入本身怎么说，因为有些 Agent 会把子会话的提示标成用户输入的。这一行可以是该会话自己的，也可以是另一个会话的，例如父会话点名它启动的子 Agent。
2. **Agent 为这条消息写下的字段**，说明是用户输入的，还是运行时、某个任务或另一个 Agent 写的。它对 meta 事件同样适用：Agent 没有放进对话记录的输入也可以是主人的，只是不算提示。
3. **它的类型。** 没有这类字段的 meta 事件属于系统。
4. **它的正文**，用于没有这些字段的旧记录：读起来像提示（见[会话名称](#search-and-timeline)）且不是子 Agent 的（Claude Code 的 sidechain）消息属于主人，其他消息属于系统。

- **分开保存，读取时合并。** 采集把每条输入的作者、说话人和决定作者的字段以它的事件的 `seq` 为键保存（`event_author`），并把某一行声明为子会话或无界面运行的每个会话连同那个字段保存下来（`session_kind`）；事件从不改动（不变量 3）。读取时把两者合并为输入的**有效作者**：子会话的输入属于 Agent，无界面运行的输入属于系统，其余的属于它自己那一行给出的作者。所以行到达的顺序无关紧要：无论父会话的行先到还是子会话的行先到，子 Agent 的提示都属于 Agent，中枢从设备的镜像中也推导出同样的结果。
- **派生、可重建。** 两者都派生自原始行，每个解析这些行的库都得出相同的结果，`rebuildAuthorship()` 会从镜像重新推导它们（见[存储](#storage)）。没有保存作者的输入（例如在已升级的库上仍在运行的旧版本进程所保存的输入）按第 3、4 条规则读取。
- **每个来源的字段**见 [sources.md](sources.md)，与它的格式写在一起：Claude Code 的见下文；ZCode 按 `task_type` 把工作流步骤和子 Agent 的会话当作子会话，其余的读取 `semantics.origin`；Grok Build 按父会话的 `subagent_spawned` 更新或子 Agent 自己的 `session_kind` 把子 Agent 当作子会话；Codex 按 `session_meta` 的 `source` 把子 Agent 的 rollout 当作子会话，把 `codex exec` 当作无界面运行；Cursor 会标出它模拟的消息。不记录这些字段的来源，以及不记录它们的 Agent 版本，按上面的规则读取。
- **事件行**自己说明，用 `author` 和 `speaker`（见[你自己的来源](sources.md#your-own-sources-event-lines)）：没有 `author` 的行，消息属于某个人（person），meta 事件属于系统，所以 `owner` 要由来源自己说明，没有说话人信息的录音属于某个人。

### Claude Code 映射 {#claude-code-mapping}

- 文件：`<projects>/<cwd-slug>/<session-id>.jsonl`，以及 `<session-id>/subagents/` 下的子 Agent 记录。`tool-results/` 目录会被跳过，每个项目的 `memory/` 目录则作为记忆流读取（见[原生记忆](#native-memories)）。
- `user` / `assistant` 行变成事件。文本块合并为一个 `message` 事件；每个 `tool_use` 和 `tool_result` 块各自成为一个事件（分别截断到 2,000 / 4,000 个字符）。`isMeta` 行变成 `meta` 事件。`thinking` 块不建立索引，但保留在原始镜像中。
- 输入是谁写的（见[作者](#authors)），依次判断：子 Agent 的（`isSidechain`，或 `subagents/` 下的记录）属于 Agent；无界面运行的（`entrypoint` 为 `sdk-*`，`claude -p` 和 Agent SDK 的每一行都有）属于系统；然后是 `origin.kind`：`human` 属于主人，`task-notification` 属于系统，`peer` 和 `coordinator` 属于 Agent，说话人是 `origin.name`；压缩的摘要（`isCompactSummary`）属于系统；`promptSource` 为 `typed` 或 `queued` 的属于主人。2.1.303 之前的版本既不记录 `origin` 也不记录 `promptSource`，所以它们的其他输入按类型和正文读取。
- 用户在 Agent 忙碌时排队发出的提示，即 `type` 为 `queued_command`、`origin.kind` 为 `human` 的 `attachment` 行，单独成为一个 `message` 事件，属于主人，以该行的 uuid 为 id，正文保持原样，meta 中记有 `queued`。排队的任务通知，以及以这种方式交给子 Agent 的内容，不产生任何事件；原始镜像保留它们。库在 Origin 能读取它们之前镜像的行，会在升级时产生这些事件（迁移 8）。
- 会话自己的记录中（而不是其子 Agent 的记录中）的标题行设置它的标题。每种标题行都会被写入很多次，最新的一行就是当前的标题：`ai-title` 行由 Claude Code 随着对话的进行而生成；`custom-title` 行是用户给出的名称（`/rename`、`--name`），之后的 `ai-title` 行不会替换它；较旧的记录中则是 `summary` 行。`agent-name` 行重复这些标题之一，不会被读取。
- 事件上的标签取 `cwd` 的最后一段。目录在工作树中时，Origin 显示的项目是主工作树（见[项目](#projects)）。

其他适配器的映射与各自的格式一起记录在 [sources.md](sources.md) 中（Codex 见 [Codex CLI](sources.md#codex-cli)；事件行见[你自己的来源](sources.md#your-own-sources-event-lines)）。

### 原生记忆 {#native-memories}

Claude Code、ZCode 和 Grok Build 都维护自己的记忆：由 Agent 原地写入、改写和删除的 Markdown 文件，每个文件一条笔记，每个项目或工作区一个目录（各自的布局见 [sources.md](sources.md#native-memories)）。Origin 把它们单向导入为条目：只读取这些文件，从不写入，于是一个 Agent 记住的内容能到达所有 Agent，并且带着来源。

- **记忆流。** 每个记忆目录是一个[生成的来源](#ingestion)，即一条*记忆流*，镜像在它所属来源的 `memory/` 下（例如 Claude Code 某个项目的记忆流是 `memory/<cwd-slug>.jsonl`）。它的适配器为记忆文件的每个版本写出一行，保存整个文件，文件被删除时也写出一行：先按从旧到新的顺序，为自记忆流最后一行以来新出现或内容有变化的每个文件各写一行，再为每个已经消失的文件各写一行。一行保存文件名、`write` 或 `delete`、它的时间（文件的修改时间，或者发现删除的时间）、这些记忆所属的项目和工作目录（已知时），以及写出这一行之后目录的状态：每个文件最新一行的 id 和它内容的哈希，文件删除之后则没有哈希。适配器根据最后一行中的状态写出接下来的行，所以它自己不保存任何状态，内容也只会增长（不变量 3）。记忆流的令牌是它的文件的名称、大小和修改时间的摘要，所以没有变化的目录会被直接跳过，不读取任何文件。读取失败的文件保持原样，超过 256 KiB 的文件不计入。
- **事件。** 每一行是一个类型为 `memory` 的事件：正文是写入时的文件（删除时为空），并记下文件名和操作。它的 id `<source>:memory:<hash>` 是一个从该文件上一行串联而来的 SHA-256：取上一行的 id（文件的第一行则取记忆流的路径和文件名）、操作和内容的哈希。因此，同样的历史无论在哪里解析都得到同样的 id，而删除后又出现的文件会得到新的 id。记忆事件不属于任何对话：它不计入任何会话，记忆流也从不出现在时间线中。
- **每个记忆文件一个条目。** 适配器读出文件每个版本中的记忆：它的类型、正文和置信度（见 [sources.md](sources.md#native-memories)）；文件里没有记忆时什么也不读出。Origin 从每一行派生出一个条目的版本（`core` 中的 `memories.ts`）。它引用这一行的事件（不变量 1）；它的 id 由事件的 id 派生（`ent_` 加一个 SHA-256 的 24 个十六进制字符）；作者为 `<source>@<device>`，origin 为记忆所在的设备：对本库自己的文件是本库的名称，在中枢上则是发送这条记忆流的设备或中继。
  - 文件的第一个版本开始一个条目。之后的每个版本取代从该文件上一行派生出的版本，时间取文件的修改时间，并且晚于被取代的版本（不变量 3），所以条目的当前版本跟随文件变化。
  - 被删除的文件，或者被清空了内容的文件，会结束这个条目：它的最后一个版本被再写一次，`valid_to` 设为删除的时间。文件重新出现时会取代这个版本，条目重新成为当前的。没有可结束内容的删除不派生任何东西，而在一个没有派生出任何东西的行之后的版本会开始一个新的条目。
  - 导入的条目和其他条目一样可以纠正和遗忘。在 Origin 中做的纠正会取代当前版本，而文件的下一个版本取代它之前派生出的版本；按[并发纠正](#entries)的规则，两者中较晚的一个是当前版本，所以文件在纠正之后再有变化时，以文件为准。被遗忘的条目在文件变化时保持遗忘：每个新版本及其引用的事件都在到达时就被隐藏（不变量 2），恢复会把条目带回到它最新的版本。遗忘只在 Origin 中隐藏条目；Agent 的文件保持原样。
- **每个库都派生。** 与事件一样，这些版本由每个解析这条记忆流的库派生，id 和内容都相同：设备从自己的文件派生，它的中枢从设备的镜像或中继发来的行派生。因此它们从不发送给其他库：`imported_entry` 列出它们，设备推送时会略去它们，它们也不会让库的名称固定下来（见[存储](#storage)）。对它们的纠正和遗忘照常发送；中枢一旦解析了设备的镜像（设备会先推送镜像），就有了这些纠正和遗忘所指向的版本。较早版本的中枢收到设备发来的记忆流时只镜像、不读取；升级之后，它在打开库时读取这些记忆流（迁移 4，见[迁移](#migrations)），在此之前，设备对导入条目的纠正会等待中枢。在中枢派生出某个导入条目之前，设备上对这个条目或其记忆事件的遗忘，会在条目派生出来时覆盖它。
- **在结果中。** MCP 结果中的条目带有 `imported`；管理界面和 CLI 会标出导入的条目，显示条目的有效期何时结束，并把记忆事件显示为它所属文件的一个版本。MCP 的 instructions 会告诉 Agent，导入的条目对应某个 Agent 自己的记忆文件，所以文件之后的变化会取代在 Origin 中做的纠正。

## 条目 {#entries}

- **记住（remember）。** 一个条目是一条自成一体的陈述，带有类型、0 到 1 之间的置信度、作者（`<agent>@<device>`：MCP 客户端的名称加上它写入的库的名称，例如 `claude-code@laptop`；CLI 和管理界面写入时为 `user@<device>`；直接使用中枢的 Agent 见[访问](#access)）、可选的项目和有效期，以及至少一个来源（不变量 1）。来源可以是一个事件 id、一段精确引文，或者两者兼有：
  - 给出 id 时，该事件必须存在且可见；如果同时给出引文，引文必须出现在该事件中（忽略空白和大小写）。
  - 只给出引文时，Origin 引用包含该引文的最新可见 `message` 事件，找不到时退而查找 `propose` 结果以外的 `tool_result` 事件。工具调用永远不参与匹配，因为 Agent 自己那次包含该引文的 `remember` 调用，本身就会作为工具调用被记录下来。最新指时间戳最新。Origin 像检索那样查找引文中的词（见[检索与时间线](#search-and-timeline)），每种事件最多核对含有所有这些词的最新 25,000 个事件，所以完全由非常常见的词组成的引文，可能在较早的事件中找不到；这时请改为引用事件 id。
  - `cognition` 是用户的偏好、方法、目标或边界，所以只能来自用户自己的话：当它引用的事件中有输入（用户消息或 meta 事件），而这些输入的有效作者都不是主人（见[作者](#authors)）时，它会被拒绝（`A preference can only come from the user's own words: …`），并列出这些事件以及写下它们的是谁。不是输入的来源，例如 Agent 自己的消息、工具调用和结果，以及记忆文件的版本，两边都不算。`remember`、`propose`、接受提议，以及把条目改为 cognition 或给 cognition 增加来源的 `correct` 都会检查；从记忆文件导入的条目，以及库从别的库收到的条目，不检查。
  - 提议的事件只能通过接受这条提议来引用（见[提议](#proposals)）：`remember` 和 `correct` 都会拒绝它。
- **纠正（correct）。** 纠正一个条目的当前版本，会插入一个 `supersedes` 它的新版本（不变量 3）。原有来源会被继承，也可以添加新的来源。纠正的时间总是晚于被纠正的版本，即使本机时钟偏慢也是如此。一个条目的所有版本共享它的 `root`，也就是第一个版本；它们合起来构成这个条目的版本链。
- **并发纠正。** 两个库可能在互相知道之前纠正了同一个版本，所以一个版本可以被不止一个版本取代。这时版本链出现分叉，而每个库都以同样的方式解决它：链中 `(created_at, id)` 最大的版本是**当前**版本，其他版本都是已被取代的版本。一个已被取代、但没有被任何版本纠正的版本，是输给了一次并发纠正，会被标记出来（`concurrent`）。只有当前版本可以被纠正。
- **状态**由推导得出：如果有生效中的遗忘覆盖该条目（见[遗忘](#forgetting)），则为 `forgotten`；如果它是所在版本链的当前版本，则为 `active`；否则为 `superseded`（`superseded_by` 指向当前版本）。除非请求历史，查询只返回活跃条目；被遗忘的条目永远不会被返回。历史按从旧到新的顺序列出版本链中的每个版本，包括分叉。
- **有效期。** 条目可以说明它何时成立（`valid_from`、`valid_to`）。`valid_to` 一过，条目就*结束*了，例如文件已被删除的导入记忆：它成为历史，不再是当前的知识。除非请求历史，检索和列表都不包含已结束的条目（MCP `search`、`origin search`、`origin entries`，以及管理界面的检索和条目页；`origin entries --history` 和管理界面的历史会包含它们），而 `get` 和 `origin show` 仍然显示它们及其有效期。
- **导入的条目**派生自 Agent 为自己保存的记忆，并标记为 `imported`（见[原生记忆](#native-memories)）。

## 遗忘 {#forgetting}

`forget` 接受一个条目 id 或事件 id，以及一个原因，并写入一条遗忘记录，也就是一次**遗忘**（不变量 2）。它按三条规则隐藏它的目标及其连带内容：

1. **遗忘一个条目**会隐藏它的所有版本（整条版本链，包括分叉），以及这些版本引用的所有事件。
2. **遗忘一个事件**会隐藏该事件，并像规则 1 那样隐藏所有引用它的条目。
3. **当前版本不再有任何可见来源的条目**已经失去溯源，因此同样会被隐藏，包括它的每个版本。这一步不会再隐藏其他事件，所以级联到此为止。

版本链要么整体被隐藏，要么完全不被隐藏。被隐藏的条目和事件会从检索、时间线、会话计数、`get` 和 `sources` 中消失，被隐藏的事件也不能再被引用。重新同步——即使源文件已被改写——也不会让它们回来，因为事件 id 是稳定的，而隐藏按 id 生效。不会隐藏任何新内容的遗忘不会被记录。

**遗忘是一条记录。** 每条遗忘记录都保存它的目标、原因、时间、创建它的库（`origin`），以及在已知时由谁做出（`author`：Agent 的 `forget` 记为 `<agent>@<device>`，CLI 和管理界面记为 `user@<device>`）。无论在哪里遗忘，都必须给出原因：MCP 工具、CLI 和管理界面都会拒绝空的原因（Origin 0.1 写下的遗忘记录可能没有原因）。`tombstone` 中从不删除任何东西，所以遗忘与恢复的历史始终完整。

**恢复。** 主人可以随时恢复一次遗忘，并给出原因，方式是 CLI（`origin restore`）或管理界面；Agent 不能恢复。恢复本身也是一条遗忘记录，有自己的 id、原因、时间、origin 和作者，它的目标是那次遗忘的 id：它遗忘了那次遗忘。没有恢复以它为目标时，一次遗忘就是**生效中**的。只有遗忘可以被恢复，而且只能恢复一次；恢复不能被恢复。要再次隐藏目标，就再遗忘它一次：这会产生一次新的遗忘，有它自己的记录。

**遗忘覆盖什么。** 只要有生效中的遗忘覆盖一个条目或事件，它就被隐藏。每次遗忘在一个库中覆盖的内容记在 `tombstone_effect` 中，一项内容可以被多次遗忘覆盖，覆盖方式有四种：

- `direct`：按本库的数据，由它的目标经规则得出的内容，包括之后才到达的版本和引用条目。
- `listed`，在设备上：它的中枢为这次遗忘列出的内容。中枢每发来一份新的列表，就替换上一份，因为中枢为它持有的条目判断规则 3，并且可能在一次恢复之后撤回某个判断。
- `reported`，在中枢上：发送这次遗忘的设备在它那里覆盖的内容，累加到它之前所报的内容上。
- `cascade`：本库中的规则 3。应用一次遗忘时，凡是引用了它所覆盖的事件、而当前版本已不再有可见来源的版本链，都由它覆盖。

`forgotten_entry` 和 `excluded_event` 保存被隐藏的内容，每一项都记有一次覆盖它的、生效中的遗忘；每个查询都据此过滤，所以隐藏不会让查询比以前多花任何代价。

**恢复会带回什么。** 一次遗忘不再生效时，它覆盖的每个事件都会回来，除非另有生效中的遗忘覆盖它。它覆盖的每条版本链，以及引用了回来的事件的每条版本链，都会重新判断：如果另有生效中的遗忘按自己的规则或自己中枢的列表覆盖它，或者它的当前版本仍然没有可见来源（规则 3），它就继续被隐藏；后一种情况下，凡是覆盖了这些来源之一的生效中的遗忘，都覆盖它。在中枢上，设备对这样一条版本链所报的内容也会这样重新判断。其余一切都会回来，连同会话计数、检索结果和引用，所以一次恢复会让库回到仿佛那次遗忘从未发生的样子。回来的条目中由本库自己写下的那些，会在 `change_log` 中再次记录，这样设备会把隐藏期间扣下的条目发给中枢。CLI 和管理界面在恢复之前会先展示它将带回的内容。

**跨库。** 遗忘记录的 id 是全局的，所以在一个库中创建的遗忘或恢复，到达任何库时都保持它的 id、origin、原因和作者。库按规则把一次遗忘应用到自己持有的数据上，并覆盖发送方列出的内容，只要库认识那些 id；除非库知道这次遗忘已被恢复，否则把这些都隐藏起来。一次恢复会解除它的遗忘；如果那次遗忘还没有到达，就等待它：中枢会保存这样的恢复，而设备只保存它持有的遗忘的恢复，会在遗忘之后再次收到这条恢复（见[复制](#replication-raw-mirrors-entries-and-tombstones-up-tombstones-down)）。同一条遗忘记录应用两次不会改变任何东西。一项内容是否被隐藏，只取决于生效中的遗忘以及它们覆盖的内容，而遗忘记录只增不减，所以无论遗忘和恢复以什么顺序到达，各个库都会收敛到同一个状态：恢复先于它的遗忘到达，遗忘在别处已被恢复之后才到达，或者其中任何一条被应用两次。之后才到达、属于一条被隐藏的版本链的版本，在到达时就会被隐藏；来源已在本库中被隐藏的条目也是如此（规则 2 和 3）；某次遗忘以它为目标、或以它引用的事件为目标、而在应用这次遗忘时两者都还不在本库中的条目，同样如此：从原生记忆派生的条目在每个库中的 id 都相同，所以可能在一个库中被遗忘之后，另一个库才派生出它。

遗忘是隐藏，而不是擦除。原始镜像文件仍保留在磁盘上（不变量 3），但永远不会被展示，恢复也依赖它们。物理擦除被遗忘的内容会是一个单独的、显式的操作；目前没有实现。CLI 会先展示一次遗忘将隐藏的内容，以及一次恢复将带回的内容，只有加上 `--yes` 才会执行。

## 提议 {#proposals}

Agent 推断出本人没有说过的内容，或者代本人整理记忆时，不把它当作知识写下：它**提议**一个条目，由本人审阅。这是主动工作中只做记录的第一步：Agent 想要记住的内容先被记录下来，经本人校准之后才算数。不调用任何模型，提议也不需要任何复制：它像跟随链接那样从归档中推导出来（见[线索](#threads)）。

- **派生自 Agent 的记录。** MCP 工具 `propose` 像 `remember` 检查条目那样检查一条提议，不写入任何内容，并把它完整地返回：`{ "proposal": "prp_…", "kind", "text", "confidence", "project", "valid_from", "valid_to", "note", "sources": [{ "event_id", "quote" }] }`，它的 id 和 `ent_` id 一样是随机的。Agent 的记录把这个结果记为一个工具结果，采集从每个这样的事件推导出一行 `proposal`，并为它引用的每个事件推导出一行 `proposal_source`，每个解析这一行的库都是如此。这个 JSON 对象是从结果的正文中找出、单独解析的，所以 Agent 可以在它前后加上别的文字；同样的正文被引在另一个结果之中时，引号被转义，而被截断的结果无法解析，所以两者都不会产生提议。适配器只保留工具结果的 4,000 个字符，所以结果会超过 3,800 个字符的提议会被 `propose` 拒绝。按时间、再按 id，最早携带一条提议的事件是它自己的事件，所以之后的副本（例如某个工具把这个结果又打印了一遍）不改变任何东西，无论它们以什么顺序到达。`rebuildProposals()` 从事件（包括被隐藏的事件）重新推导它们，结果相同。
- **状态由推导得出，从不存储**，与条目一样：只要有一个未被遗忘的条目引用提议的事件，它就是 `accepted`；只要有一次生效中的遗忘以它的事件为目标，它就是 `rejected`；否则为 `pending`。
- **接受**以 `user@<device>` 的身份，通过 `remember` 写下一个条目，取提议的类型、正文、置信度、项目和有效期。它引用提议所引用的事件及其引文，也引用提议自己的事件，引文是结果中记录的所提议的正文，所以它的出处既显示它依据的内容，也显示它是被提议出来的（不变量 1）。这个条目像其他条目一样复制，提议在它到达的每个库中都成为已接受。接受是从提议得到条目的唯一途径，也是条目引用提议事件的唯一途径：`remember` 和 `correct` 都会拒绝引用它，引文也永远不会在 `propose` 的结果中被找到。之后本人可以像对待其他条目那样纠正或遗忘这个条目。已经接受、已被拒绝或被隐藏的提议不能被接受，引用了本库尚未持有的事件的提议也不能。
- **拒绝**通过遗忘操作，以本人的原因遗忘提议的事件：这是一条有记录、可恢复的遗忘记录，像所有遗忘一样复制（见[遗忘](#forgetting)）。提议在这次遗忘到达的每个库中离开所有列表，恢复则使它重新成为待审。被隐藏的只是结果的事件：Agent 的那次调用含有它所提议的内容，它像其他工具调用一样留在会话中，也可以被遗忘。
- **为什么沿用条目和遗忘。** 被接受的提议就是一个条目，被拒绝的提议就是一次遗忘，所以提议不增加需要复制的操作，不增加需要在各库之间保持一致的状态，也不增加不变量：出处、有记录的遗忘和恢复都和其他内容一样起作用。
- **可见性。** 只有当提议的事件和它引用的每个事件都可见时，提议才会被展示（不变量 2）。正如引用了被遗忘事件的条目会被隐藏（规则 2），引用了被隐藏事件的提议会离开所有列表、它的卡片和变更流，并随恢复而回来。被拒绝的提议像遗忘记录那样为它的所有者列出：只列 id，以及那次遗忘的原因、作者和时间，从不列出它的正文，正文只在那次遗忘自己的页面上展示（见[管理界面](#admin-ui)）。
- **只有本人**可以接受或拒绝，通过 CLI 或管理界面；Agent 没有这样的工具，就像它们没有恢复的工具一样。待审的提议还不是知识：条目、检索和召回都不包括它们。
- **整合。** Origin 只存储和提供数据，不调用模型，所以它自己不整合任何东西。Origin 之外的 Agent（例如个人 Agent）通过 MCP 工具读取本人的工作（`digest` 读一天，`changes` 读它上次查看以来进入库中的内容，`get` 和 `timeline` 读一个会话，`search` 查条目已经说了什么），并用 `propose` 提议值得保留的条目；`changes` 和 `digest` 会列出已经提出的提议，它不必再提一次。和所有提议一样，它的提议是从它自己的记录中读出来的，所以它的会话进入 Origin 时，提议才随之进入：作为 Origin 读取的 Agent 的会话，经由 OpenClaw 插件，或者写成事件行（见[你自己的来源](#your-own-sources)）。它何时运行、花费多少，由它自己决定；本人像对待其他提议一样接受或拒绝它的提议。
- **归属。** 提议属于它指明的项目；没有指明时，属于它所在会话的项目。由它产生的条目属于它指明的项目，所以没有指明项目而提议的认知在所有地方都成立。

## 检索与时间线 {#search-and-timeline}

事件检索只覆盖 `message` 事件，除非请求包含工具事件（`--all` / `include_tools`），并且从不返回已遗忘的事件。条目检索覆盖有效期没有结束的活跃条目（见[条目](#entries)）。

**词。** 查询按空白切分，每个词都必须作为子串出现在文本中（不区分大小写；`log` 能匹配 `catalog`）。一个词如何被找到，取决于它的字符数：

- **三个或更多字符**：通过 trigram 索引查找，对中日韩（CJK）文字和拉丁文字都一样。
- **一到两个 CJK 字母**（汉字、假名或谚文），例如 `部署` 或 `库`：通过 CJK 索引查找，它保存每一对相邻的 CJK 字母，以及每一串 CJK 字母的最后一个字母。
- **一到两个其他字符**，例如 `AI`、`C#` 或 `5号`：没有索引能找到它们，所以 Origin 从新到旧核对候选事件的文本。候选事件是检索所覆盖的事件（它的事件类型，以及所请求的项目、来源和时间范围）中匹配查询其他词的事件。最多核对最新的 25,000 个候选事件（`SCAN_LIMIT`），所以这样的词可能漏掉较早的事件；限定时间范围、指定项目或加上一个更长的词，就能找到它们。

**索引。** 事件检索由三个 FTS5 索引支撑，它们都以 `seq` 为键。其中一个索引驱动查询，从新到旧，其余的词再过滤它的匹配：

| 索引 | 内容 | 用途 |
|---|---|---|
| `message_fts` | `message` 事件，记录每个 trigram 的位置（`detail=full`） | 含有三个或更多字符的词的消息检索：每个词都作为短语精确匹配，并用 BM25 打分 |
| `event_fts` | 所有事件，只记录哪些事件含有每个 trigram（`detail=none`），体积只是完整索引的一小部分 | 包含工具事件的检索：事件必须含有每个词的每个 trigram，然后再用词本身核对 |
| `event_cjk` | 每个含 CJK 文字的事件的 CJK 二元组（`detail=none`，无内容表） | 一到两个字母的 CJK 词，以及其他词都同样短的查询 |

**排序。** 结果默认按 BM25 相关度排序，最相关的在前。排序只考虑最新的 2,000 个匹配（`RANK_WINDOW`），匹配更少时则考虑全部：查询匹配的事件更多时，较早的匹配既不参与排序也不会返回，所以非常常见的词会偏向近期的事件，而限定时间范围会移动这个窗口。对于消息，BM25 把词作为短语打分；包含工具事件时，它对词的 trigram 打分。没有三个或更多字符的词的查询，以及 `--recent`，改为按时间排序。按时间排序指按时间戳从新到旧，时间戳相同的事件中后到达的在前；相关度相同的结果也按同样的方式排列。无论事件以什么顺序到达，按时间排序的结果以及最新 2,000 个匹配的窗口都是精确的：查询按到达的块读取索引（见[存储](#storage)），一旦没有未读的块可能含有比所需匹配更新的匹配，就立即停止。匹配很少的查询（不超过 2,000 个，或所需数量的五倍）则直接读取全部匹配。

**摘要**显示第一个匹配周围最多 200 个字符的文本，每个匹配都用方括号标出。

**条目**按同样的词检索：三个或更多字符的词通过 `entry_fts` 查找并按 BM25 排序，更短的词通过核对文本查找（条目很少）。没有三个或更多字符的词时，条目从新到旧排列。

时间线按时间列出会话，除非请求列出子会话，否则只列顶层会话（见[父会话](#parent-sessions)）；或按顺序、一页一页地列出单个会话的事件：它的某一轮，或某个事件之后的事件（工具事件默认隐藏，除非请求显示）。变更流列出某个游标之后到达库中的内容（见[变更流](#change-feed)）。

**主人的提示。** 有效作者是主人（见[作者](#authors)）、且读起来像提示的可见用户 `message` 事件，就是**主人的提示**（`core` 中的 `isOwnerPrompt`，查询中用的是同一条规则）：它是判断主人说了什么的唯一规则，用来给会话命名、开始一轮（见[管理界面](#admin-ui)）、让会话成为主人的对话，并给召回提供背景词（见[召回](#recall)）。一条消息读起来像提示，是指跳过它开头的 XML 风格元素（`<tag …>…</tag>`，Agent 作为上下文或命令回显添加，例如 Claude Code 的 `<command-name>`、`<local-command-stdout>` 和 `<local-command-caveat>`，或 Codex 的 `<environment_context>`）之后，剩下的内容不只是一个方括号提示（例如 `[Request interrupted by user]`）。meta 事件（注入的上下文、Agent 不放进对话记录的提示）不是消息，所以不是提示；是消息但不属于主人的内容，例如压缩的摘要、任务的通知、子 Agent 的提示或别人的话，也不是主人的提示。至少有一条可见的主人提示的会话，是**主人的对话**：子 Agent 的会话、无界面运行、有父会话的会话（见[父会话](#parent-sessions)），以及只有别人的话的会话都不是。

**会话的名称。** 会话的 `title` 是它的 Agent 给它的标题，或用户通过 Agent 给它的标题（见各来源的映射）；Codex 不给任何标题，其他 Agent 也并不总是给。没有标题的会话改为带有一个 `prompt`：它的主人的第一条提示，作为一个临时的名称，界面可以把它作为临时名称显示，其中的空白会被合并，并截断到 80 个字符；没有主人提示的会话（例如子 Agent 的会话）没有这个名称。它在每次读取会话时（`listSessions`、`getSession`）通过 `event_user_message`（一个只包含每个会话的用户消息的索引）从事件中计算得出，因此会随遗忘而变化（不变量 2）；不保存任何东西。MCP 的 `timeline`、`origin timeline`（放在引号中）以及管理服务的会话列表都在标题旁边带上它；MCP 的结果用标题或这条提示来指明事件所在的会话（`session_title`）。这些列表显示的名称可以与已存的标题不同：当已存标题含有 `actor#N@M` 时，工作流的子会话以其运行的名称显示（见[父会话](#parent-sessions)）。已存的标题不变。

### 变更流 {#change-feed}

回到库中的 Agent，例如每隔几分钟看一次的常驻 Agent，需要的是自它上次看过以来改变了什么，而不是再看一遍全部内容。变更流（`core` 中的 `changesSince`，MCP 工具 `changes`）列出某个游标之后到达库中的内容，分成两路，每一路都按到达的次序排列：可见的事件，按 `seq`；条目和遗忘记录，按它们在 `change_log` 中的序号。不调用任何模型，也不做任何排序。

- **一页**最多含 `limit` 个事件（默认 50，最多 200；除非请求包含工具事件，否则只有消息，而且从不包含记忆事件，它们的条目本身就会出现在变更流中），条目和遗忘记录合计最多 `limit` 个，这些事件所属的会话（每个都带有它的线索，以及它是否在这一范围内开始：它的可见事件没有一个早于这一范围），以及 `next`，即两路各自最后一项之后的游标。这些会话是顶层会话（见[父会话](#parent-sessions)），除非这一页被筛选到某一个会话或某一条线索，那时子会话会与其余会话一起列出。子会话的事件仍然可以出现在这一页中。`more` 表示某一路的内容多于这一页：用 `next` 一直读下去，直到 `more` 为假，每一项都恰好读到一次。
- **没有游标时**，变更流从 24 小时前开始：时间落在最近 24 小时内的事件，以及这段时间里记录下的条目和遗忘记录，如果更多，就取每一路最新的 `limit` 个，游标则是当前的位置。更早的内容请用 `search` 和 `timeline`。
- **条目**在读取这一页时是当前条目（没有被取代、遗忘或结束）才会列出，并带有它所取代的版本：一次修正以它的新版本出现。被恢复带回的条目会被库再次记录，所以会再次出现。
- **遗忘记录**列出它的 id、它的目标的 id 和它的创建时间，从不列出目标的文本或原因：被遗忘的内容离开变更流，Agent 得知它的 id，从而不再引用它。恢复也会出现，它的目标是那次遗忘的 id；中枢因为某次遗忘在那里覆盖的内容发生变化而再次记录它时，它也会再次出现。
- **提议**：范围内产生的提议也会列出，按读取这一页时的状态，为待审或已接受（见[提议](#proposals)）：即事件落在事件流范围内的那些，无论事件是什么类型，最多 `limit` 条。含有更多提议的一页止于它列出的最后一条提议，其后的事件随下一页给出。
- **过滤条件。** 一个项目（它的事件和它的条目），一个会话或一条线索（它们的事件，以及从它们写下、引用这些事件的条目）。无论过滤条件如何，遗忘记录都会列出。
- **游标**是一个小 JSON 对象的 base64url 编码，记录它在两路中各自到达的序号。Agent 把它当作不透明的值，原样传回拿到的 `next`；格式错误的游标会报错。序号是库自己的，所以游标只对给出它的库有效；超出库末尾的游标（例如库从备份中恢复之后）不会得到任何内容，`next` 则是库的末尾。
- **可见性。** 一页中从不含被隐藏的内容（不变量 2）：被遗忘的事件和条目被略去，但它们的序号照常越过；遗忘之后重新读取同一范围，也不再含有它们。

### 每日摘要 {#daily-digest}

要回顾一天，无论是 Agent，还是一天结束时的主人，需要的是这一天里发生的事情的全貌，而不是一个会话一个会话地看。摘要（`core` 中的 `digest`，MCP 工具 `digest`，`origin digest`）只凭库本身读出一个日历日。不调用任何模型，同一个库给出同一份摘要。

- **这一天**是某个时区中的一个日历日：默认是今天，按作答的进程所在的时区（它解析出的 IANA 名称，例如 `Asia/Shanghai`），或者按请求指定的时区。它从这一天的第一个时刻持续到下一天的第一个时刻，所以当时区在这一天里改变偏移时，它有 23 或 25 个小时。摘要写明这一天、这个时区和这两个时刻（`from`，含；`until`，不含），其中的每个时间都按这个时区给出。连接到中枢的设备和中继，向中枢请求的是它们自己的这一天、按它们自己的时区。
- **会话。** 这一天里有可见事件（记忆事件除外）的顶层会话（见[父会话](#parent-sessions)），最近有活动的在前，最多 `limit` 个（默认 50，最多 200），并给出还有多少个。这一天里活跃的子会话计入它的父会话链最终到达的那个顶层会话，即使那个会话在这一天里没有事件：它的事件、它的首末时间、它的工具调用和它编辑过的文件，都与那个会话的合在一起计数，摘要的 `children_included_in` 列出了这些字段；那个会话还会给出有多少个子会话活跃过，以及它们的工作流名称。每个会话带有它的 id，形如 `<source>:<session id>`，可以用 `get` 打开；它的解析后项目（见[项目](#projects)）、它的线索、它的标题或第一条提示（见[会话名称](#search-and-timeline)）、主人这一天的提示（有多少条，以及前五条，每条截到 200 个字符）、按工具名称统计的工具调用（调用最多的 20 个，以及所有工具的调用总数），以及它的编辑调用改动过的文件（编辑最多的 20 个，以及一共有多少个）。只有主人的提示才计入，依据的是同一条规则（见[主人的提示](#search-and-timeline)）：子会话的、无头运行的、其他人的话都不算。哪些调用算作编辑文件、它们的路径怎么读取，按 Agent 分别在[编辑过的文件](sources.md#files-edited)中规定：尽力而为，取自 Agent 的编辑工具的输入，从不解析 shell 命令。
- **合计**统计过滤条件保留下来的所有会话，而不只是列出的那些：会话数、事件数、主人的提示数、有名称的项目数、Agent 数，以及并入的子会话数；还有按解析后项目（没有项目的会话归在 `null` 下）和按 Agent 分别给出的同样的计数，事件最多的在前。
- **条目、提议和遗忘。** 这一天里写下且未被遗忘的条目版本，最新的在前，包括修正：修正会写明它取代的版本（`supersedes`），导入的版本会注明这一点。这一天里产生、仍会显示的提议，待审或已接受（见[提议](#proposals)）。这一天里做出的遗忘和恢复，只给出 id：它的目标的 id、目标是什么（条目、事件、提议的事件——拒绝提议就是这样做的——或者恢复所撤销的那次遗忘），以及时间，从不给出原因或被隐藏的内容。每一类最多 `limit` 个，并给出还有多少个。
- **过滤条件。** 项目保留解析后项目为它的会话、按简报所用的规则属于这个项目的条目，以及它的提议；来源保留这个 Agent 的会话、引用了它的可见事件的条目，以及在它的会话中产生的提议。过滤条件作用于顶层会话：它的子会话随它一起保留。无论过滤条件如何，遗忘都会列出。
- **可见性。** 摘要中从不含被遗忘的内容（不变量 2）：被遗忘的事件离开计数、提示、工具和文件；这一天的事件全部被隐藏的会话不会列出；被遗忘的条目和被拒绝的提议也不会。
- **在连接到中枢的设备上，** 摘要是中枢的，中枢持有每台设备的会话，再去掉设备已遗忘的内容：设备持有的会话按设备自己的摘要显示，它的事件在设备上全部被隐藏时则略去；设备已遗忘的提示、条目和提议也会略去。合计是中枢的。设备还没有发送的会话，要等它同步之后才会出现。中枢没有及时应答时，摘要是设备自己的，并附上通常的说明（见[MCP server](#mcp-server)）。

## 线索 {#threads}

一个会话是一个进程的记录，但一件工作常常要用好几个会话：用户第二天接着做，压缩上下文之后接着做，或者换一个 Agent 接着做。**线索**（thread）是同一项目中属于同一件工作的一组会话。Origin 按两条确定性的规则从归档中推导线索，每个库都根据相同的数据这样推导，所以对于双方都持有的会话，中枢和它的设备得出一致的结果。不调用任何模型。

没有哪个 Agent 的记录能可靠地说明一个会话接续了另一个会话：Claude Code 只在 2.1 之前写过这种谱系（带 `leafUuid` 的 `summary` 行），它的 `last-prompt` 行指向的是同一个会话；其他 Agent 都不记录。所以一个会话只能经下面两条规则之一加入线索，两条都不适用的会话不属于任何线索：

- **R1，跟随。** 当用户接着做之前某个会话里的工作时，Agent 用 MCP 工具 `follow` 声明它的会话接续了另一个会话或一条线索（见 [MCP server](#mcp-server)）。这个工具本身不写下任何持久的内容：它的结果被 Agent 的记录作为一个工具结果保存下来，其中含有一个链接 id（`"link": "lnk_…"`，随机生成，与 `ent_` id 一样）和它所接续的会话（`"follows": "<source>:<session id>"`）。采集时从每个这样的事件派生一行 `session_follow`，就像根据工具结果中的召回 id 找到召回所属的会话一样（见[召回](#recall)），所以每个解析这一行的库都派生出同样的链接，不需要复制任何东西。同样的文本如果被引用在另一个结果里（例如找到它的一次检索），其中的引号已被转义，不会产生链接；一个会话跟随它自己也不会产生链接。链接在它的事件可见时才算数：遗忘这个事件就会去掉这条链接（不变量 2）。
- **R2，分支。** 同一项目（按名称，与归档命名项目的方式相同）中位于同一个工作分支上的主人的对话（见[检索与时间线](#search-and-timeline)），如果从一个会话结束到下一个会话开始相隔不超过 30 天，就连在一起。分支上子 Agent 的会话或无界面运行（例如一次整理运行）本身并不是主人工作的一部分，不会以这种方式加入线索；说明某个会话是什么的行在它的事件之后到达时，会重新计算这个会话的线索。会话的分支（`session.git_branch`）是它的多数可见事件所记录的分支，并列时取最晚的那个；它与会话的计数保存在一起，随着事件到达或被遗忘而更新。默认分支 `main`、`master`、`trunk`、`develop` 和 `dev`，以及分离的 `HEAD`，承载各种各样的工作，所以位于这些分支上的会话只通过跟随链接相连。在 Origin 读取的 Agent 中，只有 Claude Code 记录分支；人自己的来源可以用 `branch` 给出分支。

线索是这两条规则在所有含可见事件的会话上的传递闭包；只有一个会话的组不是线索。子会话（见[父会话](#parent-sessions)，或 `session_kind` 为 `child`）在它的父会话已经属于某条线索时加入那条线索，这个子会话自己的子会话也一样，只要这些会话有可见事件。子会话永远不是根会话，也不会自己创建线索：只有它的子会话相伴的父会话仍然没有线索，两个只彼此相连的子会话也不是线索。根会话是那些不是子会话的成员中最早开始的那个。

- **Id。** 线索的 id 是 `thr_` 加上它的**根会话**（不是子会话的成员中最早开始的那个，开始时间相同时依次按来源和会话 id）的 `<source>:<session id>` 的 SHA-256 的前 12 个十六进制字符；它的标题是根会话的标题，或根会话的第一条提示，它的项目也是根会话的项目。只有根会话改变时 id 才会改变：一个更早的会话加入时，比如较旧的记录后来才到达（设备推送积压的数据，中枢收到另一台设备的会话）；根会话因为它的事件或链接被遗忘而离开时；或者一条线索分裂时。比父会话更早开始的子会话不会成为根会话。持有相同成员的每个库都给这条线索同样的 id。
- **保持最新，可以重建。** `session_thread` 列出每条线索的成员。当采集、遗忘或恢复改变了一个会话（它的事件、分支或链接）时，它原来所在和现在所在的线索会从这个会话出发按规则重新计算：一条链接或一段分支只随它的会话之一而改变，所以别的线索不可能改变。`rebuildThreads()` 从事件和会话重新推导链接和线索，结果相同。
- **在中枢和它的设备上。** 设备持有自己的会话和它们的链接；中枢持有所有设备的。设备上的一条线索可以是中枢上某条线索的一部分，当中枢持有更早的会话时，id 也会不同。指向某个库没有的会话的链接会被保留，那个会话到达后就会连上。
- **可见性。** 只有含可见事件的会话参与，也只有事件可见的链接才算数，所以被遗忘的会话或链接会立即离开它的线索、每个列表和每个计数，恢复又会把它带回来（不变量 2）。
- **线索不是什么。** 它不是项目、分支或任务：它不做总结、排序或计划。它列出自己的会话，Agent 用 `get` 打开它们。它的任何部分都不是手写的，所以没有什么可编辑：当一个会话的链接事件被遗忘，或它的全部事件都被遗忘时，这个会话就离开线索。子会话随它的父会话一起离开。

## 父会话 {#parent-sessions}

子 Agent 或工作流步骤本身就是一个会话。当镜像中的一行已经写明这个会话的父会话时，Origin 在 `session_parent` 中记录一行：子会话、父会话（它的来源和 id）、子会话是怎样开始的（`via`，`subagent` 或 `workflow`）、行中写明时的工作流运行分组和名称（`run_group`、`run_name`），以及决定这一事实的字段（`signal`）。`session.title` 保持 Agent 存下的标题。已存标题含有 `actor#<数字>@<数字>`、且这一行有运行名称的工作流子会话，显示为 `{运行名称} · actor#N@M`。这个名称在读取会话时计算；已存的标题不变。

Agent 的行里已经有的事实，在设备和中枢上相同：

- **ZCode。** 生成的一行带有 `session.parent_id`。`task_type` 为 `workflow_child` 时 `via` 是 `workflow`，为 `subagent_child` 时是 `subagent`；信号是 `parent_id`，父会话的来源是 `zcode`。当这一行还带有 `workflow`（`id`、`name`、`resumed_from`，以及 `group`，即该运行的 `resumed_from` 链的根）时，有 `group` 就用 `group` 作为分组，`resumed_from` 为 null 时用 `id`，名称是 `name`，信号则是 `dwf_run`。适配器在写出这一行时，以只读方式从 `dwf_run` 和 `dwf_actor` 复制 `workflow`，并沿着 `resumed_from` 走到 `resumed_from` 为 null 的那次运行，因此只有这一行的库不需要数据库。它不读取 `workflow_run`。`resumed_from` 已设置且没有 `group` 的行不记录分组。
- **Grok Build。** `subagent_spawned` 更新写明 `child_session_id` 和 `parent_session_id`：`via` 为 `subagent`，信号为 `subagent_spawned`。标题行的 `session_kind` 说明某个会话是子 Agent，并不指明父会话。
- **Codex。** `session_meta` 的 `source.subagent.thread_spawn.parent_thread_id` 在它是非空字符串时：`via` 为 `subagent`，信号为 `parent_thread_id`，父会话的来源是 `codex`。`source.subagent` 只是一个字符串时，仍然把会话标为子会话，但不指明父会话。
- **Claude Code 和 Cursor** 不记录会话的父会话。Claude Code 的子 Agent 记录保持原样，不会从中添加父会话行。Cursor 的记录文本和编辑器对话也不指明父会话。

Agent 自己的记录没有写明的父会话，或稍后补上的运行分组，是该来源 `places.jsonl` 中的一行，一份设备可以推送的生成镜像。父会话行是一个 JSON 对象，`{"v":1,"type":"parent","session","parent","via","signal"}`，已知时带有 `group` 和 `name`。`parsePlaceLine` 不产生消息事件。`root` 行记下 `project_root`，`place` 行记下 `session_place`，`parent` 行记下 `session_parent`。采集根据父会话行更新 `session_parent`。Agent 自己的行已经写明的父会话，在后来的一行写了另一个父会话时仍然保留；缺失的分组和名称仍会补上，已经存下的分组或名称从不清除或替换。早先的行不被改写。不是其类型所要求的 JSON 对象的一行会被跳过，并记一条警告。同一文件里的其他行，以及其他来源，仍照常读取，打开库也不会失败。追加之前，不以换行符结尾的镜像会先补一个换行符，这样写到一半的行不会和下一行连在一起。中枢解析的是同样的字节。

版本 10 建立这张表，并像版本 8 重新解析作者那样，重新解析可能写明父会话的镜像行。这张表建好之后，它还会读取在项目表出现之前就已经镜像的 `places.jsonl` 行。它不打开 ZCode 的数据库，也不打开 Grok Build 的会话目录。其余的事由 `origin sessions parents` 在你运行它时完成，并且只读：它读取 `dwf_run` 和 `dwf_actor`，不读取 `workflow_run`，并读取 Grok 的 `summary.json` 字段 `parent_session_id`；当镜像还没有记录这个父会话，或工作流子会话的分组或名称仍然缺失时，它追加一行父会话。`--dry-run` 打印它会追加多少行，什么也不写。不存在的数据库或会话目录会被跳过，命令以 0 退出。在不保存会话的中继上，它说明这一点并退出，不打开这些目录。

会话列表除非被要求，否则不列出子会话。顶层会话没有 `session_parent` 行，也不是一个未指明父会话的、`session_kind` 为 `child` 的会话。MCP 的 `timeline`（`include_children`）、`origin timeline`（`--children`）、变更流的会话列表，以及管理界面的会话页，都使用这个默认。每个顶层行带有 `children`（有多少）和 `workflows`（不同的运行名称）。管理界面把每个有事件的子会话嵌在它的父会话之下；已存的标题留在这一行上，看见的名称是上面所说的那个。`brief` 把子会话排除在主人的对话之外，并在父会话的那一行，以及根会话有子会话时线索的那一行，加上子会话数量和这些名称。对父会话调用 `get` 会按运行分组列出它的子会话，每个一行（显示的名称、`via` 和 id）；对子会话调用 `get` 会给出它的父会话和父会话的标题。落在有父会话的会话上的检索命中包含 `parent`（`<source>:<session id>`）和 `parent_title`。

## MCP server {#mcp-server}

`origin mcp` 通过 stdio 提供以下工具。结果是 JSON 文本，时间戳为本地时间的 ISO 8601 格式，精确到毫秒。

| 工具 | 用途 |
|---|---|
| `brief` | 用户的记忆中与 Agent 工作之处有关的内容，即召回交出的内容，并记录为一次召回（见[召回](#recall)）。父会话的那一行会加上它有多少子会话，以及这些子会话的工作流名称 |
| `search` | 对条目和事件做全文检索；不带查询词时列出最近的条目。过滤条件：范围、类型、时间段、来源、项目、工具事件。每个事件都指明它所在的会话；落在子会话上的命中也会指明它的父会话（见[父会话](#parent-sessions)） |
| `timeline` | 某个时间段内的顶层会话（默认 7 天；`include_children` 也列出子会话），每个会话带有它的标题，没有标题时带有它的第一条提示（见[会话的名称](#search-and-timeline)）、它有多少子会话及其工作流名称，以及它的线索；或单个会话的事件，一次一页：某一轮（`turn`），或某个事件之后（`after`），并说明后面还有多少（`more`） |
| `changes` | 某个游标之后到达库中的内容，从旧到新且有界：这些事件所属的顶层会话（当筛选指明那个会话或一条线索时也包括子会话）、事件、条目和遗忘（只给 id），以及接着读用的游标（见[变更流](#change-feed)）。过滤条件：项目、线索、会话、工具事件 |
| `digest` | 一个日历日，只凭库本身（见[每日摘要](#daily-digest)）：合计、按项目和按 Agent 的计数；这一天里活跃的顶层会话，并入活跃的子会话，每个带有它的 id、主人的提示、按工具统计的调用和编辑过的文件；写下的条目、产生的提议和做出的遗忘（只给 id）。参数：日期（默认今天）、时区（默认 server 自己的）、项目、来源、数量上限 |
| `get` | Origin 交出的任意 id，以一张写明近旁内容的卡片返回（见[沿引用阅读](#reading-along-references)）：条目及其来源、历史和相关条目；事件及其正文（分页）、所在会话、所在轮次、前后的事件和引用它的条目；会话及其各轮、它的线索、从中写下的条目、它拿到的召回、前后的会话、它是子会话时的父会话，以及它是父会话时按运行分组的子会话；线索及其会话和从中写下的内容；召回及其交出的内容；提议及其来源、提出它的会话和它成为的条目 |
| `sources` | 条目或事件对应的原始记录行：文件、镜像、行号、原始文本 |
| `follow` | 声明调用者的会话接续了 Agent 所在项目中的某个会话或某条线索，使它们成为一条线索（见[线索](#threads)）：它不写下任何内容，只返回链接，由采集从 Agent 的记录中读出 |
| `remember` | 写入一个条目，包括类型、正文、置信度和来源 |
| `propose` | 提议一个条目交给用户审阅，带有 `remember` 的各字段和一条说明：它像 `remember` 检查条目那样被检查，不写入任何内容，返回这条提议，采集从 Agent 的记录中读出它（见[提议](#proposals)）。只有用户可以接受或拒绝它，通过 CLI 或管理界面 |
| `correct` | 用纠正后的版本取代一个条目 |
| `forget` | 按上述规则隐藏一个条目或事件，并附上用户给出的原因；仅在用户明确要求时使用。没有用于恢复的工具：只有主人能恢复，方式是 CLI 或管理界面 |

- **新鲜度。** server 在启动时采集所有来源，在 `brief`、`search`、`timeline`、`changes`、`digest` 和 `follow` 之前也会采集（最多每 10 秒一次；在连接了中枢的设备上，`get` 和 `sources` 之前也会），在 `remember`、`propose` 和 `correct` 之前则总会采集，因此 Agent 能引用它当前所在对话中的记录行。
- **Agent 运行期间。** Claude Code 和 Codex 的 hook 会在每一轮结束时把会话新增的行交给 Origin（见[实时采集](#live-ingestion)）。作为后备，为其他 Agent 以及 hook 漏掉的内容，server 还会每 60 秒查看一次有没有新的记录行（`ORIGIN_WATCH_INTERVAL_MS`；设为 0 则关闭），这样 Agent 最后一次调用工具之后写下的内容也能进入库和中枢，而不必等到下一个 Agent 启动。每次查看会把各记录文件的大小和修改时间与上次采集时比较，不读取文件内容，只有发生变化时才采集。查看在后台进行，与其他刷新使用同一套闸门，所以一次只查看一次，也绝不会与另一次同步重叠；工具调用不会等待它，除非本来就需要刷新；耗时较长的采集也会在各个事务之间让工具调用先执行。
- **Agent 离开时。** 标准输入结束，或者 server 收到 SIGTERM、SIGINT 或 SIGHUP 时，它会再采集一次，已接入中枢时还会与中枢同步，最多等待 5 秒，然后退出。Agent 如果直接杀掉 server，就会跳过这一步；下一次启动时会补上。
- **在已接入中枢的设备上。** server 仍然根据设备自己的库作答，读取类工具（`search`、`timeline`、`changes`、`digest`、`get`、`sources`）会同时询问中枢的 `/mcp`。两边的结果会合并、按 id 去重，并标上 `origin: "local"`（本设备有这一项）或 `"hub"`。无论中枢返回什么，设备已经遗忘的内容都不会显示；同一个条目的多个版本中，只列出按[条目](#entries)中的规则确定的当前版本；`get` 会合并两个库中该条目的历史。对于设备没有的 id，`get` 和 `sources` 由中枢作答；对设备没有的会话或线索调用 `follow`，也由中枢按它自己的库、针对设备的工作树来检查。`changes` 的游标同时含有设备的游标和中枢的游标（`{ l, h }`）：两边的变更流按 id 合并并加上标签，去掉设备已遗忘的内容，连同在本设备上事件已全部消失的会话；任何一边还有更多内容时，`more` 为真；中枢没有回应时，游标中属于中枢的部分保持不动。`digest` 向中枢请求设备的这一天、按设备的时区，结果是中枢的，再去掉设备已遗忘的内容（见[每日摘要](#daily-digest)）。如果中枢在 2 秒内（`ORIGIN_HUB_TIMEOUT_MS`）没有回应，或者无法连接，工具就只根据设备作答，并附加第二段文本，说明这次没有询问中枢。agent 一完成初始化，server 就建立到中枢的连接，这样第一次读取不必把这段时间花在 TLS 握手和 MCP 初始化上。
- **已接入中枢的设备上的写入**先落到设备的库中，再同步上去。`propose` 不写入任何内容，它像 `remember` 一样针对设备的库检查。server 在读取类工具之前与中枢同步（最多每 10 秒一次），每次写入后、每次后台查看发现新的记录行后、以及 Agent 离开时也会同步，而且为了等待中枢而推迟回答的时间不会超过超时时限。失败的同步会在下一次后台查看时重试。对于设备没有的条目或事件，`correct` 和 `forget` 会在中枢上执行；连不上中枢时，它们会失败并给出清楚的错误说明。
- **在中继上。** 每个工具都交给中枢的 `/mcp`，中枢的回答原样返回，不带 `origin` 标签；`brief` 和 `follow` 以中继的工作树作为 Agent 的目录，因为中枢看不到中继的磁盘；`digest` 则带上中继的时区。在此之前，server 先把 Agent 新增的记录行发送给中枢：读取类工具之前最多每 10 秒一次，最多等待中枢超时时限；每次写入之前（包括 `propose`）都会发送，最多等待 15 秒，这样条目就能引用刚刚说过的内容。由于它自己没有回答，它最多等待中枢的回答 15 秒；连不上中枢时，工具会失败，并说明中继离线时无法作答。记录文件有变化时，它每分钟也会发送一次新的行，Agent 离开时再发送一次（见[中继](#relays)）。
- **只读连接。** 预设权限为 `readonly` 的 Agent 的连接（见[访问](#access)）不提供 `remember`、`propose`、`correct` 和 `forget`，它的说明会告诉 Agent 它可以读取记忆，但不能修改。
- **OpenClaw 的 Agent。** OpenClaw 插件（见[你自己的来源](#your-own-sources)）把其中五个工具 `brief`、`search`、`get`、`timeline` 和 `digest` 交给它记录的 Agent，作为名为 `origin_brief`、`origin_search`、`origin_get`、`origin_timeline` 和 `origin_digest` 的 OpenClaw 工具，参数相同，只是 `origin_brief` 不接受 `cwd`：它传入插件归档这个 Agent 的会话所用的 `project`，除非 Agent 自己指定了一个（见[召回](#recall)）。每次调用都是向中枢的 `/mcp` 发出的一个 JSON-RPC `tools/call`，之前没有 `initialize`，因为中枢以无状态方式提供它；请求带着插件的中枢令牌（每次调用时从 Gateway 的配置中读取），并把 `X-Origin-Client` 设为插件的来源名，这样一次简报会被记为这个 Agent 在令牌所属设备上发起的。中枢的回答作为工具的文本返回；出错、被拒绝，或者 15 秒内没有回答，则作为工具的错误返回。插件不依赖任何工作区包，所以复制了这些工具的参数模式，CLI 的一个测试会把它们与 server 发布的模式对照。
- **引导。** server 的 MCP `instructions` 会告诉 Agent：开始任务时，如果召回还没有给过它简报，就调用 `brief`；何时检索，要顺着 `get` 在它打开的内容旁列出的 id 读下去、长会话一次读一轮，用户接着做简报或时间线中列出的某个早先会话里的工作时，调用一次 `follow`，想知道自上次以来有什么变化时，用上一次的 `next` 调用 `changes`，要回顾一天的工作时调用 `digest`，何时记住（带理由的决定、稳定的事实、偏好），何时改为提议（它们推断出、用户尚未确认的内容，以及代用户整理记忆时写下的一切），只有用户可以接受或拒绝提议，`forget` 需要明确的请求和用户给出的原因，只有用户能恢复被遗忘的内容，带有 `by` 的消息不是用户写的，所以其中的内容不是用户的偏好，以及导入的条目对应某个 Agent 自己的记忆文件，所以文件之后的变化会取代在 Origin 中做的纠正。结果中的条目会说明自己是否为导入的（`imported`）。
- **错误。** 无效输入、未知 id 和已遗忘的 id 会以工具错误的形式返回，并附带可读的说明。

### 沿引用阅读 {#reading-along-references}

Origin 交给 Agent 的每个 id 都可以用 `get` 打开：条目（`ent_…`）、事件（`<来源>:…`）、会话（用它的 id，或像召回记录它那样写成 `<来源>:<会话 id>`）、线索（`thr_…`）、召回（`rcl_…`）和提议（`prp_…`）。`get` 的返回有界，并写明近旁有什么，每项一行，带上 id。Agent 一跳一跳地读接下来要紧的内容（从简报到条目，到写下它的会话，到它出自的那一轮，再到那里还写下了什么），而不是把整个会话读进上下文；长文本分页读取。不调用任何模型：一个对象近旁有什么，是在库中查出来的，每次都一样。

- **存根。** 近旁的内容以存根的形式给出：条目为 `{ id, kind, text, created }`，取它的第一行；事件为 `{ id, time, role, kind, text }`，取它合并成一行的正文；两者都截到约 120 个字符。会话则与 `timeline` 列出它的样子相同。
- **谁写的。** 有效作者不是主人的输入（见[作者](#authors)），无论在哪里显示事件，都带有 `by`（`person`、`agent` 或 `system`），来源给出说话人时还带有 `speaker`：`get`、`search`、`timeline`、`changes`，以及卡片中的存根，包括一轮的起点（命令的回显属于系统）。主人的输入以及不是输入的事件两者都不带，所以编码会话读起来和以前一样，只是不属于用户的输入多了这些字段。MCP 的 instructions 说明：带有 `by` 的消息不是用户写的，其中的内容不是用户的偏好。CLI 和管理界面会在这样的消息旁边显示是谁写的。
- **条目**带有它的来源（每个来源都指明所在的会话）、它的历史，以及最多 10 个相关条目：引用了它所引用的某个事件、或它所引用会话中另一个事件的其他当前条目，从新到旧。记忆文件的版本不属于任何会话（见[原生记忆](#native-memories)），所以导入的条目只与引用了同一个版本的条目相关，而不是与它所在目录的每条记忆都相关。
- **事件**带有它所在会话的名称，以及从某个偏移量开始的正文，最多 20,000 个 UTF-16 码元，并给出正文的全长和下一页的起点。它的第一页还带有：它所在的轮次和这一轮的提示；它的 Agent 记录的、它所接续的事件（如果 Agent 记录了的话，即 Claude Code 的 `parentUuid`；一行被拆成多个事件时，取其中第一个）；同一会话中它前后各两个可见的事件，除非它本身是工具调用或工具结果，否则只取消息；以及最多 10 个引用它的当前条目。
- **会话**以卡片的形式给出：它的名称、时间、可见事件数和轮数；它前 20 轮的起点（轮次见[管理界面](#admin-ui)），并说明后面还有多少轮；它所在的线索及其会话数（如果在某条线索中，见[线索](#threads)）；最多 10 个从中写下的当前条目，即引用了它的事件的条目，从新到旧；最多 10 次它拿到的召回，从新到旧，并说明每次召回交出的内容中有多少仍然可见；同一项目中、按开始时间紧挨在它前后的会话，不限 Agent；它是子会话时的父会话及该父会话的标题；以及它是父会话时按工作流运行分组的子会话，每个一行（见[父会话](#parent-sessions)）。`timeline` 一次读它的一轮或一页，并说明后面还有多少事件。两个来源的会话共用同一个会话 id 时，需要指明来源。
- **线索**以卡片的形式给出：它的项目、名称（取自根会话）、开始和结束的时间、它的前 20 个会话（从旧到新）并说明后面还有多少，它的会话所属的 Agent 和所在的工作分支，最多 10 个从其中任一会话写下的当前条目（从新到旧），以及它的最后一条提示，即有提示的会话中最近那一个的最新提示。
- **召回**带有它为谁、在哪里而做、它的各项、会话后来是否用到了每一项，以及按库现在的样子重建的、Agent 当时拿到的文本（`rebuildRecall`），这样 Agent 就能看到它早先拿到了什么，例如在上下文压缩之后。
- **提议**以卡片的形式给出：它提议的内容（各字段，与 `propose` 返回的一样），它的状态（待审或已接受），它在何时、在哪个会话中提出，读出它的事件，它引用的事件（以存根给出，带有各自的引文），其中本库尚未持有的数目，以及被接受之后它成为的条目。它的 id 放在 `id` 下，从不放在 `proposal` 下，这样卡片被读进 Agent 的记录时不会再次提出这条提议。被拒绝的提议，或引用了被遗忘事件的提议，都无法打开（见[提议](#proposals)）。
- **可见性。** 当前条目就是列表中会显示的条目：没有被取代、没有被遗忘、也没有到期。隐藏的内容既不会作为近旁的内容出现，也不会被计数（不变量 2）：一个事件或条目被遗忘后，会立即从每个列表、每个计数、它开启的轮次和每次召回的各项中消失。每张卡片和每一页都由核心构建（`describeSession`、`describeThread`、`eventContext`、`relatedEntries`、`readSession`），MCP 和 CLI 用的都是它们（不变量 5）。
- **在已接入中枢的设备上**，事件、会话、线索或召回是其中一个库的回答，带的是那个库的近旁内容，从不混合两边：设备有这个 id 时用设备的，否则用中枢的，并去掉设备已遗忘的内容（中枢卡片中的计数，在遗忘传到中枢之前仍是中枢的）。条目的相关条目来自给出这个回答的库。会话的分页按事件 id 合并，`more` 取自有事件的那一边，设备有事件时取设备的。

## 项目 {#projects}

一个会话的项目是一个名字，这个项目的每一次检出共用它。列表、过滤和简报用的都是它。存在事件上的标签保持那一行所写的内容。

名字按下面第一条适用的规则决定：

1. **写明的名字。** 这一行自己给出了 `project`，包括事件行的 `project` 字段恰好等于 `cwd` 最后一段的情况。Origin 保留这个名字。已经存下的、不是 `cwd` 最后一段、而且尚无信号的名字也一样：那是 Agent 选定的。一旦设了 `manual`，这个名字也会保留。
2. **Git。** 目录在一个工作树里。链接的工作树（一个 `.git` 文件、它的 `gitdir:`，以及那个 git 目录的 `commondir`）属于主检出的项目。名字是主工作树的最后一段，用磁盘上那个目录的大小写。子模块是它自己的项目。`.git` 在，但工作树读不出来时（裸仓库、符号链接的 `.git`，或单独的 git 目录），根就是放着 `.git` 的那个目录，名字是这个目录的最后一段。
3. **学到的根。** 这个库已经把这个目录、或它的某一级父目录，记成某个项目的工作树（`project_root`）。只有目录已经不在，或者这个库读不到磁盘（中枢）时，才用它。在中枢上，每个设备一行，所以两台设备上的同一条路径不会互相覆盖。
4. **`cwd` 的最后一段。** 这种情况不存任何行。目录已经不在、又没有 Agent 记下的事实、也没有学到的根时，就停在这里。

`event.project` 和 `session.project` 保持行上的标签（`session.project` 取第一个事件的）。解析后的名字在 `session_place`，每个会话一行，过滤匹配的是它。条目不会被改名。过滤匹配条目自己的项目，或它所引用的某个会话解析后的项目，所以写在工作树目录名下的条目，用那个名字和用主项目的名字都能找到。

设备为 git 或 Agent 的解析追加 `places.jsonl`（根行和位置行），并像推送其他镜像一样推送它。目录不存在、退回最后一段、或名字是 Agent 选定的，都不追加。一行再次成为结论时会再追加一次，即使文件前面已经有过同样的文字。本 Origin 不认识的 `v`（目前只读 `1`；将来的 `"v":2` 即是一例）按原样留在镜像里，解析时跳过并记一条警告。以后哪个格式开始认识它，就在那个格式的迁移里再调用一次 `reparsePlaces`。中枢从这些行得知名字，`project_root` 每个设备一行。在这些行到达之前，中枢仍显示 `cwd` 的最后一段；那里的召回也只有在根行到达之后，才把链接的工作树和它的主检出当作同一个项目。两边的库都不改条目的名字。`origin sessions reproject` 为已经归档的会话追加同样的行；这些行被采集之后，表才会变。`--dry-run` 什么都不写，但仍报告每个旧名字、有多少会话会改、仍用旧名字的条目，以及顶层会话和子会话的数量。目录已经不在时，如果这台机器上还留着 Agent 自己的记录（Grok Build 的 `git_root_dir`，ZCode 的 `directory`），可以用它来解析。

## 召回 {#recall}

召回是 Origin 不经询问就交给 Agent 的内容：会话开始时的一份简报，以及与每个提示匹配的条目和过往消息。Agent 通过它们的 hook 运行召回（`origin recall --hook <agent>`，见[召回](guide/recall.md)）；hook 无法交出内容的 Agent，则用 MCP 工具 `brief` 主动请求。召回不调用任何模型，每一次都有记录。

**范围。** 召回针对一个工作目录。它的项目是包含这个目录的主 git 工作树（链接的工作树就是那个检出）；不在工作树中时，就是这个目录本身；项目名是主工作树的最后一段，与归档中一致（见[项目](#projects)）。从记忆文件导入的条目属于这个文件所对应的目录，会话属于它的工作目录，所以两个同名的检出能够区分开，主目录也不会把它下面的项目都算作自己的；通过 Origin 写下的条目属于它写明的项目。

- 其他项目的记忆和知识从不交出。认知（用户的偏好、方法、目标和边界）在哪里都成立，但简报只包含本项目的认知和不属于任何项目的认知：某个项目的 Agent 记忆文件很少说明它在别处是否也成立，所以其他项目的认知只有在提示与它匹配时才会交出。
- 只交出当前的条目：没有被取代、遗忘、结束，也不是尚未开始的。
- Agent 不会拿到从它自己为本项目保存的记忆文件导入的条目，这些文件它自己会加载。

**会话开始时**（新的、清空后的或压缩后的会话；已经有过简报的恢复会话不再给），一份简报：

- 认知：先是本项目的，再是不属于任何项目的，从新到旧，最多 5 条；
- 本项目的记忆和知识，从新到旧，最多 5 条；
- 本项目最近 30 天内结束的、主人与任意 Agent 的对话（见[检索与时间线](#search-and-timeline)；本会话除外），最多 3 个：Agent、时间、会话 id、标题或第一条提示，以及最后一条提示。子 Agent 的会话、无界面运行、有父会话的会话，以及只有别人的话的会话不在其中。父会话的那一行在它有子会话时也会说明有多少，以及它们的工作流名称（见[父会话](#parent-sessions)）。与其他会话同在一条线索中的会话以它的线索代替（见[线索](#threads)），这条线索只占 3 行中的一行，且只出现一次：它的 id、多少个会话及其 Agent、第一天和最后一天、名称、最后一条提示，以及根会话有子会话时同样的子会话数量。

**用户输入的每个提示**，与它匹配的条目，最多 5 条；Agent 当作提示交进来的内容（例如用标签包着的后台任务通知）什么也拿不到，归档也不把它当作提示（见[会话名称](#search-and-timeline)）。匹配是基于词汇的，结果确定：

- **词。** CJK 之外的单词（字母、数字和 `_`；`linkos.io` 这样的名称既整体算一个词，也按各部分算），以及按平台（ICU）分词得到的 CJK 词；分词器不认识某个词而留下单字时，用相邻两字组成的词对代替，按一半计。停用词会去掉，项目自己的名字也会去掉。
- **匹配什么。** 条目的第一行，它说明条目是关于什么的；正文几乎总能在某处匹配上提示。
- **权重。** 一个词的权重是它在用户自己的话（归档中用户最近的 1,000 条提示，即主人的提示，见[检索与时间线](#search-and-timeline)：Agent、程序和别人写的内容不算在内）和条目第一行中的逆文档频率，所以用户一直在说的词权重很低。
- **阈值。** 当条目含有的提示中的词，权重加起来超过最罕见的词的权重（两个罕见的词，或者几个常见的词），而且它的 BM25 分数至少是最佳匹配的 40% 时，条目才算匹配。本会话上一次简报之后已经交出的条目会被略去。

**过往消息。** 在条目之后，是与提示匹配的过往消息，最多 3 条：项目以前的对话里说过的话，直接从归档本身交给 Agent，即使没有人为它写过条目。只检索项目的消息，所以没有项目的召回不交出过往消息。

- **候选。** 提示中权重最高的 6 个词（按上面的权重），从它在 CJK 之外、至少三个字符且含字母的单词，以及至少两个字的 CJK 词中选取；代替未知词的字对和项目的名字不算，权重相同时按它们在提示中的顺序。每个词都在检索索引中（见[检索与时间线](#search-and-timeline)）查找本项目在这次召回之前的消息，每个词取最新的 50 条。
- **哪些可以交出。** 一条可见的消息，即主人的提示或 Agent 的回复，所在的会话是主人在本项目中的对话，会话归属与简报相同，所以两个同名的检出能够区分开。子 Agent 的会话、无界面运行，以及只有别人的话的会话不在其中，与简报一样；这次召回自己的会话（如果它写明了会话）以及本会话上一次简报之后已经交出的消息，也会被略去。
- **匹配。** 每个候选的开头，即它的前 2,000 个字符，按条目第一行的方式匹配，权重和阈值相同。一个会话由它最好的那条消息代表，所以各行来自不同的会话。
- **那一行。** 消息的事件 id、它的 Agent、日期和作者（`user` 或 `assistant`），然后是一行摘录：从它含有的提示中权重最高的词第一次出现处之前一点开始（约 12 个 token，从一个词的开头开始），截到约 60 个 token，有内容被略去的一端标上 `…`。对这个 id 调用 `get` 可以打开整条消息及其前后的轮次。

**预算。** 每项一行：条目的 id 和第一行，或者会话、线索的这些信息，截到约 40 个 token，或者如上所述的过往消息的一行，上面有一行说明，告诉 Agent `get` 可以打开其中的任意 id（条目得到它的正文和来源，会话或线索得到它的各轮或各个会话，以及在其中写下的内容，在可能含有过往消息的召回中，消息得到它的全文及其前后的轮次；见[沿引用阅读](#reading-along-references)），并且用户在本会话中说的话优先。一份简报最多占 800 个 token，一个提示的匹配最多 600 个，Agent 请求的简报最多 1,500 个，按每个 CJK 字符一个 token、其他字符每四个一个 token 估算；放不下的会被略去。

**记录。** 每一次召回（包括什么都没匹配到的）都是 `recall` 中的一行，它的各项在 `recall_item` 中：一个 id（`rcl_…`）、时间、进行召回的库、Agent 及其会话、时机（`start`、`prompt`，或者 `request`，表示 Agent 用 `brief` 请求）、项目和目录、预算和用掉的 token，以及每一项的排名、层、类型（条目、会话、线索或事件）、id、分数和大小，事件还有它的摘录在正文中从哪里开始（按码位计），以便准确地重新截出那一行。召回不保存任何文本，提示只存哈希，这样遗忘隐藏的内容不会仍从记录中显示出来（不变量 2）：每一项是什么，在显示召回时才从库中读取，已遗忘的显示为已遗忘；管理界面也以同样的方式重建交给 Agent 的文本（`rebuildRecall`），只用仍然可见的内容，之后遗忘的不显示。两张表都是只追加的。设备会把自己所做的召回发送给中枢（见[复制](#replication-raw-mirrors-entries-and-tombstones-up-tombstones-down)），所以中枢保存着每台设备的召回。`origin recalls` 列出召回，`origin show rcl_…` 显示一次召回，包括它回应的提示（会话中具有该哈希的用户消息，归档之后才能找到），以及每一项本会话之后是否用上了：它的 id 是否出现在该会话中 Agent 之后的工具调用或回复里。

**Hook。** Claude Code 和 Codex 发送同样的 hook 事件，也读取同样的回答；`origin agents connect` 把 hook 加到它们的设置中，并把 Origin 的 MCP server 注册到每个已安装的 Agent，事先显示要做的修改，并备份每个文件。它添加两类 hook，按命令识别，再次运行时会补上 Agent 缺少的 hook，所以由早先版本连接的 Agent 也会得到新的 hook：召回 hook，即 `SessionStart` 和 `UserPromptSubmit` 时的 `origin recall --hook <agent>`，Agent 会等待它（最多 10 秒）；以及采集 hook，即 `Stop` 和 `SubagentStop` 时、在 Claude Code 中还有 `PostCompact` 时的 `origin sync --hook <agent>`，它们在后台运行（见[实时采集](#live-ingestion)）。Codex 只有在用户用 `/hooks` 信任了新的或改动过的 hook 之后才会运行它。`origin agents disconnect` 移除这两类 hook，别的什么都不动。`origin recall` 只加载核心和适配器，以便快速启动，而且从不妨碍 Agent：出现任何故障时，它什么都不输出，在标准错误中说明原因，并以 0 退出；它最多等待 3 秒获取库的写锁。它只读取本设备的库，所以其他设备上写下的条目暂时不会被召回；中继不保存条目，不交出任何内容。

**其他 Agent 的 hook。** ZCode 发送 Claude Code 的事件，旁边附带 camelCase 字段，也读取同样的回答，回答中写明它所问的事件；它的 hook 在 `~/.zcode/cli/config.json` 的 `hooks.events` 下，只有 `hooks.enabled` 为 true 时才会运行，`origin agents connect` 只在 Origin 的 hook 是那里仅有的 hook 时才打开它。ZCode 把子 Agent 和每个工作流步骤作为单独的会话运行，会话 id 表明了这一点（`sess_subagent_agent_…`、`sess_dwf-<run>-<actor>`），这些会话什么都拿不到。Cursor 的 hook 在 `~/.cursor/hooks.json` 的 `beforeSubmitPrompt` 中，它得到的是对话的 id 和工作区文件夹，而不是工作目录：第一个文件夹就是目录，回答是 `additional_context`。Cursor 在创建对话时运行 `sessionStart` hook，并不等待它，常常丢掉它返回的内容，所以对话的第一条提示带来简报以及与提示匹配的内容，记录为时机为 `start` 的一次召回；子 Agent 的对话写明了它的父对话，什么都拿不到。召回记录的是 Agent 的来源 id，以及归档中所用的会话 id（ZCode 的 `sess_…`、Cursor 的对话 id）。Grok Build 和 Cursor 也会运行 `~/.claude/settings.json` 中的 hook，Grok Build 还会运行 `~/.cursor/hooks.json` 中的 hook，传入的是它们自己的事件：Origin 的 hook，无论召回还是采集，只为写明的那个 Agent 工作；事件或环境表明是别的 Agent 时（Grok Build 的 `GROK_HOOK_EVENT`，或同时带有 `hookEventName` 和 `workspaceRoot`；Cursor 的 `cursor_version`；ZCode 同时带有的 `hookEventName` 和 `agentName`），它什么都不做，也不打开库。Grok Build 在会话开始时和随提示都不读取 hook 返回的任何内容，所以不设 hook：它按 server 的说明调用 `brief`。`origin agents` 还会说明 Codex 何时尚未信任任何 hook，这一点在 Codex 的配置中没有 `trusted_hash` 时可以判断出来。

**通过 MCP。** `brief` 交出一份简报，加上 `about` 时还有与它匹配的条目和过往消息，记录为时机为 `request` 的一次召回。由 Agent 运行的 server 作答：在设备上根据设备的库作答，已接入中枢的设备也不询问中枢，与 hook 一致；中继把它交给中枢，以自己的工作树作为目录，中枢看不到 Agent 的磁盘，所以按原样使用这个目录，并把这次召回记录为为该设备所做。MCP 调用不说明会话，所以这类召回不记录会话，并且可能交出 Agent 自己会话中的消息；它的会话是日志中有某个工具结果含有这次召回 id 的那个会话，归档之后才能找到。

**按项目名称。** 不在任何目录中工作的 Agent，比如 OpenClaw 的 Agent，或者访问中枢 `/mcp` 的机器人，给 `brief` 传 `project` 而不是 `cwd`。这时召回针对这个名称，没有目录也没有工作树，也不使用 server 自己的目录：条目和会话按它们所归的项目划入范围（OpenClaw Agent 的会话归在它的 Agent id 之下）。同时给出 `cwd` 时，`project` 指定项目，`cwd` 给出它的目录，对于记录了目录的会话和导入的条目，仍由目录决定。中继把这样的调用原样交给中枢，`origin recall --project` 预览的是同样的简报。

## 个人中枢 {#personal-hub}

中枢就是一个普通的 Origin 库，只是额外运行了 `origin serve`。它是自托管、单租户的：一个人，以及这个人的设备和 Agent。中枢中没有任何部分依赖特定的托管服务商；发布的容器镜像 `ghcr.io/openlinkos/origin` 可以在任何地方运行它。

### 角色 {#roles}

每个库都是一个副本；中枢是那个始终在线的副本。

- **设备**：任何有 Agent 会话记录的机器。它的库本身就是完整的：它在本地采集（适配器、原始镜像、游标、改写代次、压缩都保持不变），它的 Agent 读写这个库，离线时也照常工作。接入中枢后，它把自己写下的内容发送给中枢（`origin sync`，以及运行中的 `origin mcp`），并通过中枢读取其他库中的内容。
- **中继**：一台不保有自己记忆的设备，适用于磁盘空间不多的机器。它在 Agent 写下记录时就把记录发送给中枢，所有问题都通过中枢回答（见[中继](#relays)）。
- **中枢**：`origin serve` 为 Agent 提供基于 HTTP 的 MCP，为设备提供复制 API，启用后还为它的主人提供一个管理界面。它保存每台设备发来的内容，以及云端 Agent 直接写入它的内容和没有设备的写入者向它追加的事件行（见[你自己的来源](#your-own-sources)），所以在那里能找到一切。它可以把原始镜像中已封存的帧保存在兼容 S3 的存储桶中，而不是自己的磁盘上（见[帧存储](#frame-stores)）。

### 复制：原始镜像、条目和遗忘记录上行，遗忘记录下行 {#replication-raw-mirrors-entries-and-tombstones-up-tombstones-down}

设备把自己写下的内容发送给中枢；中枢发给设备的只有被遗忘的内容。一次同步（已接入中枢的设备上的 `origin sync`）按顺序分四步进行：

1. **原始镜像。** 设备推送的是**原始镜像字节**，而不是解析后的事件。中枢把它们存为自己的只追加镜像，并用同样的适配器解析，因此溯源（不变量 1）在中枢上同样成立，解析器的修复也会在所有地方生效。事件 id 在每个库中都完全相同。
   - 每个远程文件以 `(source, "@<device>:<original path>", generation)` 为键；本地路径永远不会以 `@` 开头。中枢上的镜像位于 `raw/devices/<device>/<source>/<relPath>[.g<n>]`，存储方式与其他镜像相同（见[原始镜像](#raw-mirrors)）。
   - 推送可续传且幂等：设备先向中枢查询游标，再把每个镜像的 `[cursor, local size)` 区间按完整行分块发送（每块最多 1 MiB，或者单独一个更长的行）。偏移量与中枢游标不一致的块会被拒绝，并返回当前游标，设备从那里继续。偏移量和游标都按镜像未压缩内容的字节计算：设备解压读取自己的镜像，请求在传输中以 gzip 编码，中枢再压缩存储。
   - 中枢直接拒绝的文件（`400`、`413`），例如早期版本的中枢还不认识的人自己的来源的文件，会被报告出来并留到下一次同步，与中继的做法相同；其他文件，以及随后的条目、遗忘记录和召回记录，照常发送。
   - 如果设备的另一个文件已经占用了某个新文件的镜像名称，即两个相对路径相同的原始路径，例如用某台设备的令牌追加的行与这台设备自己的来源并存，或者设备挪动过某个 Agent 的目录，这个新文件会得到一个自己的镜像名称（见[原始镜像](#raw-mirrors)）。
2. **条目和遗忘记录上行。** 设备按照自己 `change_log` 的顺序，发送推送游标之后它自己写下的条目和遗忘记录（遗忘与恢复；也就是 `origin` 为它的名称的那些）。它从原生记忆派生出的条目不发送：中枢会从设备的镜像派生出同样的条目（见[原生记忆](#native-memories)）。被隐藏的条目不会被发送；被恢复带回的条目会再次记录，并在那时发送。中枢以相同的 id 保存它们，保留作者和 origin，并按[遗忘](#forgetting)中的规则应用这些遗忘记录，所以一个到达时已属于被遗忘内容的版本或条目，会在到达时就被隐藏。由于设备先推送镜像，它的条目所引用的事件通常已经在中枢上了；如果某个条目引用的事件或它取代的版本还不在中枢上，中枢会说明缺少哪些 id，推送游标停在这个条目之前，之后的条目等到下一次同步。遗忘记录照样发送：遗忘从不等待。
3. **遗忘记录下行。** 设备请求中枢 `change_log` 中位于自己拉取游标之后的遗忘记录；中枢会略去该设备自己创建的那些，并为每次遗忘附上它此刻在中枢上覆盖的内容一起发送。设备把它们应用到自己的库中，从而让遗忘和恢复到达每一个副本（不变量 2）。当一次遗忘在中枢上覆盖的内容后来发生变化——因为中枢把它应用到了设备没有的数据上，因为到达了它所覆盖的纠正或条目，或者因为一次恢复让中枢重新判断了规则 3——中枢会再次记录它，于是每台设备，包括创建它的那台，都会收到新的覆盖内容，它会替换中枢上一份列表。先于它的遗忘到达中枢的恢复，会在那次遗忘到达后再次记录；在订阅流的同一页中被记录多次的遗忘记录只发送一次，位置在它最后一次被记录的地方。
4. **召回上行。** 设备按从旧到新的顺序，发送召回游标之后它所做的召回（见[召回](#recall)），也就是 `origin` 为它的名称的那些。召回只含 id，所以不需要中枢先有别的内容，中枢以同样的 id 保存它。不认识召回的旧版中枢会返回 404：召回连同游标一起留在设备上，等中枢升级后再发送。

- **只有遗忘记录下行。** 中枢从不把条目或事件发给设备：设备的库只保存它自己的会话、它自己的条目，以及与之相关的遗忘记录。
- **每个条目只有一个裁决者。** 设备应用来自中枢的遗忘记录时，只对中枢还没有收到的条目判断规则 3（不再有可见来源）。对其余条目，中枢持有每一个版本，它的裁决作为这次遗忘覆盖内容的一部分到达，所以设备和中枢对它们都有的条目保持一致。在设备上做出的遗忘或恢复，会立即在设备上按它持有的版本判断；对于中枢已有的条目，随后以中枢的判断为准。如果中枢持有来自另一个库的更新版本，一次恢复可能让设备继续隐藏一个中枢显示的条目（见[待解决的问题](#open-questions)）。
- **游标。** 设备在 `setting` 中为每个中枢 URL 保存三个游标：自己的变更推送到了哪里、中枢的变更拉取到了哪里，以及自己的召回发送到了哪里。每次请求成功后都会保存游标，所以中断的同步会从中断处继续，再次运行则什么也不会发送。
- 在中枢上被遗忘的事件即使被再次推送，也会保持排除，因为排除按事件 id 生效。

### 访问 {#access}

中枢只有一个人，即它的**主人**，访问中枢的一切都代表这个人：主人的**设备**，每台都是有自己的库、与中枢复制的机器；以及主人的 **Agent**，即使用中枢的 `/mcp`、可能还追加事件行的云端 Agent、机器人和流水线。它们每一个都是主人名下一个有名称的主体，持有凭据，主人在同一个地方查看和吊销这些凭据：管理界面的「设备和 Agent」页面（或者 `origin token list` 和 `revoke`）。没有其他人，也没有邀请或角色：别人要用，就运行自己的中枢。

- **凭据。** 发往 `/mcp` 和 `/v1/*` 的每个请求都需要 `Authorization: Bearer <credential>`；`/admin` 下的管理界面有自己的登录（见[管理界面](#admin-ui)）。没有有效凭据的请求会被拒绝，返回 `401 { error, docs }`，`docs` 是中枢指南的地址。除管理界面外，只有 `/healthz`、公开首页、`/robots.txt`、首页用到的文件，以及 OAuth 的元数据和端点（见下文）不需要凭据，它们不显示库里的任何内容。凭据是以下两种之一，都只显示一次，只以 SHA-256 哈希的形式存储，并且可以吊销：
  - **令牌**（`ogn_…`），属于一台设备或一个 Agent，在中枢上创建（`origin token create <name> [--agent [--readonly]]`，或者管理界面中的**添加 Agent**），或者发给主人在浏览器中批准的设备（见[从设备使用中枢](#using-a-hub-from-a-device)）；它永不过期；
  - 通过 OAuth 登录的 Agent 的**访问令牌**（`oga_…`），有效一小时，只用于 `/mcp`，也就是签发它时所针对的资源：`/v1/*` 拒绝它（`403`）。
- **预设权限。** 主体能做什么：`readwrite`，即令牌一直以来能做的一切，用于设备，也是 Agent 的默认值；或者 `readonly`，只用于 Agent：`/mcp` 中没有写入类工具（`remember`、`propose`、`correct`、`forget`；见 [MCP server](#mcp-server)），也不能向 `/v1/*` 提交任何内容（`403`），但 `/v1/*` 仍会回答它的读取请求。在有预设权限之前创建的令牌是 `readwrite`，所以照旧可用。
- **每个令牌绑定一台设备，即与它同名的设备。** 在复制接口上，令牌只能为这台设备发送和接收数据：它推送的内容都记在令牌名下，请求里指明了其他设备（请求体或查询参数中的 `device`）时会被拒绝并返回 `403`，`origin` 不是这台设备的记录同样会被拒绝。因此设备的库必须与它的令牌同名，`origin hub connect` 会检查这一点（见[从设备使用中枢](#using-a-hub-from-a-device)）。与中枢自身同名的令牌不服务于任何设备；只用于 `/mcp` 的令牌（例如云端 Agent 的令牌）不需要对应设备。被吊销的令牌可以用同一个名称新建一个来替换，所以丢失令牌的设备仍能保留它的名称；有效的令牌必须先吊销。Agent 的令牌也以同样的方式在它的名称下追加事件行。
- **用 OAuth 登录。** 管理界面挂载在中枢自己端口的 `/admin` 下时，中枢就是它的 `/mcp` 的 OAuth 2.1 授权服务器，如 MCP 授权规范所述，这样 Claude Code 或 Codex 之类的 MCP 客户端就通过主人的浏览器登录，而不是拿到一个令牌。这时 `/mcp` 返回的 `401` 会说明受保护资源元数据在哪里（`WWW-Authenticate: Bearer resource_metadata="<hub>/.well-known/oauth-protected-resource/mcp", scope="readwrite"`，RFC 9728），这份元数据指明中枢就是授权服务器，而授权服务器的元数据（RFC 8414）列出各个端点、只支持 `S256` 的 PKCE、只支持公开客户端（`token_endpoint_auth_methods_supported: ["none"]`）、各个 scope（`readwrite`、`readonly` 和 `offline_access`）、客户端 ID 元数据文档，以及授权响应中的 `iss` 参数（RFC 9207）。其中中枢的地址都是公开 URL；没有公开 URL 时，对于经回环地址发往回环主机名的请求，则是 `http://<Host>`，与管理界面的响应方式相同。在其他情况下，以及在没有管理界面、或者管理界面在单独的监听地址上（`--admin-listen`）的中枢上，元数据和端点返回 404，`401` 则和以前一样是普通的 `Bearer` 质询。
  - **客户端**要么注册（RFC 7591；重定向 URI 只能是 `http://127.0.0.1:<port>/…`、`http://localhost:<port>/…` 或 `https://…`；没有密钥；一直没有得到授权的注册在一天后被丢弃，同一时间最多有 200 个在等待），要么用一份**客户端 ID 元数据文档**的 https URL 来指称自己，由中枢获取这份文档：只用 https，只从公网地址获取（名称解析到的每个地址都会被检查，连接也只连向检查过的地址，这样 DNS 无法在两者之间指向别处；使用 fake-IP DNS 的代理所回答的基准测试地址段算作公网地址），最多 3 次重定向，每次都同样检查，限时 5 秒，最大 5 KiB。文档必须是 JSON，它的 `client_id` 就是它的 URL，带有 `client_name`，重定向 URI 如上所述，并且没有密钥；中枢按它的 `Cache-Control` 保留它，介于 5 分钟到一天之间（没有这个头时为一小时）。获取文档由 CLI 负责，因为 `core` 和 `admin` 不发起任何网络请求。
  - **授权**（`/oauth/authorize`，它转到 `/admin/oauth/authorize`）需要主人已登录，并在最近 10 分钟内输入过密码；它先检查客户端及其重定向 URI（回环重定向 URI 可以改变端口，RFC 8252），有任何错误都显示给主人；之后的错误则连同客户端的 `state` 和签发者一起返回给客户端。必须提供代码质询（`S256`）；如果给出了 `resource`（RFC 8707），它必须是中枢的 `/mcp`。授权页面写着，例如「Claude Code 想使用你的 Origin 记忆」，说明浏览器之后会回到哪里（如果那是 localhost 地址，会发出警告，因为任何程序都可能在监听它），以及客户端的名称是来自它自己地址上的一份文档，还是只来自它的注册；主人从客户端请求的预设权限中选择一个（只请求了 `readonly` 的客户端不能被授予 `readwrite`），并选择授权的有效期（1、30、90 或 365 天），或者拒绝。这个页面的 Content-Security-Policy 把重定向 URI 的源加入 `form-action`，因为作答会把浏览器送到那里。
  - **令牌**（`/oauth/token`）：授权码只能使用一次，须在一分钟内使用，只对签发给的客户端和重定向 URI、以及与其质询相符的 PKCE 验证值有效；再次出示的授权码会吊销它所给出的授权。授权就是主人的一个 Agent，以它的客户端命名（`claude-code`；这个名称仍在使用时则是 `claude-code-2`；从不与某个令牌或中枢同名）。它得到一个有效一小时的访问令牌和一个刷新令牌；每个刷新令牌只能使用一次，并给出下一对令牌（轮换），再次出示的刷新令牌会吊销整个授权（重用检测），任何令牌都不会比它的授权存续得更久，刷新也不能扩大授权。`/oauth/revoke`（RFC 7009）让客户端退出登录：刷新令牌会吊销它的授权，访问令牌只吊销它自己。
  - 通过 OAuth 登录的 Agent 经 `/mcp` 写入的内容，以授权的名称记为作者，与 Agent 的令牌名一样。
- **审计。** 审计日志写明是谁做的：管理界面中是主人的用户名，中枢命令行上是 `cli`；Agent 通过中枢的 API 对自己的访问权限所做的操作（退出登录，或者因为某个授权码或刷新令牌被出示了两次而吊销授权）记为 `<username> / <agent>`，设备（收到它的令牌）记为设备的名称，后两者的渠道为 `api`。
- 中枢使用明文 HTTP。在 localhost 之外开放之前，请把它放在 TLS（反向代理或 CDN）之后。
- 设备推送上来的条目保留写入时的作者。通过中枢的 `/mcp` 写入的条目，如果调用方在 `X-Origin-Client` 中报上了它的 Agent（设备上的 `origin mcp` 就会这样做），作者记为 `<agent>@<主体名>`（如 `claude-code@laptop`）；否则只记主体的名称（例如云端 Agent 的令牌 `ci`，通过 OAuth 登录的 Agent 则是 `claude-code`），因为无状态请求不携带 MCP 客户端的名称。作者中的设备部分始终是主体的名称：设备上的 `origin mcp` 还会在 `X-Origin-Device` 中报上自己的名称，如果这个请求头指明的是另一台设备，中枢会拒绝请求（`403`），所以任何凭据都不能以另一台设备的身份写入，库名与令牌不一致的设备也会明显地报错。中继上的 `origin mcp` 发送同样的请求头，所以它的 Agent 写入的内容记为 `<agent>@<中继名>`，origin 为中枢；它的 CLI 写入的内容记为 `user@<中继名>`。

### HTTP 接口 {#http-interface}

| 方法与路径 | 用途 |
|---|---|
| `GET /healthz` | `{ "ok": true, "version": … }`，无需鉴权 |
| `GET /` | 公开首页，无需鉴权：Origin 的标志和名称，一句说明这个中枢是什么的话（语言取自 `Accept-Language`），管理界面挂在 `/admin/` 时有指向它的链接，以及「由开源的 Origin 驱动」和指向项目网站与源代码的链接（`ORIGIN_POWERED_BY` 为 off 时不显示）。接受 `application/json` 而不接受 `text/html` 的请求会收到 `{ "service": "origin", "docs": … }`。带有管理界面的 Content-Security-Policy 和防护响应头，`Cache-Control: no-store` |
| `GET /robots.txt` | 禁止一切：个人中枢不进搜索结果；无需鉴权 |
| `GET /assets/…` | 公开首页用到的文件：设计系统的样式表及其字体，以及标志，使用带内容哈希的文件名，按不可变内容缓存；无需鉴权 |
| `GET /.well-known/oauth-protected-resource/mcp` | 管理界面在 `/admin` 下时（见[访问](#access)）：`/mcp` 的受保护资源元数据（RFC 9728），`{ resource, authorization_servers, scopes_supported, … }`；`/.well-known/oauth-protected-resource` 下也有。无需鉴权；否则返回 404 |
| `GET /.well-known/oauth-authorization-server` | 有管理界面时：授权服务器元数据（RFC 8414）。无需鉴权；否则返回 404 |
| `POST /oauth/register` | 有管理界面时：公开客户端的动态客户端注册（RFC 7591），输入输出都是 JSON；返回 `201 { client_id, … }`，或者 `400 { error, error_description }` |
| `GET /oauth/authorize` | 有管理界面时：授权请求，交给 `/admin/oauth/authorize` 的授权页面（`302`） |
| `POST /oauth/token` | 有管理界面时：一个表单，`grant_type` 为 `authorization_code`（带 `code`、`client_id`、`redirect_uri`、`code_verifier`、`resource`）、`refresh_token` 或 `urn:ietf:params:oauth:grant-type:device_code`（带 `device_code` 和 `client_id=origin`）；返回 `200 { access_token, token_type, expires_in, refresh_token, scope }`，对设备则返回带有它的设备令牌的 `{ access_token, token_type, device }`；其他情况返回 `400 { error, error_description }`，例如设备等待期间的 `authorization_pending` 或 `slow_down` |
| `POST /oauth/revoke` | 有管理界面时：由客户端发起的令牌吊销（RFC 7009）；总是返回 `200` |
| `POST /oauth/device` | 有管理界面时：供 `origin hub connect` 使用的设备授权（RFC 8628），一个带有 `client_id=origin` 和 `device_name` 的表单；返回 `200 { device_code, user_code, verification_uri, verification_uri_complete, expires_in, interval }`，验证码有效 10 分钟 |
| `POST /mcp` | MCP Streamable HTTP，无状态，JSON 响应；与 stdio server 相同的十二个工具，对 `readonly` 的 Agent 则不含写入类工具。中枢提供 OAuth 时，`401` 会指明受保护资源元数据 |
| `GET /v1/device` | `{ device, hub }`：令牌所属的设备（即令牌名）和中枢的名称 |
| `GET /v1/cursors?device=<name>` | 令牌所属设备的每个文件在中枢上的字节游标；加上 `&source=<id>&path=<path>` 时，只给出那一个文件每个代次的游标（较早的中枢会忽略这两个参数，列出每个文件，由调用方从中挑出这个文件） |
| `POST /v1/ingest` | 追加一个块：JSON `{ device, source, path, relPath, generation, offset, mtimeMs, agentVersion, data }`，其中 `data` 为 base64，`offset` 按镜像未压缩的内容计算（中继发送的是文件的内容，二者相同）；请求体可以使用 gzip 编码。返回 `200 { bytes, eventsAdded, … }`，偏移量不匹配时返回 `409 { bytes }` |
| `POST /v1/sources/<name>/lines?path=<path>` | 为没有自己设备的写入者追加事件行（见[你自己的来源](#your-own-sources)），写到来源 `<name>` 的文件 `path`，视为令牌所属设备发送的内容。请求体是 `application/x-ndjson` 或 `text/plain`，可以用 gzip 编码；解压后最多 8 MiB，没有换行符的最后一行以请求体结尾为界。`<name>` 必须是人自己的来源名称，不能是内置来源；`path` 是相对路径，由 `/` 分隔的若干部分组成，每部分由字母、数字、`.`、`_` 和 `-` 组成并以字母或数字开头，以 `.jsonl` 结尾，最多 200 个字符。返回 `200 { lines, events, duplicates, parse_errors }`；名称、路径或请求体无效时返回 `400`，请求体过大返回 `413`，媒体类型不对返回 `415` |
| `POST /v1/entries` | `{ device, entries }`，最多 1,000 个条目，每个为 `{ id, kind, text, confidence, author, project, supersedes, validFrom, validTo, createdAt, origin, sources: [{ eventId, quote }] }`，其 `origin` 必须是令牌所属的设备。按顺序保存；返回 `200 { applied, pending }`，其中 `pending` 为 null，或者是第一个所引用事件或所取代版本尚不在中枢上的条目的 `{ id, missing }`（它之后的条目都不会被保存）。同一个 id 下内容不同时返回 `409` |
| `POST /v1/tombstones` | `{ device, tombstones }`，最多 1,000 条遗忘记录，每条为 `{ id, target, reason, createdAt, origin, author, entries, events }`（`author` 可选），附带它在设备上覆盖的内容，其 `origin` 必须是令牌所属的设备。恢复的目标是一次遗忘的 id，并且不列出任何内容；如果中枢还没有收到它的遗忘，就先保存它，等那次遗忘到达时生效。按[遗忘](#forgetting)中的规则应用；返回 `200 { applied }`，同一个 id 下内容不同时返回 `409` |
| `POST /v1/recalls` | `{ device, recalls }`，最多 1,000 次召回，每次为 `{ id, at, origin, source, sessionId, occasion, project, cwd, promptHash, budget, tokens, items }`，每一项为 `{ rank, layer, kind, ref, score, tokens, excerpt }`，其中过往消息的 `excerpt` 可以省略，0.5 及更早版本的设备就不发送它；`origin` 必须是令牌所属的设备。按 id 只保存一次；返回 `200 { applied }`，同一个 id 内容不同时返回 `409` |
| `GET /v1/tombstones?after=<seq>&device=<name>` | `{ tombstones, next, more }`：中枢变更日志中序号大于 `after` 的遗忘与恢复，不含令牌所属设备自己创建的，每条都附带 id、目标、原因、`createdAt`、origin、已知时的作者，对遗忘而言还有它在中枢上覆盖的条目和事件。`more` 为 true 时，用 `after=<next>` 继续 |
| `GET`, `POST /admin/…` | 启用时的管理界面：需要管理员登录的服务器端渲染页面，其中包括授权页面（`/admin/oauth/authorize`）和批准设备的页面（`/admin/activate`）。未启用时返回 404 |
| `GET`, `POST /admin/api/…` | 管理界面的 JSON API：与页面相同的操作、会话和检查 |

中枢会校验每个字段。用 `readonly` Agent 的凭据向 `/v1/*` 发出的 `POST` 会被拒绝并返回 `403`，用 OAuth 访问令牌向 `/v1/*` 发出的任何请求也是如此。复制请求总是代表令牌所属的设备：`device` 可以省略，如果请求指明的是另一台设备，会被拒绝并返回 `403`，响应体中附带令牌所属的设备（`{ error, device }`）。设备名必须匹配 `[a-z0-9][a-z0-9._-]{0,62}`，并且不能是中枢自己的名称，来源必须是内置的来源，或者是一个可以作为人自己来源名称的名字（中枢把它按事件行解析，见[你自己的来源](#your-own-sources)），`relPath` 必须是相对路径且不含 `..` 段，因此设备永远无法写到它自己的镜像目录之外。

### 从设备使用中枢 {#using-a-hub-from-a-device}

设备以两种模式之一使用中枢，在接入时选定。默认情况下，它是一个**完整的库**：像没有中枢时一样保有自己的记忆，并按上文所述与中枢复制。加上 `--relay` 时，它是一个**中继**：除了游标什么也不保存，直接把 Agent 的记录发送给中枢，所有问题都通过中枢回答（见[中继](#relays)）。除非另有说明，本节其余部分说的都是完整的库。

- `origin hub connect <url> [--token <token>] [--device <name>] [--relay]` 把连接信息保存在 `<ORIGIN_HOME>/hub.json` 中。不带 `--token` 时，由主人按设备授权许可（RFC 8628）在浏览器中批准这台设备：这个命令向中枢请求一个验证码（`POST /oauth/device`，使用库的名称），打印指向 `/admin/activate` 的链接和验证码，主人登录管理界面后打开链接或输入验证码，然后批准或拒绝（「把设备 laptop 接入你的中枢？」，附有它请求的时间和来源地址；如果已经有同名的设备接入，还会发出警告，批准会取代那台设备的令牌）；在此期间，命令每 5 秒询问一次 `POST /oauth/token`（每收到一次 `slow_down` 再加 5 秒），最多 10 分钟，获批后以自己的名称收到一个设备令牌，只收到一次。这和 OAuth 一样，需要管理界面挂在中枢端口的 `/admin` 下（见[访问](#access)）；否则，或者带上 `--token` 时，使用在中枢上创建的令牌。设备名就是它的库的名称（见[存储](#storage)），而且必须是这台设备的令牌名：这个命令会向中枢询问令牌属于哪台设备（`GET /v1/device`），如果不是这个库，就拒绝接入并说明如何解决。`--device` 可以给一个还没有写入任何条目或遗忘记录的库改名。`origin hub status` 也做同样的检查。每一次与中枢的同步，无论由哪个命令或 Agent 发起，都会在 `setting` 中记下它完成的时间，失败时则记下时间和原因；`origin status` 和 `origin hub status` 显示上一次同步完成的时间，以及此后失败的那一次同步的错误。`ORIGIN_HUB_URL` 和 `ORIGIN_HUB_TOKEN` 会覆盖保存的连接信息。
- 配置了中枢之后，`origin mcp` 仍然根据设备自己的库提供服务，并合并中枢的回答（见 [MCP server](#mcp-server)）。它在运行中与中枢同步：读取类工具之前最多每 10 秒一次，每次写入后立即同步，记录文件有变化时每分钟同步一次，Agent 离开时再同步一次；等待中枢的时间不会超过超时时限。Agent 的采集 hook 还会在每一轮结束后立即推送记录文件新增的行（见[实时采集](#live-ingestion)）。Agent 的注册无需改动，Agent 也仍然能引用刚刚说过的内容。
- 没有本地记录的云端 Agent 直接注册中枢的 `/mcp` URL，并用 OAuth 登录，或者使用 Agent 的令牌（见[访问](#access)）。
- CLI 管理命令（`entries`、`show`、`correct`、`forget` 等）作用于设备自己的库。在已接入中枢的设备上，`correct` 和 `forget` 之后会与中枢同步，所以改动会到达中枢；如果是遗忘，还会到达其他每台设备。`origin ui` 同样作用于设备自己的库，并在每次写入后在后台与中枢同步。中枢的管理界面会显示所有设备的条目。

### 中继 {#relays}

中继是一台不保有自己记忆的设备，适用于磁盘空间不多的机器。它运行与其他设备相同的适配器和相同的 `origin mcp`，但不保存原始镜像，也不保存事件：在中枢收到之前，Agent 自己的记录文件就是它的会话唯一的副本。所以中继不是一份完整的记忆：没有中枢，它什么也回答不了；它发送的一切，其溯源都在中枢上解析，原始行保存在中枢的镜像中。

- **选择中继。** `origin hub connect <url> --token <token> --relay` 把库变成中继。只有还没有保存任何内容的库才能成为中继：已有事件、镜像文件、条目或遗忘记录的库会被拒绝，并附上如何新建一个空库的说明，不会删除任何东西。模式保存在库中（`setting`），而不是连接信息中，所以 `ORIGIN_HUB_URL` 和之后的 `origin hub connect` 都不会改变它；中继也会一直是中继：要在那台机器上保有完整的库，请使用新的 `ORIGIN_HOME`。中继不能运行 `origin serve`；没有接入中枢时，它既不发送也不回答任何东西。
- **保存什么。** 每个来源文件一个游标，保存在 `setting` 中：中枢正在接收的代次、中枢已确认收到的该代次的字节数、这些字节最后 4 KB 的 SHA-256、游标最后变化的时间，对压缩文件还有它是否已全部发送；对生成的来源，用它的令牌代替哈希，并保存中枢已确认收到的最后一行，适配器从这一行接着写。游标保存在 `setting` 而不是 `raw_file` 中，因为一行 `raw_file` 代表 `raw/` 下的一个镜像，备份、封存、存储统计和推送都会读取它；而在 `setting` 中，生成的来源的最后一行与它的游标在同一次写入中改变。除了游标，中继还保存它的名称、模式、复制游标和同步日志：每个来源文件几百字节，外加每个生成的来源的最后一行。
- **发送。** `origin sync`，以及运行中的 `origin mcp`，先向中枢查询游标（`GET /v1/cursors`），再从中继的游标之后、直接从 Agent 的文件（或者它自己的某个来源的文件）读取每个来源文件：压缩文件读取解压后的内容，生成的来源则读取适配器在已发送的最后一行之后写出的行。完整的行按块发送到 `POST /v1/ingest`，每块最多 1 MiB（或者单独一个更长的行），与设备发送镜像的方式相同，最旧的文件先发送。中枢用同样的适配器镜像并解析它们，所以它的镜像、事件和事件 id，与一台完整的设备推送同样这些文件的镜像时完全相同。只有中枢确认收到一个块之后，游标才会前移。Agent 的采集 hook 以同样的方式发送它指明的那一个文件，只向中枢查询这个文件的游标，所以会话的行在每一轮结束时就离开中继，而不必等上一分钟（见[实时采集](#live-ingestion)）；条目和遗忘记录由下一次同步复制。
- **改写。** 变小了的文件，或者已发送的最后 4 KB 不再匹配的文件，说明它被改写了：中继把它作为下一个代次、从偏移量 0 开始发送，中枢保留旧的代次。生成的来源从不检测改写。
- **中枢的进度。** 当中枢持有的某个文件比中继的游标所说的更多或更少时（途中丢失的回应、中继的另一个进程抢先发送、从备份恢复的中枢、以中枢已知的设备名新建的中继库），只要文件在中枢游标处恰好有一行结束，中继就从中枢的游标继续；生成的来源会向适配器要行，直到到达那个偏移量。否则，它把这个文件作为一个新的代次发送。因偏移量被拒绝的块（`409`）也按同样的方式处理。中枢直接拒绝的文件（`400`、`413`）会被报告并跳过，其他文件照常发送。
- **离线。** 什么也不发送，游标也不移动：新的行留在 Agent 自己的记录文件里。有些 Agent 会删除旧的记录（Claude Code 在 `cleanupPeriodDays` 之后删除，默认 30 天），而中继不保留副本，所以中继必须定期连上它的中枢。Agent 运行期间，有 hook 的 Agent 在每一轮结束后由 hook 发送记录文件新增的行，它的 `origin mcp` 也每分钟发送一次新的行，Agent 离开时再发送一次；`origin status` 按来源显示还有多少字节尚未发送。
- **清理前的警告。** 当仍有完整的行尚未发送的最旧文件，临近它的 Agent 删除它的年龄时，中继会发出警告；年龄按文件的修改时间计算，和 Claude Code 的做法一样。对 Claude Code，是在 `cleanupPeriodDays`（从它配置目录中的 `settings.json` 读取，未设置时为 30 天）之前一周以内，如果它短于两周，则是过了它的一半之后；对保留期限未知的 Agent，是这样的文件已有一周之久，而且中继已有一周没有连上中枢。`origin status` 会显示这个警告，`origin sync` 在没能发送全部内容时也会显示；`origin mcp` 在连不上中枢期间最多每小时检查一次，把警告写入它的日志，并附在工具的错误里，让 Agent 看到。检查在 CLI 中进行；`core` 只给出这样的最旧文件（`relayPending`）。
- **回答与写入。** 中继没有可以据以作答的事件，也没有事件可以用来核对条目所引用的事件，所以每个工具都是中枢的（见 [MCP server](#mcp-server)）。写入按中枢的规则在中枢上进行：中枢检查每个被引用的事件都在它那里存在且可见（不变量 1），应用遗忘（不变量 2），并把作者记为 `<agent>@<中继名>`，origin 为中枢（见[访问](#access)）。CLI 的查询和管理命令（`search`、`timeline`、`digest`、`show`、`entries`、`correct`、`forget`）同样询问中枢的 `/mcp`，身份是 `user@<中继名>`；`entries --history`、`projects`、`forgotten` 和 `restore` 在中继上不可用，恢复要在中枢的管理界面中进行。
- **复制。** 中继自己不写条目或遗忘记录，中枢的遗忘记录在它那里也找不到需要隐藏的东西，所以它不保存任何遗忘记录；它仍然拉取这些记录，让自己的复制游标像设备的一样前移。它的 Agent 的记忆所对应的条目，由中枢从中继发来的行中派生（见[原生记忆](#native-memories)）。

### 管理界面 {#admin-ui}

中枢可以为它的主人提供一个 Web 界面。它默认关闭；它是同一个库的一个视图，而不是另一套系统：每个页面、每次 JSON 调用都经过 MCP 和 CLI 所用的同一组 core 操作（不变量 5）。`@openlinkos/origin-admin` 包提供一个请求处理函数，由中枢挂载。`origin ui` 在设备上为该设备自己的库提供同样的界面，并有自己的登录方式（见最后两点）。

- **提供方式。** `origin serve --admin` 把界面挂载在中枢端口的 `/admin` 下；`origin serve --admin-listen 127.0.0.1:7078` 则改在一个单独的监听地址上提供，通过 SSH 隧道或 `kubectl port-forward` 访问。如果界面会在非回环地址上提供，除非 `--public-url`（`ORIGIN_PUBLIC_URL`）是 https URL，或者是回环主机上的 http URL（例如发布在 `127.0.0.1` 上的容器端口），否则中枢拒绝启动。没有公开 URL 时，界面只响应发往回环主机名的回环连接，这同时也能防御 DNS 重绑定。界面未启用时，`/admin` 返回 404。
- **登录。** 中枢只有一个主人，主人用用户名和管理密码登录。用户名（2 到 32 个小写字母、数字、`-`、`_` 和 `.`，保存在 `setting` 中）在第一次登录时连同密码一起选定，新的中枢是这样，从没有用户名的版本升级而来的中枢也是这样，后者原有的会话随之视为已退出登录；`origin admin username <name>` 可以修改它。用户名不是秘密：用户名错误时和密码错误时一样失败，而且照样会先校验密码。设置了 `ORIGIN_ADMIN_PASSWORD` 时，它就是管理密码，并且优先于其他来源；它至少要有 10 个字符，否则中枢拒绝启动。否则，管理密码在中枢上用 `origin admin password` 设置（在终端中输入两次，或从标准输入读取一行），或用 `origin admin password --generate` 生成。如果中枢在启用管理界面的情况下启动时两者都没有，它会生成一个密码（20 个随机 base32 字符，100 位），保存它的哈希，并在日志中只打印这一次。首次访问时唯一的设置就是用户名，而这需要密码，所以新建的中枢不会被第一个访问到它的人占用。密码以 scrypt 哈希的形式（N = 2^15、r = 8、p = 3，随机的 16 字节盐）写成 `scrypt$N$r$p$<salt>$<hash>`，保存在只留在中枢上的 `setting` 中；中枢也会保存 `ORIGIN_ADMIN_PASSWORD` 的这种哈希，以便发现它是否变化。校验逐个进行，并以恒定时间比较。管理密码和中枢令牌互不接受：密码不能以 `ogn_` 开头，`/mcp` 和 `/v1/*` 只接受 bearer 令牌，`/admin` 只接受它自己的会话 cookie。
- **会话。** 会话保存在服务器端的 `admin_session` 中，以会话 id 的哈希为键。会话在 30 分钟没有请求或登录满 12 小时后结束；管理密码变化时，所有会话都会结束：用 `origin admin password` 设置新密码时，以及中枢启动时 `ORIGIN_ADMIN_PASSWORD` 与上次不同，或者在它和保存的密码之间切换时。在 https 公开 URL 之后，cookie 是 `__Host-origin-admin`（Secure、HttpOnly、SameSite=Lax）；在回环 http 上，cookie 是 `origin-admin`（HttpOnly、SameSite=Strict，路径 `/admin`）。在 https 公开 URL 之后，普通 cookie 只在回环隧道上有效，所以从兄弟子域名种下的 cookie 无法固定会话。添加或吊销设备和 Agent、批准 OAuth 客户端或设备，以及结束会话，要求最近 10 分钟内输入过密码。遗忘和恢复只需要会话：两者都是记录，可以互相撤销。
- **请求。** 只有 GET 和 POST，所有写操作都是 POST。POST 需要会话的 CSRF 令牌（表单字段 `_csrf` 或请求头 `X-CSRF-Token`），以及与中枢源相同的 `Origin` 请求头；带有 `Sec-Fetch-Site: cross-site` 的请求会被拒绝。请求体上限为 64 KiB。密码校验失败的次数受到限制：每个客户端每 10 分钟 10 次，总计每 10 分钟 100 次（返回 429 和 `Retry-After`）；只有设置了 `ORIGIN_CLIENT_IP_HEADER` 时才从该请求头取客户端地址，否则取连接的地址。在代理或 CDN 之后，必须设置这个请求头：否则所有客户端共用代理的地址和同一个限额，任何人的失败尝试都可能把主人锁在外面。
- **响应。** 页面在服务器端由一个对每个插值都做转义的模板渲染。Agent 的消息按 Markdown 的一小部分（段落、标题、强调、行内代码、围栏代码块、列表、引用块、分隔线、GitHub 的竖线表格和链接）渲染，渲染器位于管理包中，它只识别结构，并让每一段文本都经过同一个模板输出，所以消息中的 HTML 仍然是文本；链接只能指向 `http` 和 `https` URL，在新标签页中以 `rel="noopener noreferrer"` 打开，并显示它们的 URL。一小段脚本提供一些便利，例如就地加载原始行，但没有页面依赖它。每个响应都带有严格的 Content-Security-Policy（没有内联脚本或样式，启用 Trusted Types 且不允许任何策略）、`Cache-Control: no-store, private`、`Vary: Cookie`，以及防止嵌入、类型嗅探、引用来源泄露和被搜索引擎收录的请求头；在 https 之后还带有 HSTS。所有资源，包括设计系统的样式表、字体和图标，都由中枢自己以带内容哈希的文件名提供；每个页面只内联它用到的图标符号，界面从不发起外部请求。
- **能做什么。** 概览（数量统计；近 30 天每天的可见事件数，按来源区分；最近的会话；这段时间事件最多的项目；每个来源的 Agent 最新版本、最近一次归档和 7 天内的解析错误；设备及其最近推送；最新的条目，以及最近的遗忘与恢复，只显示它们的目标 id、原因和数量；存储：数据库、磁盘上的原始镜像，以及存储桶中的帧）、设备和 Agent（每台设备带有它的令牌和最近发送的数据；使用令牌的 Agent 及其预设权限，添加时令牌只显示一次，旁边附有现成的命令：Claude Code、Codex，以及在它可以写入时的事件行；通过 OAuth 登录的 Agent，带有它们的客户端、预设权限和到期时间；其中任何一个都可以吊销）、OAuth 的授权页面和批准设备的页面（见[访问](#access)）、接入命令、设备及各自发送的内容、时间线（按最近活动的日期排列的顶层会话，每个子会话嵌在它的父会话之下，并以显示标题呈现，可以按来源、项目或父会话名称中的词筛选）、按轮次查看的会话（见下文）、线索及其会话、Agent、分支和从中写下的条目（每个会话的页面都写明它的线索）、带溯源链的事件（原始行按需加载，截断到 4,000 个字符）、检索、条目及其历史、`correct`（未指定时置信度为 1）、从事件页面 `remember`（引用该事件，作者为 `user@` 加中枢的名称），预览之后附上原因的 `forget`：请求带上所展示计划的摘要，如果计划在此期间发生了变化，就不会遗忘任何内容（409）；以及遗忘记录页面，它列出每一次遗忘和恢复，连同时间、origin、作者、原因和覆盖的内容。提议（见[提议](#proposals)）：待审的排在前面，可按状态和项目筛选，每条带有正文、类型、置信度、来源和提出它的会话；在它自己的页面上，**接受**以 `user@` 加库的名称写下它的条目，**拒绝**需要原因，它遗忘提议的事件并打开那次遗忘的页面；被拒绝的提议只列出 id 和原因。概览会说明有多少提议等待审阅，侧边栏也会计数。生效中的遗忘有自己的页面，向主人展示它隐藏的内容——条目的文本和会话事件——并在说明将带回什么之后，附上原因恢复它。
- **按轮次查看会话。** 会话页面把它的事件分成一轮一轮。一轮从一条主人的提示开始（见[检索与时间线](#search-and-timeline)），与 `get` 和 `timeline` 数的轮次相同。一轮也可以从一条命令回显（只由元素组成、带有 Claude Code 的 `<command-name>` 的消息，子 Agent 的除外）开始，前提是 Agent 在下一条提示或命令之前，以自己的消息或工具调用据此工作；这时命令及其参数就是这一轮的提示，判断这一点对每条命令只需查一次 `(source, session_id, ts)` 索引。Agent 没有据以工作的命令，例如 `/clear` 或 `/model`，不开始新的一轮，而是所在那一轮中的一条备注；临时名称仍然跳过所有命令。一轮包含到下一轮开始之前的所有事件，第一轮之前的内容是第 0 轮。在一轮之中，工具调用按调用 id（`callId`，或 Claude Code 的 `toolUseId`）与它的结果配对；没有 id 的，与更早的、同样没有 id 且还没有结果的第一次调用配对；调用的结果取自其结果的错误标记或状态。Agent 在之后不再调用任何工具的最后一条消息是回复，按 Markdown 渲染；它的调用，以及回复之前说的话，折叠在一行摘要之后；读起来像提示、但不是主人写的消息，例如同事的话、子 Agent 的提示或压缩的摘要，作为消息显示在它所在的那一轮中，并带有一个小标签，说明是谁写的：它的说话人，否则是他人、某个 Agent 或系统；命令回显、它们的输出、注入的上下文和系统事件以备注显示。一页包含 20 轮，如果会超过 1,500 个事件就少一些；更长的一轮分成每部分 1,500 个事件。提示通过 `event_user_message` 读取，这是一个只包含用户消息的部分索引；之后只通过 `(source, session_id, ts)` 索引读取从本页第一条提示到下一页第一条提示之间的事件，所以有数千个事件的会话从不会被整个读取。从某个事件出发的链接（`at=<id>`）打开包含它的那一轮所在的页面。会话的日期索引和时间线里的日期，都以服务器的时区为准。
- **召回。** 「召回」页按从新到旧列出 Agent 拿到的内容（见[召回](#recall)），可以按设备和 Agent 筛选，也可以列出什么都没交出的召回。一次召回的页面显示每一项现在在库中的样子：条目、会话、线索，或者带摘录的过往消息，带链接，或者它之后已被遗忘；还有它的层、分数，以及会话之后是否用上了它，和它回应的提示。条目的页面列出交出过它（任何一个版本）的召回，会话的页面在每次召回所在的那一轮显示它，这是通过检索索引找到的，不读取整个会话。中枢的页面显示每台设备的召回。
- **概览的查询。** 概览上的一切都来自派生表（`session`、`sync_log`、`raw_file`、`raw_chunk`）和索引，从不扫描 `event`。图表和最活跃的项目只通过 `(source, session_id, ts)` 索引统计近 30 天的可见事件，每个事件读一个索引条目（27 万个事件约 100 毫秒），只统计这段时间有活动的会话，再减去通过 `excluded_event` 找到的已遗忘事件；只要日期和每个来源的总数不变，结果就会被保留。Agent 的最新版本取自它最近五个会话的最新事件。有存储桶时，统计磁盘用量需要对每个镜像的帧文件做一次 stat，最多每分钟一次。
- **不能做什么。** 编辑或删除事件、原始镜像、条目或遗忘记录；在隐藏它的那次遗忘的页面之外显示被隐藏内容的任何文本（列表只显示遗忘记录的目标 id、原因和数量；审计日志只保存 id 和数量）；保存没有可见来源的条目；再次显示令牌；修改管理密码、已选定的用户名或其他安全设置；执行任意查询，或读取可见事件的镜像行以外的任何文件。
- **审计日志。** 来自界面的登录和失败尝试（每个客户端在每个时间窗口内合并为一条记录）、选定的用户名、令牌变更、被允许和被拒绝的 OAuth 客户端、被批准和被拒绝的设备、被吊销的授权、写入的条目、接受和拒绝的提议、遗忘与恢复和被结束的会话（操作者为主人的用户名，在 `origin ui` 中为 `local`），来自 CLI 的令牌、授权、用户名和密码变更（操作者 `cli`），中枢启动时生成或变更的密码（操作者 `hub`），以及设备和 Agent 通过中枢的 API 对自己的访问权限所做的操作（渠道 `api`，操作者为 `<username> / <agent>` 或设备的名称；见[访问](#access)），都会连同渠道、客户端地址和 user agent 一起追加到 `audit_log`。详情只含 id 和数量，从不包含文本、原因或密码，因此被隐藏的内容保持隐藏；触发器拒绝任何更新和删除。
- **在设备上：`origin ui`。** CLI 为它所在机器的库（`~/.origin` 或 `$ORIGIN_HOME`）提供同样的页面，只监听 `127.0.0.1`，端口默认为 7079，可用 `--port` 指定；它拒绝其他任何地址。它只响应 `Host` 为 `127.0.0.1:<port>` 或 `localhost:<port>` 的请求，以此防御 DNS 重绑定，并保留上面所说的响应头、请求体上限以及对每个 POST 的检查。这里没有密码，因此也没有要管理的令牌、设备、接入命令或管理会话：这些页面和调用在这里并不存在，中枢上要求最近输入过密码的操作在这里只需要会话。它能写入的与中枢的界面相同（`remember`、`correct`、接受和拒绝提议、预览之后的 `forget`，以及 `restore`），作者记为 `user@<device>`，审计日志中的操作者为 `local`。在已接入中枢的设备上，每次写入之后都会在后台与中枢同步，与 `origin correct` 和 `origin forget` 之后一样；概览会显示中枢、设备上次与它完成同步的时间（保存在 `setting` 中），以及 `origin ui` 的上一次同步是否失败。它启动时会在后台归档设备上 Agent 的会话，和 `origin sync --local` 一样，并像 `origin mcp` 那样在各个写事务之间处理请求，让界面显示 Agent 最近写下的内容；停止它时不会等待归档结束，下一次同步会从停下的地方接着做。中继没有可以显示的库，`origin ui` 拒绝在中继上运行。
- **登录 `origin ui`。** 它启动时打印一个带一次性密钥（32 个随机字节）的链接，并用平台自带的方式（`cmd /c start`、`open`、`xdg-open`）在默认浏览器中打开它，除非指定了 `--no-open`。交给浏览器的不是链接本身，而是一个跳转到该链接的文件，这个文件只有它的主人可读，并在退出时删除，因为机器上的其他用户能读到进程的命令行。密钥只能使用一次，须在 5 分钟内使用，并且只在这个进程中有效，进程只保存它的哈希。在它运行的终端里按 Enter，会以同样的方式打印并打开一个新链接，之前的链接无论是否用过都会失效；只有标准输入是终端时才会读取它，从不读取管道或文件。密钥被兑换成一个会话，响应随即重定向到 `/admin/`，所以密钥不会留在地址栏和 referrer 中。会话只存在于这个进程的内存中，从不写入 `admin_session`：它在 `origin ui` 停止、退出登录或满 12 小时后结束，其他任何 server 都不接受它，包括同一个库上中枢的管理界面。它的 cookie 是 `origin-ui`（HttpOnly、SameSite=Lax，路径 `/admin`）：使用自己的名称，因为浏览器在同一主机的各个端口之间共享 cookie；没有 `Secure` 属性或 `__Host-` 前缀，因为 Safari 在纯 http 的回环地址上会丢弃这样的 cookie；用 Lax，因为从文件打开链接算作跨站请求。

## 待解决的问题 {#open-questions}

- **低成本的认知。** 用户谈到自己时，Agent 写入认知条目，它推断出的内容则提议出来，交给本人接受或拒绝。读一天或一条线索、提议值得保留的内容，是 Origin 之外的 Agent 的工作，Origin 不调用模型（见[提议](#proposals)）。尚未设计的有：这样的 Agent 如何从本人拒绝的内容中学习，让之后提议得更好，因为被拒绝的提议已被遗忘，Agent 看不到它。
- **与原生记忆互通。** Origin 单向导入 Claude Code、ZCode 和 Grok Build 的记忆（见[原生记忆](#native-memories)）。尚未设计的有：把条目写回 Agent 的记忆文件，以及导入 Codex 的记忆（启用后，它在 `~/.codex/memories/` 下自行合并的摘要）；Cursor 已不再在磁盘上保存记忆。
- **召回的质量与范围。** 召回匹配的是词，所以会漏掉用别的说法或别的语言表达同一件事的条目或消息，也仍会交出一些与提示只有常见词相同的内容；它只按提示中权重最高的六个词查找过往消息，每个词只看含有它的最新消息，所以可能漏掉一条更早但更匹配的消息（见[召回](#recall)）。如何根据召回记录和 Agent 之后用上了什么来评判召回的内容，还没有设计；在不拖慢 Agent 处理提示的前提下，从中枢召回其他设备写下的条目，也还没有设计。
- **变更通知。** Claude Code 和 Codex 通过它们的 hook 告诉 Origin 一轮何时结束，所以它们会话的行在写下几秒之后就会到达（见[实时采集](#live-ingestion)）；`origin mcp` 也在 Agent 运行期间每分钟比较一次文件的大小和时间来查看新的记录行，并在 Agent 离开时再同步一次，所以只要设备上的 Agent 使用 Origin，就不需要定时任务。尚待解决的是：没有这类 hook 的 Agent，即 Cursor、ZCode 和 Grok Build，以及人自己的来源，只能靠查看发现，所以在 Agent 运行 `origin mcp` 期间，它们的行最多要等一分钟；完全不使用 Origin 的 Agent 写下的行、没有设置 hook（或者在 Codex 中尚未信任 hook）的 Agent 写下的行，以及 Agent 直接杀掉 server 之后写下的行，要等到下一个 Agent、hook 或 `origin sync`；对这些情况，改为监听文件而不是每分钟查看可以缩短延迟，但文件监听在某些平台上并不可靠。
- **中继与 Agent 的清理。** 中继不保留尚未发送的内容的副本。如果它的中枢无法连接的时间超过了某个 Agent 保留记录的时间，这些会话就会丢失。中继会在那之前发出警告（见[中继](#relays)），但无法阻止它发生：为面临删除的记录保留副本尚未设计。目前只知道 Claude Code 的保留期限，而且只读取它的用户设置，不读取优先级更高的托管设置；其他 Agent 只在一周没有同步之后才会收到警告。
- **用过时的版本恢复。** 设备按它持有的条目版本判断规则 3。当另一个库在中枢上纠正了设备的某个条目时，一次恢复可能让设备继续隐藏这个条目，而中枢显示它，直到之后又有遗忘或恢复涉及它。把条目下发给设备，或者把中枢的判断与遗忘覆盖的内容分开发送，可以解决这个问题；两者都尚未设计。
- **擦除。** 遗忘是隐藏，恢复会把内容带回，所以原始行仍保留在磁盘上、备份中和中枢的存储桶中。显式擦除被遗忘的内容——有它自己的记录和限制（擦除之后无法恢复）——尚未设计。
- **通行密钥。** 主人用用户名和密码登录；改用通行密钥（WebAuthn）登录，并以此批准 Agent 和设备，尚未设计。
- **中枢的存储后端。** 中枢可以把原始镜像中已封存的帧——它的大部分数据——保存在兼容 S3 的存储桶中，其余部分留在自己的磁盘上：开放尾部和 SQLite 数据库。尚未设计的有：把帧从存储桶移回磁盘或移到另一个存储桶，不阻塞中枢的帧传输方式，以及为一块磁盘装不下的中枢改用 PostgreSQL 保存库。
