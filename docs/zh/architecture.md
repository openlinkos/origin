## 问题 {#problem}

开发者越来越多地同时使用多个 AI Agent：Claude Code、Codex、Cursor、ZCode、Grok Build。每个 Agent 都有自己的记忆，范围限定在一个仓库、一台机器或一个云端账户。换一个工具或项目，就得从零开始。这些记忆难以查看，难以纠正，其他 Agent 看不到，还常常被悄悄清除（例如 Claude Code 默认在 30 天后删除本地会话记录）。

与此同时，这些 Agent 都会把纯文本、可解析的会话记录写到本地磁盘，也都能与本地的 [MCP](https://modelcontextprotocol.io) server 通信。Origin 正是建立在这两点之上：它把本机所有 Agent 会话归档进同一个本地库，再通过同一个 MCP server 把这个库提供给每个 Agent。

长远的方向，是一个长期陪伴一个人的 AI：记忆、知识以及对这个人的理解，都能跨越工具和模型代际延续下去。Origin 从这个核心做起。

## 范围 {#scope}

**当前目标——一份通过 MCP 提供的跨 Agent 个人记忆：**

- 把 Claude Code、Codex、Cursor、ZCode、Grok Build 的本地会话归档进同一个只追加的库。
- 把 Agent 为自己保存的记忆（Claude Code、ZCode 和 Grok Build 的记忆文件）导入为条目，让一个 Agent 记住的内容也能到达其他 Agent。
- 让任何 Agent 都能通过 MCP 检索归档、浏览时间线、把任何回答展开到它的原始来源，并记录持久的条目（记忆 / 知识 / 认知）。
- 让人通过 `origin` CLI 或管理界面查看、纠正和遗忘条目，无论是在自己的中枢上，还是用 `origin ui` 在自己的机器上；遗忘必须持久生效，直到这个人恢复他遗忘的内容。
- 一个人常常在多台机器上运行 Agent（笔记本、服务器、云端 Agent）。每台设备都保有一份完整的、属于自己的记忆；可选的自托管**个人中枢**把每台设备写下的内容汇集到一个库中，让任何地方的 Agent 都能找到。磁盘空间不多的机器也可以改为中枢的**中继**（relay），它不保有自己的记忆。

达成目标的标志是：在你任何一台机器上，从任何一个已接入的 Agent 问“上周在项目 X 里我决定了什么，为什么？”，都能得到附带来源的回答，而且被遗忘的条目除非你恢复它，否则永远不会再回来。

**目前明确不做：** 多租户托管（Origin 只服务一个人，每个人运行自己的一份）、由本项目运营的托管服务、端到端加密、设备之间互相拉取对方的数据、不经过中枢的点对点同步、实时协作、自己的中枢或机器上供主人使用的管理界面之外的任何 Web 界面（没有公开页面、没有分享、没有多账户）、屏幕 / 邮件 / 浏览器采集、知识图谱、向量检索、主动提醒，以及任何对模型 API 的调用。

## 记忆、知识与认知 {#memory-knowledge-and-cognition}

Origin 区分三类持久条目。每个条目都带有自己的来源，并且可以被纠正或遗忘。

| 类型 | 含义 | 示例 |
|---|---|---|
| `memory` | 发生过什么（情景记忆） | “10 月 20 日，为了保持代码简单，我们决定在首个版本发布前不做 schema 版本管理。” |
| `knowledge` | 稳定的事实与关系 | “项目 A 依赖库 B。” |
| `cognition` | 关于这个人的模型：偏好、方法、目标、边界 | “偏好不带署名 trailer 的提交信息。” |

## 核心对象 {#core-objects}

| 对象 | 含义 | 关键字段 |
|---|---|---|
| **Source**（来源） | 某个 Agent 的适配器：`claude-code`、`codex`、`cursor`、`zcode`、`grok` | id、Agent 版本、发现根目录 |
| **Raw**（原始镜像） | 原始记录文件的只追加镜像，或适配器从数据库写出的记录的只追加镜像，以 zstd 帧存储 | 来源、原始路径、代次、字节 / 行游标、尾部哈希（生成的来源存的是它的令牌）、已封存的帧 |
| **Event**（事件） | 规范化后的对话事件：用户消息、助手消息、工具调用、工具结果；或者 Agent 保存的某个记忆文件的一个版本（见[原生记忆](#native-memories)） | id、来源、会话、时间戳、项目、cwd、git 分支、角色、类型、正文、原始定位 |
| **Entry**（条目） | 一条持久的 `memory` / `knowledge` / `cognition` 陈述 | id（`ent_…`）、类型、正文、置信度、作者、项目、来源（事件 id + 引文）、supersedes、root（它的第一个版本）、valid_from / valid_to、created_at、origin（写入它的库）；状态（`active` / `superseded` / `forgotten`）由推导得出，从不存储；`imported`（这个版本是否派生自原生记忆）同样如此 |
| **Recall**（召回） | Origin 在会话开始时或随提示，不经询问交给 Agent 的内容（见[召回](#recall)） | id（`rcl_…`）、时间、origin（进行召回的库）、Agent、会话、时机、项目和目录、提示的哈希、预算和 token 数；每一项的排名、层、条目或会话 id、分数和大小 |
| **Tombstone**（遗忘记录） | 一次遗忘或一次恢复的记录 | id（`tmb_…`）、目标（遗忘的目标是条目或事件 id；恢复的目标是一次遗忘的 id）、原因、作者（已知时）、时间、origin（创建它的库）；对遗忘而言，还有它在每个库中覆盖的内容 |

## 数据流 {#data-flow}

```
agent session logs on disk ──scan──▶ Raw (append-only mirror)
                                        │ deterministic adapter parsing (no LLM)
                                        ▼
                                  Event store (SQLite + FTS5) ◀── Entries · Tombstones
                                        │
 agents ◀── MCP (stdio): brief · search · timeline · get · sources · remember · correct · forget
 agents ◀── hooks: origin recall (session start · prompt): a brief, and the entries a prompt matches
 people ◀── CLI `origin`: sync · status · timeline · search · show · entries · correct · forget · forgotten · restore · recall · recalls
 people ◀── admin UI (hub, /admin): overview · timeline · search · entries · remember · correct · forget · restore · tokens
 people ◀── origin ui (device, 127.0.0.1): overview · timeline · search · entries · remember · correct · forget · restore
```

使用个人中枢时，每台设备都保有一份完整的、属于自己的库，离线时也照常可用。它把原始镜像发送给中枢（由中枢用同样的适配器解析），也把自己写下的条目和遗忘记录（遗忘与恢复）发送给中枢；它从中枢收到的只有遗忘记录。设备上的 Agent 使用本地的 `origin mcp`，它根据设备自己的库作答，并合并中枢的回答；云端 Agent 则使用中枢的 HTTP 端点：

```
agents on A ──▶ origin mcp ──▶ store A ──raw mirrors · entries · tombstones──▶ ┐
                    │             ▲                                             │
                    │             └──────────────── tombstones ─────────────────┤
                    └──────── reads, merged (MCP over HTTP) ───────────────────▶ hub store ◀── MCP over HTTP ── cloud agents
agents on B ──▶ origin mcp ──▶ store B ── (as for device A) ───────────────────▶ ┘
```

中继（见[中继](#relays)）没有可以据以作答的库。它直接从 Agent 的记录文件读取新增的行，发送给中枢；它的 `origin mcp` 把每一次工具调用都交给中枢：

```
agent logs on C ──new complete lines, read after C's cursors──────────────────▶ hub store
agents on C ──▶ origin mcp ──── every tool call (MCP over HTTP) ──────────────▶ hub store
```

## 不变量 {#invariants}

这些是产品层面的保证。每一条都必须有测试覆盖，代码注释按编号引用它们。

1. **溯源。** 每个条目至少引用一个事件；每个事件都指向某个 Raw 文件中的某一行。任何回答都能一路展开到原文。中继不保存事件，所以经由它写入的内容在它的中枢上校验，溯源也在中枢上解析。
2. **有记录的遗忘。** 执行 `forget` 之后，它的目标及其连带内容立即从该库的所有查询中消失，并在这次遗忘到达其他每个库时从那里消失，而且一直不再出现，直到主人恢复这次遗忘：重新同步、之后才到达的版本和副本，以及遗忘记录到达的先后顺序，都不会让它们回来。每一次遗忘和每一次恢复都连同原因保存为一条记录；遗忘记录会到达每一个库，并且只增不减。
3. **只追加。** Raw 镜像和事件永远不会被改写：镜像的内容（即其未压缩的字节）只会增长，一行一旦采集就永远不变，无论它以何种形式存储（见[原始镜像](#raw-mirrors)）。条目通过取代（`supersedes`）来变更，从不原地修改。
4. **你的数据，留在你的机器上。** 所有数据都存放在你控制的机器上：你的各台设备上的 `~/.origin/`，以及可选的你自己的中枢，如果你为它配置了存放原始镜像的存储桶，也包括这个存储桶。Origin 从不调用第三方服务；唯一的网络流量发生在你的设备和你的中枢之间，以及你的中枢和它的存储桶之间。
5. **单一入口。** 无论来自哪个界面，每一次读写都经过同一组 core 操作：Agent 使用 MCP（所在设备的 `origin mcp`，或中枢的 HTTP 端点）；人使用 CLI 或管理界面（自己中枢上的，或设备上的 `origin ui`）。写入发生在发起它的那个库中——在设备上就是先写入设备自己的库（中继没有自己的库，所以它的写入发生在它的中枢上）——再由复制通过同样的操作应用到其他库。中枢的复制 API 在你自己的各个库之间传输原始镜像、条目、遗忘记录和召回，它既不是 Agent 的入口，也不是人的入口。

## 设计原则 {#design-principles}

- **内核不含 LLM。** Origin 从不调用模型 API。它只负责归档、规范化、建立索引和存储。分析发生在提问的那个 Agent 里——它本身就是一个能力很强的模型。Agent 通过 MCP `remember` 保存它学到的东西；人通过 CLI 或管理界面纠正和遗忘。如果将来需要周期性的整合，它会作为无头的编码 Agent 任务运行（例如 `claude -p`），而不是直接集成模型 API。这是当前的立场；如果评估表明它力有不逮，尤其是在认知层，可以重新考虑。
- **确定、容错的适配器。** 每个来源都有一个纯粹、确定性的解析器。Agent 的记录格式变化频繁，所以适配器会记录 Agent 版本，跳过无法解析的行并统计失败次数，绝不中止采集。
- **以 MCP 作为互通点。** MCP 是所有目标 Agent 唯一共有的接口。其中几个 Agent 还会读取 Claude Code 的 MCP 配置，所以一次注册就能覆盖不止一个 Agent。
- **小而保守的管理界面。** 管理界面，无论是中枢上的，还是设备上的 `origin ui`，都只供它的主人使用。页面在服务器端由一个对每个值都做转义的模板渲染，外加一点可选的脚本。它的样式表、字体和图标来自 OpenLinkOS 设计系统（`@openlinkos/ui`），在构建时复制进这个包；不从别处加载任何东西，也没有打包工具。CLI 能做的它都能做，但不做任何会破坏不变量的事：不原地编辑或删除；被隐藏的文本只出现在隐藏它的那次遗忘自己的页面上，只给它的主人看，主人可以在那里恢复它。
- **小而可运行的增量。** 每个来源适配器都单独交付、单独可用；设计只深入到当前增量所需的程度。

## 包 {#packages}

pnpm workspace，TypeScript（strict、ESM、NodeNext），Node.js ≥ 22.16（需要 `node:zlib` 的 zstd 和 `node:sqlite` 的在线备份）。`core`、`adapters` 和 `admin` 只使用 Node 内置模块；`mcp` 依赖官方的 [MCP TypeScript SDK](https://github.com/modelcontextprotocol/typescript-sdk) 和 zod。中枢及其管理界面使用 Node 内置的 `node:http`。

| 包 | 路径 | 职责 | 依赖 |
|---|---|---|---|
| `@openlinkos/origin-core` | `packages/core` | 存储、schema 与迁移、采集（本地与远程）、中继、条目、遗忘、令牌、管理密码与会话、审计日志、查询 | — |
| `@openlinkos/origin-adapters` | `packages/adapters` | 每个来源一个确定性解析器 | core |
| `@openlinkos/origin-mcp` | `packages/mcp` | MCP 工具；基于 stdio 和无状态 HTTP 的 server，已接入中枢的设备上的 server（它把中枢的回答合并进自己的回答），以及中继上的 server（它把每一次工具调用都交给中枢） | core |
| `@openlinkos/origin-admin` | `packages/admin` | 管理界面，供中枢和 `origin ui` 使用：服务器端渲染的页面、JSON API 及其静态资源 | core |
| `@openlinkos/origin` | `packages/cli` | `origin` 命令，包括 `origin mcp`、`origin serve`（中枢）、`origin ui`、设备或中继与中枢之间的同步，以及中枢的 S3 客户端 | core, adapters, mcp, admin |

五个包以同一个版本号一起发布到 npm；用户安装 `@openlinkos/origin`，其余几个随之安装。1.0 之前，另外四个包属于内部实现，它们的 API 可能在任何版本中改变。

`core` 不得依赖任何其他包，`mcp` 和 `admin` 都不得依赖 `adapters`：CLI 以回调的形式把采集注入各个 server，中枢和 `origin ui` 的 HTTP server 位于 CLI 中，并由它挂载管理界面的请求处理函数。适配器实现 `core` 中的 `SourceAdapter` 接口：

```ts
interface SourceAdapter {
  id: string; // 'claude-code' | 'codex' | 'cursor' | 'zcode' | 'grok'
  displayName: string;
  version(): string | null; // agent version, if known
  discover(): Promise<SourceFile[]>; // { absPath, relPath, compression?: 'zstd', generated? }
  parseLine(line: string, ctx: ParseContext): ParsedLine | null; // deterministic; throws on malformed input
}
// ctx: { absPath, relPath, lineNo, fileMtimeMs, readLine(n) }; readLine returns an earlier line of
// the same file as ingested, for an adapter that needs, say, a file's first line on a hub.
// generated: { token, mtimeMs, next(last, maxBytes) } for a source that is not a log file, such as
// a database: the adapter writes the lines (see Generated sources).
```

## 存储 {#storage}

```
~/.origin/                 # or $ORIGIN_HOME
├── origin.db              # SQLite (WAL)
└── raw/<source>/...       # append-only mirrors of the original log files:
                           #   <mirror>.zst (sealed zstd frames) and <mirror>.tail (open tail)

s3://<bucket>/<prefix>/    # optionally, on a hub: its sealed frames, one object per frame
└── <mirror>.zst/<offset>
```

| 表 | 内容 |
|---|---|
| `raw_file` | 每个镜像文件代次一行，带有它的采集游标 |
| `raw_chunk` | 每个镜像已封存的帧：首行行号、行数、在内容中和在 `.zst` 文件中的偏移量与长度。触发器拒绝更新和删除 |
| `event` | 规范化后的事件，以它们到达本库的次序（`seq`）为键 |
| `event_block` | 每一块 4,096 个连续到达的事件中最晚的时间戳，以及到这一块为止最晚的时间戳（派生数据，由触发器维护） |
| `message_fts`, `event_fts`, `event_cjk` | 事件的检索索引：`message` 事件的完整 trigram 索引、只记录哪些事件含有每个 trigram 的全部事件索引，以及 CJK 二元组索引（见[检索与时间线](#search-and-timeline)） |
| `session` | 基于可见事件的逐会话聚合（派生数据，可重建），以及取自带有标题的行的会话标题，并记录它是否由用户给出 |
| `sync_log` | 每次同步运行一行 |
| `entry`, `entry_source`, `entry_fts` | 条目、条目引用的事件（含引文），以及条目的 FTS5 索引。每个版本记录它的 `root`（第一个版本，写入时确定）和它的 `origin` |
| `imported_entry` | 本库从原生记忆派生出的条目版本（见[原生记忆](#native-memories)），它们从不发送给其他库 |
| `tombstone`, `forgotten_entry`, `excluded_event` | 遗忘与恢复，每条都有一个全局 id（`tmb_` 加随机十六进制，与 `ent_` id 相同）和它的 `origin`；以及本库中被隐藏的内容，每个被隐藏的条目和事件都记有一次覆盖它的、生效中的遗忘 |
| `tombstone_effect` | 每次遗忘在本库中覆盖的内容，一个条目或事件可以被多次遗忘覆盖：按它的目标经规则得出、按它的中枢所列、按发送它的设备所报，或按规则 3（见[遗忘](#forgetting)） |
| `tombstone_meta` | 每条遗忘记录的作者（已知时） |
| `recall`, `recall_item` | 本库进行的每一次召回，以及它交出了什么，只记 id，从不记文本（见[召回](#recall)）；触发器拒绝更新和删除 |
| `change_log` | 本库写入或收到的条目和遗忘记录的只追加序列（序号、类型、id、origin、时间），由触发器填写；触发器拒绝任何更新和删除。复制游标指向这个序列 |
| `api_token` | 中枢访问令牌：名称（设备的令牌即设备名）和 SHA-256 哈希，从不保存令牌本身 |
| `setting` | 少量键值状态，只属于各自的库，从不复制：库的名称和模式、设备的复制游标及其上次与中枢同步的时间、中继上每个来源文件的一个游标，以及中枢上管理密码的 scrypt 哈希和存放其已封存帧的存储桶（如果有） |
| `admin_session` | 中枢管理界面的会话：会话 id 的哈希、它的 CSRF 令牌和各个时间戳（`origin ui` 把会话保存在内存中） |
| `audit_log` | 管理操作的只追加记录，只含 id 和数量，从不包含内容；触发器拒绝任何更新和删除 |

- 存储使用 Node 内置的 `node:sqlite`，因此没有需要编译的原生模块。多个进程可以共享同一个数据库（CLI，以及每个 Agent 会话各一个 MCP server）；WAL 模式和 busy timeout 负责处理这种情况。
- `session` 是派生数据，可以从 `event` 重建；按来源的汇总（`origin status`、管理界面的概览）从它读取。检索索引也是派生数据，由触发器保持同步：`message_fts` 和 `event_fts` 是外部内容（external-content）表（`message_fts` 的内容是消息事件的视图 `event_message`），`event_cjk` 没有内容表，通过核心在每个连接上注册的函数填写。`rebuildSearchIndexes()` 从事件和条目重建所有这些索引以及 `event_block`。
- **到达次序。** 事件以及随之的检索索引都以 `seq` 为键，即事件到达本库的次序：FTS5 保存相邻键之间的差值，所以连续的键能让索引保持很小。同步时按修改时间从旧到新采集找到的文件，设备也按最后更新的先后把文件推送给中枢，所以到达次序尽可能地跟随时间；但它并不是时间次序，例如中枢可能在收到较新的会话很久之后，才收到某台设备的旧会话。因此，一个触发器为每一块 4,096 个连续到达的事件记录其中最晚的时间戳，以及到这一块为止最晚的时间戳（`event_block`）。按从新到旧的查询从最后到达的事件开始读取索引，分成几条由连续的块组成的链（某一块比它之前的链新一天以上时，就开始一条新链），总是从未读部分可能含有最新事件的那条链读取，一旦没有链可能含有比所需事件更新的事件，就立即停止。一个窄的 `(seq, ts)` 索引无需读取事件就能给出它的时间戳。
- **大小。** 在一个有两百万个事件、平均每个事件约 800 个字符文本的库上，数据库每个事件约占 2,550 字节：事件本身 1,360，它的索引 205，`event_fts` 500，`message_fts` 460，`event_cjk` 20。而所有事件的完整 trigram 索引单独就要每个事件约 2,350 字节。
- **备份。** `origin backup <dir>` 先用 SQLite 的在线备份一次性复制数据库，即使其他进程正在写入，也能得到一致的快照；然后按这个快照记录的状态复制原始镜像：该目录中还没有的已封存帧，以及每个开放尾部（续写；如果此后已有帧从它封存，则重新写入）。尾部从正在使用的库中读取，那里它可能已经被封存，但镜像的内容只会增长，所以读到的内容相同（见[备份](guide/privacy.md#backing-up)）。如果中枢把已封存的帧保存在存储桶中，这些帧会被复制进备份，并按磁盘上的布局排列，所以备份从不依赖存储桶；备份中的数据库随后不再记录这个存储桶。
- **中继的库**没有 `raw/` 目录，它的数据库中也没有事件、镜像文件、条目或遗忘记录：只有 `setting`（它的名称、模式和游标）和它的同步日志（见[中继](#relays)）。
- **库的名称。** 每个库都有一个名称，保存在 `setting` 中：在设备上就是设备名，中枢则把自己的库叫作 `hub`。条目和遗忘记录把写入它们的库的名称记为 `origin`，设备也以自己库的名称为中枢所知。库在第一次需要名称时被命名：`origin serve` 把它命名为 `hub`；其他命令使用 `ORIGIN_DEVICE` 或主机名。库一旦写入过条目或遗忘记录，就保持这个名称不变；它从原生记忆派生出的条目不算在内，因为它从不发送这些条目。
- **格式版本。** 数据库记录库的格式版本，打开一个较旧的库时会就地把它升级到最新版本；较新的 Origin 写过的库会被拒绝（见[迁移](#migrations)）。由已有表推导出的表，只要缺少相应的行，就会在打开数据库时据已有的表补全：遗忘记录如果在写入时没有 `tombstone_effect` 和 `tombstone_meta`（由 Origin 0.1 写下，或由仍在运行的旧版本进程写下），就依据 `forgotten_entry`、`excluded_event` 和规则补上。数据库、`raw/` 下的镜像，以及中枢存储桶中已封存的帧是一个整体：不要只删除或替换其中之一。

### 原始镜像 {#raw-mirrors}

镜像保存一个文件某一代次已采集的字节（对生成的来源，是它的适配器写出的行），即它的*内容*，而且只包含完整的行。它以压缩形式存储在两个以镜像命名的文件中：

- `<mirror>.zst`：**已封存的帧**，彼此独立的 zstd 帧（级别 3，带校验和），每帧包含若干完整的行，依次追加。`raw_chunk` 记录每一帧：首行行号、行数、在内容中的偏移量和长度，以及在文件中的偏移量和长度。读取一行只需解压包含它的那一帧。
- `<mirror>.tail`：**开放尾部**，最新的若干行，未压缩。

内容就是解压后的各帧，后接尾部，二者都以数据库的记录为准（帧以 `raw_chunk` 为准，结尾以 `raw_file.bytes_ingested` 为准）；对 `raw/` 的每一次读写都经过同一个模块（`core` 中的 `mirror.ts`）及其帧存储，帧存储把已封存的帧保存在 `<mirror>.zst` 中，或保存在中枢的存储桶中（见[帧存储](#frame-stores)）。行号、游标、重写代次、尾部哈希和事件 id 都以内容为准，就像对文件的普通副本一样。

- **封存。** 尾部不到 1 MiB 时，新的行追加到尾部。如果某次追加会让尾部达到或超过 1 MiB，就改为把尾部和新的行一起封存：它们被切成若干帧，每一帧在内容达到 1 MiB 后的第一个换行处结束（更长的行单独占一帧，最后不足半 MiB 的部分并入前一帧），这些帧追加到 `<mirror>.zst` 并刷到磁盘，`raw_chunk` 在推进游标的同一事务中记录它们。这个事务提交、预写日志刷到磁盘之后，再用一个很短的事务清空尾部。一个文件一小时没有增长，多半已经结束，所以它的尾部也会被封存，无论大小：在设备上由该来源的下一次同步完成，在中枢上由每 10 分钟一次的检查完成；之后追加的行会开始一个新的尾部。
- **这里的“只追加”是什么意思。** 内容只会增长，一行的字节永远不变（不变量 3）。在磁盘上，`<mirror>.zst` 只会增长，其中的帧永远不会被改写（`raw_chunk` 拒绝更新和删除）；`<mirror>.tail` 只会被追加，唯一的例外是其中的行进入帧之后它会被清空。封存把行从尾部移入帧，而不改变内容。
- **崩溃安全。** 两个文件中超出数据库记录的字节都不属于镜像：读取时永远不会读到它们，对这个镜像的下一次写入会在追加之前丢弃它们。如果在帧写入之后、事务提交之前崩溃，会留下一个没有记录的帧；它会被丢弃，而那些行仍在尾部，会再次被封存。如果在提交之后、尾部清空之前崩溃，尾部中会留下已经进入帧的行；数据库记录的尾部为空，所以它们会被忽略，随后被丢弃。两种情况都不会丢失或重复任何一行。如果某个文件比数据库记录的短，说明数据已经丢失，Origin 会拒绝向这个镜像追加，而不是破坏来源追溯（不变量 1）。如果读取时发现尾部被另一个进程的封存清空，就重新读取。
- **大小。** 在 171 MiB 按真实形态生成的 Claude Code 合成记录上（大型工具结果、约占四分之一字节的 base64 截图、中英文文本），文件停止增长之后，镜像占 35 MiB（4.9 倍；刚导入时每个文件都还有开放尾部，占 52 MiB）。采集耗时增加约 15%，随机读取一行原始记录平均需要 1.5 ms，而扫描整个未压缩镜像需要 6.8 ms。

### 帧存储 {#frame-stores}

已封存的帧只写一次、永不改变，很适合对象存储，而在中枢上它们占据了大部分空间。帧保存在哪里由*帧存储*决定：`mirror.ts` 决定帧是什么并在 `raw_chunk` 中记录它们，帧存储则按 `raw_chunk` 记录的偏移量保存它们的字节，就好像它们被依次追加到每个镜像的一个文件中。一个库使用以下两种之一（`core` 中的 `frames.ts`）：

- **在磁盘上**：默认方式，也是设备唯一使用的方式：镜像的帧就是上文所述的 `<mirror>.zst`，逐字节相同。
- **在存储桶中**：用于配置了存储桶的中枢（见[个人中枢](guide/hub.md)）：每帧一个对象，通过一个只有两个同步操作的对象存储接口，`put(key, bytes)` 和 `get(key)`。`core` 不发起任何网络请求，所以对象存储由 CLI 提供：一个面向 MinIO 或任何其他兼容 S3 API 的存储的 S3 客户端，用 `node:crypto` 计算 AWS Signature Version 4，使用内置的 `fetch`，支持路径式（path-style）和虚拟主机式（virtual-hosted）URL，只对单个对象执行 `PUT` 和 `GET`。

无论哪种方式，开放尾部都留在磁盘上：每个尾部都不到 1 MiB，仍在增长，并在封存后被清空。

- **键。** 镜像的帧中偏移量为 `<offset>` 的那一帧是对象 `<prefix>/<mirror>.zst/<offset>`，路径各段之间用 `/` 分隔，偏移量至少写成 12 位十进制数，例如 `hub/devices/laptop/claude-code/proj/a.jsonl.zst/000000412345`。键由 `raw_chunk` 的记录推导而来，偏移量也就是 `<mirror>.zst` 中的偏移量，所以无论帧由哪种存储保存，数据库都完全相同：不需要修改 schema，而且一个镜像较早的帧可以在磁盘上、较新的帧在存储桶中。
- **崩溃安全。** 帧在记录它的事务提交之前上传，尾部则在那之后才被清空，与磁盘上的做法相同。如果在上传之后、提交之前崩溃，会留下一个没有任何记录的对象：没有读取会请求它，它的那些行仍在尾部，下一次封存会在同一个偏移量、也就是同一个键下写入这些行的帧，从而替换它。对象永远不会被删除（不变量 3），同一个键只有在替换这样的对象时才会被再次写入。无法上传的帧会让它所在的事务失败，所以它的行留在尾部，设备的推送会被拒绝，直到存储桶恢复。`<mirror>.zst` 中超出数据库记录的字节——中枢使用存储桶之前、一次从未提交的写入留在磁盘上的——会在下一帧写入存储桶之前被截掉，所以这个文件中永远只有数据库记录的帧。
- **读取。** 一帧先从内存读取，其次从 `<mirror>.zst` 读取（如果文件中有这一帧，即中枢使用存储桶之前封存的帧），最后从存储桶读取。中枢在内存中保留最近写入或读取的帧，最多 32 MiB：至少 32 帧，通常超过一百帧，因为一帧 1 MiB 的行压缩后只占 200 到 300 KiB。这足以覆盖那些被反复读取的帧，例如设备正在推送的镜像的最新一帧，下一次推送会读取它来计算尾部哈希。存储桶中没有的帧就是缺失的，它的行也是缺失的（不变量 1）；无法连接存储桶则是一个错误，绝不会被当作缺失的行，因此适配器解析推送来的行时，绝不会拿不到它所请求的前面的行。
- **同步传输。** `node:sqlite` 是同步的，而帧在写事务中写入和读取（封存时，以及适配器解析设备推送时调用 `readLine`），所以对象存储也是同步的。S3 客户端在一个 worker 线程中运行 `fetch`：调用线程把请求发给它，用 `Atomics.wait` 阻塞，直到 worker 发回响应，再用 `receiveMessageOnPort` 取出响应。每个请求都有超时（默认 30 秒）；因网络错误而失败，或被存储回答为繁忙或服务器错误的请求，最多尝试三次。代价是：每次传输期间中枢的事件循环都处于停顿状态，而在封存时，中枢在传输期间一直持有写锁。在局域网中一帧只需几毫秒（向同一台机器上的测试服务器上传 256 KiB 约需 2 ms，其中 worker 线程带来的开销约 0.15 ms），但缓慢或无法连接的存储桶会让中枢在每个请求上停顿，最长可达超时时间。中枢只在推送来的数据块让尾部封存时上传一两帧，并每 10 分钟为每个空闲的镜像上传一帧。
- **库使用的存储桶。** 库第一次使用某个存储桶和前缀时，会把它们记录在 `setting` 中（`raw.bucket`）。此后它拒绝任何其他存储桶，`origin serve` 没有它就拒绝启动，其他命令则从环境变量中读取它；如果它们需要存储桶中的帧而存储桶没有配置，就会失败，并给出需要设置什么的提示。端点不会被记录，所以可以改变。请为每个库使用各自的前缀：两个库如果写入同样的键，就会相互替换对方的帧。
- **把帧移入存储桶。** 中枢使用存储桶之前封存的帧仍留在 `<mirror>.zst` 中，并从那里读取。`origin raw upload` 把它们按上述的键上传，所以再次运行、或在中断之后运行，都不会重复上传任何东西：每一帧在上传前都会被检查（它必须能带着校验和解压成 `raw_chunk` 记录的大小），上传后再从存储桶读回校验；存储桶中已有相同字节的帧则保持不变。它在事务之外运行，所以不像中枢那样每次传输都阻塞等待：它从调用线程发出请求，默认一次传 8 帧，可用 `--concurrency` 调整。某一帧校验失败时，会报告该帧并保留存放它的文件，其他镜像照常继续；出现会让每一帧都失败的错误（例如存储桶无法访问）之后，不再开始新的帧。它列出每一帧都已在存储桶中校验过的 `<mirror>.zst` 文件，`--remove` 会在一个文件的所有帧都校验过后立即删除它。这只是移动帧而不改变它们，所以每个镜像的内容保持不变（不变量 3）。它可以在中枢运行时执行。

### 迁移 {#migrations}

库把它的格式版本记录在数据库文件头中，即 `PRAGMA user_version`：SQLite 为应用程序保留了这个整数，在任何表存在之前就能读取它，它与它所描述的改动在同一个事务中写入，备份也会随数据库一起复制它。Origin 0.1.0 没有记录版本，所以没有版本的库如果有 0.1.0 的那些表，就是版本 1，即 0.1.0 的 schema，否则就是一个新库。打开一个库时（`core` 中的 `migrations.ts`），会把它升级到最新版本：

- **新库**在一个事务中得到当前的 schema 和最新的版本。
- **较旧的库**按顺序执行它缺少的每一个迁移，每个迁移各在一个自己的写事务（`BEGIN IMMEDIATE`）中执行，这个事务也记录它的版本。拿到锁之后会重新读取版本，所以当多个进程同时打开这个库时（CLI，每个 Agent 一个 MCP server），其中一个执行每个迁移，其他进程等待（最多 5 分钟），随后发现它已经完成。失败的迁移连同它的版本一起回滚，错误信息会指出是哪一个；它之前的迁移所做的改动保留，下次打开时会再次执行它。
- **较新的 Origin 写过的库**在其中任何内容改变之前就被拒绝，并提示升级。

迁移完成之后，schema 中的幂等语句会照常在每次打开时执行，所以新的表、索引、视图或触发器，只要已有数据不需要从中得到什么，就无需迁移即可出现。

| 版本 | 改动 |
|---|---|
| 1 | 首个发布版本 0.1.0 的 schema，不记录版本 |
| 2 | `session.title_manual`：会话的标题是否由用户给出 |
| 3 | 数据：Claude Code 会话的标题，取自已经镜像、但 0.1.0 跳过了的 `ai-title`、`custom-title` 和 `summary` 行。只重新解析含有这几个名称之一（`"ai-title"`、`"custom-title"`、`"summary"`）的行，在设备和中枢上都是如此（`raw/devices/<device>/claude-code/…`） |
| 4 | 数据：库在能读懂记忆流之前镜像下来的记忆流的事件和条目，比如 0.2 的中枢收到较新版本的设备发来的记忆流时就是这样。Claude Code、ZCode 和 Grok Build 在 `memory/` 下的镜像，每一行都会被解析，存下它的事件，并派生它的条目（见[原生记忆](#native-memories)） |

**什么时候需要迁移。** 除了已有数据不需要从中得到什么的新表、索引、视图或触发器之外，对库格式的任何改动都需要迁移：新增、重命名或删除列，修改约束，修改触发器或视图（`IF NOT EXISTS` 会保留旧的），需要为已有数据填写的派生行，或者因为适配器现在能从镜像的行中读出更多内容而需要重新解析这些行。*schema 迁移*就地修改表；*数据迁移*根据库中已有的内容（包括原始镜像）修改或填写行。两者都要保持不变量：原始镜像和事件永远不会被改写（不变量 3），被遗忘的内容保持被遗忘（不变量 2）。`core` 没有适配器，所以对于需要重新解析镜像中的行的数据迁移，由打开库的进程传入适配器；CLI 正是这样做的，并且在它执行第一个迁移之前，还会先设置好库的帧存储，以便中枢读取存储桶中的帧。

**编写迁移。** 在 `migrations.ts` 的 `MIGRATIONS` 中添加一个版本号为下一个版本的 `Migration`，把 `schema.ts` 改成新的结构，使新库和升级后的库最终完全相同，并在上表中添加它的一行。已经发布的迁移永远不再修改；修正就是一个新的迁移。请在它之前那个版本的库上测试它：测试从 0.1.0 的 schema（`packages/core/test/fixtures/schema-0.1.0.sql`）构建一个 0.1.0 的库，升级它，再把它的 schema 与新库的 schema 进行比较。

## 采集 {#ingestion}

`origin sync`（以及 MCP server，见下文）会运行每个适配器的 `discover()`。自上次采集以来大小和尾部都没有变化的文件会被跳过，不需要获取写锁。有变化的文件，其新增的行在 `BEGIN IMMEDIATE` 事务中采集，每个事务最多 1 MiB 的行（更长的单行独占一个事务），因此来自不同进程的并发同步会被串行化，绝不会把同样的字节采集两次；即使在导入大量积压数据时，也没有进程会长时间占用写锁：

1. **游标。** 每个 `raw_file` 行记录 `bytes_ingested`、`lines_ingested` 和 `tail_hash`（最后采集的 4 KB 的 SHA-256）。游标在写锁之下读取，并且只读取游标之后的字节。
2. **改写检测。** 如果文件变小了，或者尾部不再匹配，说明它是被改写而不是被追加。Origin 会开启一个新的*代次*，使用全新的镜像，并保持旧镜像完好无损（不变量 3）。
3. **只取完整行。** 截至最后一个换行符的字节会被追加到镜像中（见[原始镜像](#raw-mirrors)）；末尾不完整的行留待下一次同步。镜像的内容始终等于其代次已采集的字节，因此被中断的同步遗留在游标之后的字节，会在追加之前被丢弃（不变量 1）。
4. **解析与插入。** 每一行都经过 `parseLine`；失败只计数，不致命。事件以 `<source>:<native-id>[#<block-index>]` 为 id、用 `INSERT OR IGNORE` 插入，这使同步具有幂等性（不变量 3）。每个事件都保存它的镜像文件和行号（不变量 1）。记忆流中的一行还会产生一个条目的版本（见[原生记忆](#native-memories)）。
5. **收尾记录。** 受影响的会话被重新聚合，游标在同一个事务中前移，并由一行 `sync_log` 记录这次运行。一行也可能带有它所属会话的标题（`sessionTitle`）：最新的标题替换之前的标题，但 Agent 生成的标题永远不会替换用户给出的标题（`manualTitle`）。

**压缩的来源。** 适配器可以把文件标记为 `compression: 'zstd'`。Origin 随后使用 Node 内置的 zstd，采集并镜像解压后的内容，因此游标、行号和原始行的工作方式与普通文件相同。压缩文件只写入一次，所以自上次采集以来没有变化时会被跳过，并且每个压缩文件都在单个事务中采集。

**生成的来源。** 有些 Agent 把会话存在数据库里，并且原地修改其中的行：回复流式输出时会改，过了很久也还会改；或者把会话的标题保存在一个每一轮都重写的文件里（Grok Build 的 `summary.json`）。对这样的来源，适配器把它的每一路内容（例如一个会话）标记为 `generated`：Origin 不读文件，而是向适配器要已镜像的最后一行之后的行，每次最多约一个事务的量，一直要到没有为止，然后像文件的行一样镜像和采集它们。适配器在一条记录不会再变时（例如一条消息完成之后）才把它写出，而且只写一次，所以内容只会增长（不变量 3），也不需要检测改写；已镜像的最后一行告诉适配器从哪里接着写，它自己不保存任何状态。写出之后又改变的记录不会再写一次：它被镜像的那一行，就是它的事件所来自的版本（不变量 1）。每一路内容还有一个令牌，可能有新行时就会改变；令牌和游标存在一起，占用文件尾部哈希的位置，令牌没变的内容会被直接跳过，不去问适配器。中枢像接收其他镜像一样接收这些镜像，并用同一个适配器解析。

**多个进程。** CLI 和每个 Agent 会话各一个的 MCP server 可能同时使用同一个库。读操作从不等待写操作（WAL）。写操作最多等待写锁 10 秒（busy timeout）；由于同步只为有变化的文件获取写锁，并且每次只持有一个有上限的事务，所以即使另一个进程正在导入大量积压数据，一次同步或一次 `remember` 最多也只需等待大约一个这样的事务。每次检查点之后，预写日志会被截断到 64 MiB（`journal_size_limit`），所以大量导入不会留下几个 GB 的日志。

**在中继上**，本地不采集任何内容：每个文件新增的完整行以同样的方式读取（游标、改写检测、解压后的内容、生成的行），然后发送给中枢，由中枢按本节所述采集（见[中继](#relays)）。

### 原生记忆 {#native-memories}

Claude Code、ZCode 和 Grok Build 都维护自己的记忆：由 Agent 原地写入、改写和删除的 Markdown 文件，每个文件一条笔记，每个项目或工作区一个目录（各自的布局见 [sources.md](sources.md#native-memories)）。Origin 把它们单向导入为条目：只读取这些文件，从不写入，于是一个 Agent 记住的内容能到达所有 Agent，并且带着来源。

- **记忆流。** 每个记忆目录是一个[生成的来源](#ingestion)，即一条*记忆流*，镜像在它所属来源的 `memory/` 下（例如 Claude Code 某个项目的记忆流是 `memory/<cwd-slug>.jsonl`）。它的适配器为记忆文件的每个版本写出一行，保存整个文件，文件被删除时也写出一行：先按从旧到新的顺序，为自记忆流最后一行以来新出现或内容有变化的每个文件各写一行，再为每个已经消失的文件各写一行。一行保存文件名、`write` 或 `delete`、它的时间（文件的修改时间，或者发现删除的时间）、这些记忆所属的项目和工作目录（已知时），以及写出这一行之后目录的状态：每个文件最新一行的 id 和它内容的哈希，文件删除之后则没有哈希。适配器根据最后一行中的状态写出接下来的行，所以它自己不保存任何状态，内容也只会增长（不变量 3）。记忆流的令牌是它的文件的名称、大小和修改时间的摘要，所以没有变化的目录会被直接跳过，不读取任何文件。读取失败的文件保持原样，超过 256 KiB 的文件不计入。
- **事件。** 每一行是一个类型为 `memory` 的事件：正文是写入时的文件（删除时为空），并记下文件名和操作。它的 id `<source>:memory:<hash>` 是一个从该文件上一行串联而来的 SHA-256：取上一行的 id（文件的第一行则取记忆流的路径和文件名）、操作和内容的哈希。因此，同样的历史无论在哪里解析都得到同样的 id，而删除后又出现的文件会得到新的 id。记忆事件不属于任何对话：它不计入任何会话，记忆流也从不出现在时间线中。
- **每个记忆文件一个条目。** 适配器读出文件每个版本中的记忆：它的类型、正文和置信度（见 [sources.md](sources.md#native-memories)）；文件里没有记忆时什么也不读出。Origin 从每一行派生出一个条目的版本（`core` 中的 `memories.ts`）。它引用这一行的事件（不变量 1）；它的 id 由事件的 id 派生（`ent_` 加一个 SHA-256 的 24 个十六进制字符）；作者为 `<source>@<device>`，origin 为记忆所在的设备：对本库自己的文件是本库的名称，在中枢上则是发送这条记忆流的设备或中继。
  - 文件的第一个版本开始一个条目。之后的每个版本取代从该文件上一行派生出的版本，时间取文件的修改时间，并且晚于被取代的版本（不变量 3），所以条目的当前版本跟随文件变化。
  - 被删除的文件，或者被清空了内容的文件，会结束这个条目：它的最后一个版本被再写一次，`valid_to` 设为删除的时间。文件重新出现时会取代这个版本，条目重新成为当前的。没有可结束内容的删除不派生任何东西，而在一个没有派生出任何东西的行之后的版本会开始一个新的条目。
  - 导入的条目和其他条目一样可以纠正和遗忘。在 Origin 中做的纠正会取代当前版本，而文件的下一个版本取代它之前派生出的版本；按[并发纠正](#entries)的规则，两者中较晚的一个是当前版本，所以文件在纠正之后再有变化时，以文件为准。被遗忘的条目在文件变化时保持遗忘：每个新版本及其引用的事件都在到达时就被隐藏（不变量 2），恢复会把条目带回到它最新的版本。遗忘只在 Origin 中隐藏条目；Agent 的文件保持原样。
- **每个库都派生。** 与事件一样，这些版本由每个解析这条记忆流的库派生，id 和内容都相同：设备从自己的文件派生，它的中枢从设备的镜像或中继发来的行派生。因此它们从不发送给其他库：`imported_entry` 列出它们，设备推送时会略去它们，它们也不会让库的名称固定下来（见[存储](#storage)）。对它们的纠正和遗忘照常发送；中枢一旦解析了设备的镜像（设备会先推送镜像），就有了这些纠正和遗忘所指向的版本。较早版本的中枢收到设备发来的记忆流时只镜像、不读取；升级之后，它在打开库时读取这些记忆流（迁移 4，见[迁移](#migrations)），在此之前，设备对导入条目的纠正会等待中枢。在中枢派生出某个导入条目之前，设备上对这个条目或其记忆事件的遗忘，会在条目派生出来时覆盖它。
- **在结果中。** MCP 结果中的条目带有 `imported`；管理界面和 CLI 会标出导入的条目，显示条目的有效期何时结束，并把记忆事件显示为它所属文件的一个版本。MCP 的 instructions 会告诉 Agent，导入的条目对应某个 Agent 自己的记忆文件，所以文件之后的变化会取代在 Origin 中做的纠正。

## 条目 {#entries}

- **记住（remember）。** 一个条目是一条自成一体的陈述，带有类型、0 到 1 之间的置信度、作者（`<agent>@<device>`：MCP 客户端的名称加上它写入的库的名称，例如 `claude-code@laptop`；CLI 和管理界面写入时为 `user@<device>`；直接使用中枢的 Agent 见[访问](#access)）、可选的项目和有效期，以及至少一个来源（不变量 1）。来源可以是一个事件 id、一段精确引文，或者两者兼有：
  - 给出 id 时，该事件必须存在且可见；如果同时给出引文，引文必须出现在该事件中（忽略空白和大小写）。
  - 只给出引文时，Origin 引用包含该引文的最新可见 `message` 事件，找不到时退而查找 `tool_result` 事件。工具调用永远不参与匹配，因为 Agent 自己那次包含该引文的 `remember` 调用，本身就会作为工具调用被记录下来。最新指时间戳最新。Origin 像检索那样查找引文中的词（见[检索与时间线](#search-and-timeline)），每种事件最多核对含有所有这些词的最新 25,000 个事件，所以完全由非常常见的词组成的引文，可能在较早的事件中找不到；这时请改为引用事件 id。
- **纠正（correct）。** 纠正一个条目的当前版本，会插入一个 `supersedes` 它的新版本（不变量 3）。原有来源会被继承，也可以添加新的来源。纠正的时间总是晚于被纠正的版本，即使本机时钟偏慢也是如此。一个条目的所有版本共享它的 `root`，也就是第一个版本；它们合起来构成这个条目的版本链。
- **并发纠正。** 两个库可能在互相知道之前纠正了同一个版本，所以一个版本可以被不止一个版本取代。这时版本链出现分叉，而每个库都以同样的方式解决它：链中 `(created_at, id)` 最大的版本是**当前**版本，其他版本都是已被取代的版本。一个已被取代、但没有被任何版本纠正的版本，是输给了一次并发纠正，会被标记出来（`concurrent`）。只有当前版本可以被纠正。
- **状态**由推导得出：如果有生效中的遗忘覆盖该条目（见[遗忘](#forgetting)），则为 `forgotten`；如果它是所在版本链的当前版本，则为 `active`；否则为 `superseded`（`superseded_by` 指向当前版本）。除非请求历史，查询只返回活跃条目；被遗忘的条目永远不会被返回。历史按从旧到新的顺序列出版本链中的每个版本，包括分叉。
- **有效期。** 条目可以说明它何时成立（`valid_from`、`valid_to`）。`valid_to` 一过，条目就*结束*了，例如文件已被删除的导入记忆：它成为历史，不再是当前的知识。除非请求历史，检索和列表都不包含已结束的条目（MCP `search`、`origin search`、`origin entries`，以及管理界面的检索和条目页；`origin entries --history` 和管理界面的历史会包含它们），而 `get` 和 `origin show` 仍然显示它们及其有效期。
- **导入的条目**派生自 Agent 为自己保存的记忆，并标记为 `imported`（见[原生记忆](#native-memories)）。

## 遗忘 {#forgetting}

`forget` 接受一个条目 id 或事件 id，以及一个原因，并写入一条遗忘记录，也就是一次**遗忘**（不变量 2）。它按三条规则隐藏它的目标及其连带内容：

1. **遗忘一个条目**会隐藏它的所有版本（整条版本链，包括分叉），以及这些版本引用的所有事件。
2. **遗忘一个事件**会隐藏该事件，并像规则 1 那样隐藏所有引用它的条目。
3. **当前版本不再有任何可见来源的条目**已经失去溯源，因此同样会被隐藏，包括它的每个版本。这一步不会再隐藏其他事件，所以级联到此为止。

版本链要么整体被隐藏，要么完全不被隐藏。被隐藏的条目和事件会从检索、时间线、会话计数、`get` 和 `sources` 中消失，被隐藏的事件也不能再被引用。重新同步——即使源文件已被改写——也不会让它们回来，因为事件 id 是稳定的，而隐藏按 id 生效。不会隐藏任何新内容的遗忘不会被记录。

**遗忘是一条记录。** 每条遗忘记录都保存它的目标、原因、时间、创建它的库（`origin`），以及在已知时由谁做出（`author`：Agent 的 `forget` 记为 `<agent>@<device>`，CLI 和管理界面记为 `user@<device>`）。无论在哪里遗忘，都必须给出原因：MCP 工具、CLI 和管理界面都会拒绝空的原因（Origin 0.1 写下的遗忘记录可能没有原因）。`tombstone` 中从不删除任何东西，所以遗忘与恢复的历史始终完整。

**恢复。** 主人可以随时恢复一次遗忘，并给出原因，方式是 CLI（`origin restore`）或管理界面；Agent 不能恢复。恢复本身也是一条遗忘记录，有自己的 id、原因、时间、origin 和作者，它的目标是那次遗忘的 id：它遗忘了那次遗忘。没有恢复以它为目标时，一次遗忘就是**生效中**的。只有遗忘可以被恢复，而且只能恢复一次；恢复不能被恢复。要再次隐藏目标，就再遗忘它一次：这会产生一次新的遗忘，有它自己的记录。

**遗忘覆盖什么。** 只要有生效中的遗忘覆盖一个条目或事件，它就被隐藏。每次遗忘在一个库中覆盖的内容记在 `tombstone_effect` 中，一项内容可以被多次遗忘覆盖，覆盖方式有四种：

- `direct`：按本库的数据，由它的目标经规则得出的内容，包括之后才到达的版本和引用条目。
- `listed`，在设备上：它的中枢为这次遗忘列出的内容。中枢每发来一份新的列表，就替换上一份，因为中枢为它持有的条目判断规则 3，并且可能在一次恢复之后撤回某个判断。
- `reported`，在中枢上：发送这次遗忘的设备在它那里覆盖的内容，累加到它之前所报的内容上。
- `cascade`：本库中的规则 3。应用一次遗忘时，凡是引用了它所覆盖的事件、而当前版本已不再有可见来源的版本链，都由它覆盖。

`forgotten_entry` 和 `excluded_event` 保存被隐藏的内容，每一项都记有一次覆盖它的、生效中的遗忘；每个查询都据此过滤，所以隐藏不会让查询比以前多花任何代价。

**恢复会带回什么。** 一次遗忘不再生效时，它覆盖的每个事件都会回来，除非另有生效中的遗忘覆盖它。它覆盖的每条版本链，以及引用了回来的事件的每条版本链，都会重新判断：如果另有生效中的遗忘按自己的规则或自己中枢的列表覆盖它，或者它的当前版本仍然没有可见来源（规则 3），它就继续被隐藏；后一种情况下，凡是覆盖了这些来源之一的生效中的遗忘，都覆盖它。在中枢上，设备对这样一条版本链所报的内容也会这样重新判断。其余一切都会回来，连同会话计数、检索结果和引用，所以一次恢复会让库回到仿佛那次遗忘从未发生的样子。回来的条目中由本库自己写下的那些，会在 `change_log` 中再次记录，这样设备会把隐藏期间扣下的条目发给中枢。CLI 和管理界面在恢复之前会先展示它将带回的内容。

**跨库。** 遗忘记录的 id 是全局的，所以在一个库中创建的遗忘或恢复，到达任何库时都保持它的 id、origin、原因和作者。库按规则把一次遗忘应用到自己持有的数据上，并覆盖发送方列出的内容，只要库认识那些 id；除非库知道这次遗忘已被恢复，否则把这些都隐藏起来。一次恢复会解除它的遗忘；如果那次遗忘还没有到达，就等待它：中枢会保存这样的恢复，而设备只保存它持有的遗忘的恢复，会在遗忘之后再次收到这条恢复（见[复制](#replication-raw-mirrors-entries-and-tombstones-up-tombstones-down)）。同一条遗忘记录应用两次不会改变任何东西。一项内容是否被隐藏，只取决于生效中的遗忘以及它们覆盖的内容，而遗忘记录只增不减，所以无论遗忘和恢复以什么顺序到达，各个库都会收敛到同一个状态：恢复先于它的遗忘到达，遗忘在别处已被恢复之后才到达，或者其中任何一条被应用两次。之后才到达、属于一条被隐藏的版本链的版本，在到达时就会被隐藏；来源已在本库中被隐藏的条目也是如此（规则 2 和 3）；某次遗忘以它为目标、或以它引用的事件为目标、而在应用这次遗忘时两者都还不在本库中的条目，同样如此：从原生记忆派生的条目在每个库中的 id 都相同，所以可能在一个库中被遗忘之后，另一个库才派生出它。

遗忘是隐藏，而不是擦除。原始镜像文件仍保留在磁盘上（不变量 3），但永远不会被展示，恢复也依赖它们。物理擦除被遗忘的内容会是一个单独的、显式的操作；目前没有实现。CLI 会先展示一次遗忘将隐藏的内容，以及一次恢复将带回的内容，只有加上 `--yes` 才会执行。

## 检索与时间线 {#search-and-timeline}

事件检索只覆盖 `message` 事件，除非请求包含工具事件（`--all` / `include_tools`），并且从不返回已遗忘的事件。条目检索覆盖有效期没有结束的活跃条目（见[条目](#entries)）。

**词。** 查询按空白切分，每个词都必须作为子串出现在文本中（不区分大小写；`log` 能匹配 `catalog`）。一个词如何被找到，取决于它的字符数：

- **三个或更多字符**：通过 trigram 索引查找，对中日韩（CJK）文字和拉丁文字都一样。
- **一到两个 CJK 字母**（汉字、假名或谚文），例如 `部署` 或 `库`：通过 CJK 索引查找，它保存每一对相邻的 CJK 字母，以及每一串 CJK 字母的最后一个字母。
- **一到两个其他字符**，例如 `AI`、`C#` 或 `5号`：没有索引能找到它们，所以 Origin 从新到旧核对候选事件的文本。候选事件是检索所覆盖的事件（它的事件类型，以及所请求的项目、来源和时间范围）中匹配查询其他词的事件。最多核对最新的 25,000 个候选事件（`SCAN_LIMIT`），所以这样的词可能漏掉较早的事件；限定时间范围、指定项目或加上一个更长的词，就能找到它们。

**索引。** 事件检索由三个 FTS5 索引支撑，它们都以 `seq` 为键。其中一个索引驱动查询，从新到旧，其余的词再过滤它的匹配：

| 索引 | 内容 | 用途 |
|---|---|---|
| `message_fts` | `message` 事件，记录每个 trigram 的位置（`detail=full`） | 含有三个或更多字符的词的消息检索：每个词都作为短语精确匹配，并用 BM25 打分 |
| `event_fts` | 所有事件，只记录哪些事件含有每个 trigram（`detail=none`），体积只是完整索引的一小部分 | 包含工具事件的检索：事件必须含有每个词的每个 trigram，然后再用词本身核对 |
| `event_cjk` | 每个含 CJK 文字的事件的 CJK 二元组（`detail=none`，无内容表） | 一到两个字母的 CJK 词，以及其他词都同样短的查询 |

**排序。** 结果默认按 BM25 相关度排序，最相关的在前。排序只考虑最新的 2,000 个匹配（`RANK_WINDOW`），匹配更少时则考虑全部：查询匹配的事件更多时，较早的匹配既不参与排序也不会返回，所以非常常见的词会偏向近期的事件，而限定时间范围会移动这个窗口。对于消息，BM25 把词作为短语打分；包含工具事件时，它对词的 trigram 打分。没有三个或更多字符的词的查询，以及 `--recent`，改为按时间排序。按时间排序指按时间戳从新到旧，时间戳相同的事件中后到达的在前；相关度相同的结果也按同样的方式排列。无论事件以什么顺序到达，按时间排序的结果以及最新 2,000 个匹配的窗口都是精确的：查询按到达的块读取索引（见[存储](#storage)），一旦没有未读的块可能含有比所需匹配更新的匹配，就立即停止。匹配很少的查询（不超过 2,000 个，或所需数量的五倍）则直接读取全部匹配。

**摘要**显示第一个匹配周围最多 200 个字符的文本，每个匹配都用方括号标出。

**条目**按同样的词检索：三个或更多字符的词通过 `entry_fts` 查找并按 BM25 排序，更短的词通过核对文本查找（条目很少）。没有三个或更多字符的词时，条目从新到旧排列。

时间线按时间列出会话，或按顺序列出单个会话的事件（工具事件默认隐藏，除非请求显示）。

**会话的名称。** 会话的 `title` 是它的 Agent 给它的标题，或用户通过 Agent 给它的标题（见各来源的映射）；Codex 不给任何标题，其他 Agent 也并不总是给。没有标题的会话改为带有一个 `prompt`：它的第一条提示，作为一个临时的名称，界面可以把它作为临时名称显示。它是该会话中最早的、属于用户亲手输入的提示的那个可见的用户 `message` 事件的文本：消息开头的 XML 风格元素（`<tag …>…</tag>`）是 Agent 作为上下文或命令回显添加的，例如 Claude Code 的 `<command-name>`、`<local-command-stdout>` 和 `<local-command-caveat>`，或 Codex 的 `<environment_context>`，它们会被跳过，其后的内容才算数；去掉这些之后为空、或只剩一个方括号提示（例如 `[Request interrupted by user]`）的消息会被略过。适配器标记为 `meta` 的事件（注入的上下文、合成的提示）不是消息。提示中的空白会被合并，并截断到 80 个字符。它在每次读取会话时（`listSessions`、`getSession`）通过 `event_user_message`（一个只包含每个会话的用户消息的索引）从事件中计算得出，因此会随遗忘而变化（不变量 2）；不保存任何东西。MCP 的 `timeline`、`origin timeline`（放在引号中）以及管理服务的会话列表都在标题旁边带上它。

## MCP server {#mcp-server}

`origin mcp` 通过 stdio 提供以下工具。结果是 JSON 文本，时间戳为本地时间的 ISO 8601 格式，精确到毫秒。

| 工具 | 用途 |
|---|---|
| `brief` | 用户的记忆中与 Agent 工作之处有关的内容，即召回交出的内容，并记录为一次召回（见[召回](#recall)） |
| `search` | 对条目和事件做全文检索；不带查询词时列出最近的条目。过滤条件：范围、类型、时间段、来源、项目、工具事件 |
| `timeline` | 某个时间段内的会话（默认 7 天），每个会话带有它的标题，没有标题时带有它的第一条提示（见[会话的名称](#search-and-timeline)）；或单个会话的事件 |
| `get` | 条目及其来源和版本历史，或事件及其完整正文 |
| `sources` | 条目或事件对应的原始记录行：文件、镜像、行号、原始文本 |
| `remember` | 写入一个条目，包括类型、正文、置信度和来源 |
| `correct` | 用纠正后的版本取代一个条目 |
| `forget` | 按上述规则隐藏一个条目或事件，并附上用户给出的原因；仅在用户明确要求时使用。没有用于恢复的工具：只有主人能恢复，方式是 CLI 或管理界面 |

- **新鲜度。** server 在启动时采集所有来源，在 `brief`、`search` 和 `timeline` 之前也会采集（最多每 10 秒一次；在连接了中枢的设备上，`get` 和 `sources` 之前也会），在 `remember` 和 `correct` 之前则总会采集，因此 Agent 能引用它当前所在对话中的记录行。
- **Agent 运行期间。** server 还会每 60 秒查看一次有没有新的记录行（`ORIGIN_WATCH_INTERVAL_MS`；设为 0 则关闭），这样 Agent 最后一次调用工具之后写下的内容也能进入库和中枢，而不必等到下一个 Agent 启动。每次查看会把各记录文件的大小和修改时间与上次采集时比较，不读取文件内容，只有发生变化时才采集。查看在后台进行，与其他刷新使用同一套闸门，所以一次只查看一次，也绝不会与另一次同步重叠；工具调用不会等待它，除非本来就需要刷新；耗时较长的采集也会在各个事务之间让工具调用先执行。
- **Agent 离开时。** 标准输入结束，或者 server 收到 SIGTERM、SIGINT 或 SIGHUP 时，它会再采集一次，已接入中枢时还会与中枢同步，最多等待 5 秒，然后退出。Agent 如果直接杀掉 server，就会跳过这一步；下一次启动时会补上。
- **在已接入中枢的设备上。** server 仍然根据设备自己的库作答，读取类工具（`search`、`timeline`、`get`、`sources`）会同时询问中枢的 `/mcp`。两边的结果会合并、按 id 去重，并标上 `origin: "local"`（本设备有这一项）或 `"hub"`。无论中枢返回什么，设备已经遗忘的内容都不会显示；同一个条目的多个版本中，只列出按[条目](#entries)中的规则确定的当前版本；`get` 会合并两个库中该条目的历史。对于设备没有的 id，`get` 和 `sources` 由中枢作答。如果中枢在 2 秒内（`ORIGIN_HUB_TIMEOUT_MS`）没有回应，或者无法连接，工具就只根据设备作答，并附加第二段文本，说明这次没有询问中枢。agent 一完成初始化，server 就建立到中枢的连接，这样第一次读取不必把这段时间花在 TLS 握手和 MCP 初始化上。
- **已接入中枢的设备上的写入**先落到设备的库中，再同步上去。server 在读取类工具之前与中枢同步（最多每 10 秒一次），每次写入后、每次后台查看发现新的记录行后、以及 Agent 离开时也会同步，而且为了等待中枢而推迟回答的时间不会超过超时时限。失败的同步会在下一次后台查看时重试。对于设备没有的条目或事件，`correct` 和 `forget` 会在中枢上执行；连不上中枢时，它们会失败并给出清楚的错误说明。
- **在中继上。** 每个工具都交给中枢的 `/mcp`，中枢的回答原样返回，不带 `origin` 标签。在此之前，server 先把 Agent 新增的记录行发送给中枢：读取类工具之前最多每 10 秒一次，最多等待中枢超时时限；每次写入之前都会发送，最多等待 15 秒，这样条目就能引用刚刚说过的内容。由于它自己没有回答，它最多等待中枢的回答 15 秒；连不上中枢时，工具会失败，并说明中继离线时无法作答。记录文件有变化时，它每分钟也会发送一次新的行，Agent 离开时再发送一次（见[中继](#relays)）。
- **引导。** server 的 MCP `instructions` 会告诉 Agent：开始任务时，如果召回还没有给过它简报，就调用 `brief`；何时检索、何时记住（带理由的决定、稳定的事实、偏好），`forget` 需要明确的请求和用户给出的原因，只有用户能恢复被遗忘的内容，以及导入的条目对应某个 Agent 自己的记忆文件，所以文件之后的变化会取代在 Origin 中做的纠正。结果中的条目会说明自己是否为导入的（`imported`）。
- **错误。** 无效输入、未知 id 和已遗忘的 id 会以工具错误的形式返回，并附带可读的说明。

## 召回 {#recall}

召回是 Origin 不经询问就交给 Agent 的内容：会话开始时的一份简报，以及与每个提示匹配的条目。Agent 通过它们的 hook 运行召回（`origin recall --hook <agent>`，见[召回](guide/recall.md)）；hook 无法交出内容的 Agent，则用 MCP 工具 `brief` 主动请求。召回不调用任何模型，每一次都有记录。

**范围。** 召回针对一个工作目录。它的项目是包含这个目录的 git 工作树；不在工作树中时，就是这个目录本身；项目名是它的最后一段，与归档中一致。从记忆文件导入的条目属于这个文件所对应的目录，会话属于它的工作目录，所以两个同名的检出能够区分开，主目录也不会把它下面的项目都算作自己的；通过 Origin 写下的条目属于它写明的项目。

- 其他项目的记忆和知识从不交出。认知（用户的偏好、方法、目标和边界）在哪里都成立，但简报只包含本项目的认知和不属于任何项目的认知：某个项目的 Agent 记忆文件很少说明它在别处是否也成立，所以其他项目的认知只有在提示与它匹配时才会交出。
- 只交出当前的条目：没有被取代、遗忘、结束，也不是尚未开始的。
- Agent 不会拿到从它自己为本项目保存的记忆文件导入的条目，这些文件它自己会加载。

**会话开始时**（新的、清空后的或压缩后的会话；已经有过简报的恢复会话不再给），一份简报：

- 认知：先是本项目的，再是不属于任何项目的，从新到旧，最多 5 条；
- 本项目的记忆和知识，从新到旧，最多 5 条；
- 本项目最近 30 天内结束的、与任意 Agent 的会话（本会话除外），最多 3 个：Agent、时间、会话 id、标题或第一条提示，以及最后一条提示。

**每个提示**，与它匹配的条目，最多 5 条。匹配是基于词汇的，结果确定：

- **词。** CJK 之外的单词（字母、数字和 `_`；`linkos.io` 这样的名称既整体算一个词，也按各部分算），以及按平台（ICU）分词得到的 CJK 词；分词器不认识某个词而留下单字时，用相邻两字组成的词对代替，按一半计。停用词会去掉，项目自己的名字也会去掉。
- **匹配什么。** 条目的第一行，它说明条目是关于什么的；正文几乎总能在某处匹配上提示。
- **权重。** 一个词的权重是它在用户自己的话（归档中用户最近的 1,000 条提示）和条目第一行中的逆文档频率，所以用户一直在说的词权重很低。
- **阈值。** 当条目含有的提示中的词，权重加起来超过最罕见的词的权重（两个罕见的词，或者几个常见的词），而且它的 BM25 分数至少是最佳匹配的 40% 时，条目才算匹配。本会话上一次简报之后已经交出的条目会被略去。

**预算。** 每项一行：条目的 id 和第一行，或者会话的这些信息，截到约 40 个 token，上面有一行说明，告诉 Agent 用 `get` 加 id 获取其余内容，并且用户在本会话中说的话优先。一份简报最多占 800 个 token，一个提示的匹配最多 400 个，按每个 CJK 字符一个 token、其他字符每四个一个 token 估算；放不下的会被略去。

**记录。** 每一次召回（包括什么都没匹配到的）都是 `recall` 中的一行，它的各项在 `recall_item` 中：一个 id（`rcl_…`）、时间、进行召回的库、Agent 及其会话、时机（`start`、`prompt`，或者 `request`，表示 Agent 用 `brief` 请求）、项目和目录、预算和用掉的 token，以及每一项的排名、层、类型（条目或会话）、id、分数和大小。召回不保存任何文本，提示只存哈希，这样遗忘隐藏的内容不会仍从记录中显示出来（不变量 2）：每一项是什么，在显示召回时才从库中读取，已遗忘的显示为已遗忘。两张表都是只追加的。设备会把自己所做的召回发送给中枢（见[复制](#replication-raw-mirrors-entries-and-tombstones-up-tombstones-down)），所以中枢保存着每台设备的召回。`origin recalls` 列出召回，`origin show rcl_…` 显示一次召回，包括它回应的提示（会话中具有该哈希的用户消息，归档之后才能找到），以及每一项本会话之后是否用上了：它的 id 是否出现在该会话中 Agent 之后的工具调用或回复里。

**Hook。** `origin recall` 只加载核心和适配器，以便快速启动，而且从不妨碍 Agent：出现任何故障时，它什么都不输出，在标准错误中说明原因，并以 0 退出；它最多等待 3 秒获取库的写锁。它只读取本设备的库，所以其他设备上写下的条目暂时不会被召回；中继不保存条目，不交出任何内容。

**通过 MCP。** `brief` 交出一份简报，加上 `about` 时还有与它匹配的条目，记录为时机为 `request` 的一次召回。由 Agent 运行的 server 作答：在设备上根据设备的库作答，已接入中枢的设备也不询问中枢，与 hook 一致；中继把它交给中枢，以自己的工作树作为目录，中枢看不到 Agent 的磁盘，所以按原样使用这个目录，并把这次召回记录为为该设备所做。MCP 调用不说明会话，所以这类召回不记录会话；它的会话是日志中有某个工具结果含有这次召回 id 的那个会话，归档之后才能找到。

## 个人中枢 {#personal-hub}

中枢就是一个普通的 Origin 库，只是额外运行了 `origin serve`。它是自托管、单租户的：一个人，以及这个人的设备和 Agent。中枢中没有任何部分依赖特定的托管服务商；发布的容器镜像 `ghcr.io/openlinkos/origin` 可以在任何地方运行它。

### 角色 {#roles}

每个库都是一个副本；中枢是那个始终在线的副本。

- **设备**：任何有 Agent 会话记录的机器。它的库本身就是完整的：它在本地采集（适配器、原始镜像、游标、改写代次、压缩都保持不变），它的 Agent 读写这个库，离线时也照常工作。接入中枢后，它把自己写下的内容发送给中枢（`origin sync`，以及运行中的 `origin mcp`），并通过中枢读取其他库中的内容。
- **中继**：一台不保有自己记忆的设备，适用于磁盘空间不多的机器。它在 Agent 写下记录时就把记录发送给中枢，所有问题都通过中枢回答（见[中继](#relays)）。
- **中枢**：`origin serve` 为 Agent 提供基于 HTTP 的 MCP，为设备提供复制 API，启用后还为它的主人提供一个管理界面。它保存每台设备发来的内容，以及云端 Agent 直接写入它的内容，所以在那里能找到一切。它可以把原始镜像中已封存的帧保存在兼容 S3 的存储桶中，而不是自己的磁盘上（见[帧存储](#frame-stores)）。

### 复制：原始镜像、条目和遗忘记录上行，遗忘记录下行 {#replication-raw-mirrors-entries-and-tombstones-up-tombstones-down}

设备把自己写下的内容发送给中枢；中枢发给设备的只有被遗忘的内容。一次同步（已接入中枢的设备上的 `origin sync`）按顺序分四步进行：

1. **原始镜像。** 设备推送的是**原始镜像字节**，而不是解析后的事件。中枢把它们存为自己的只追加镜像，并用同样的适配器解析，因此溯源（不变量 1）在中枢上同样成立，解析器的修复也会在所有地方生效。事件 id 在每个库中都完全相同。
   - 每个远程文件以 `(source, "@<device>:<original path>", generation)` 为键；本地路径永远不会以 `@` 开头。中枢上的镜像位于 `raw/devices/<device>/<source>/<relPath>[.g<n>]`，存储方式与其他镜像相同（见[原始镜像](#raw-mirrors)）。
   - 推送可续传且幂等：设备先向中枢查询游标，再把每个镜像的 `[cursor, local size)` 区间按完整行分块发送（每块最多 1 MiB，或者单独一个更长的行）。偏移量与中枢游标不一致的块会被拒绝，并返回当前游标，设备从那里继续。偏移量和游标都按镜像未压缩内容的字节计算：设备解压读取自己的镜像，请求在传输中以 gzip 编码，中枢再压缩存储。
2. **条目和遗忘记录上行。** 设备按照自己 `change_log` 的顺序，发送推送游标之后它自己写下的条目和遗忘记录（遗忘与恢复；也就是 `origin` 为它的名称的那些）。它从原生记忆派生出的条目不发送：中枢会从设备的镜像派生出同样的条目（见[原生记忆](#native-memories)）。被隐藏的条目不会被发送；被恢复带回的条目会再次记录，并在那时发送。中枢以相同的 id 保存它们，保留作者和 origin，并按[遗忘](#forgetting)中的规则应用这些遗忘记录，所以一个到达时已属于被遗忘内容的版本或条目，会在到达时就被隐藏。由于设备先推送镜像，它的条目所引用的事件通常已经在中枢上了；如果某个条目引用的事件或它取代的版本还不在中枢上，中枢会说明缺少哪些 id，推送游标停在这个条目之前，之后的条目等到下一次同步。遗忘记录照样发送：遗忘从不等待。
3. **遗忘记录下行。** 设备请求中枢 `change_log` 中位于自己拉取游标之后的遗忘记录；中枢会略去该设备自己创建的那些，并为每次遗忘附上它此刻在中枢上覆盖的内容一起发送。设备把它们应用到自己的库中，从而让遗忘和恢复到达每一个副本（不变量 2）。当一次遗忘在中枢上覆盖的内容后来发生变化——因为中枢把它应用到了设备没有的数据上，因为到达了它所覆盖的纠正或条目，或者因为一次恢复让中枢重新判断了规则 3——中枢会再次记录它，于是每台设备，包括创建它的那台，都会收到新的覆盖内容，它会替换中枢上一份列表。先于它的遗忘到达中枢的恢复，会在那次遗忘到达后再次记录；在订阅流的同一页中被记录多次的遗忘记录只发送一次，位置在它最后一次被记录的地方。
4. **召回上行。** 设备按从旧到新的顺序，发送召回游标之后它所做的召回（见[召回](#recall)），也就是 `origin` 为它的名称的那些。召回只含 id，所以不需要中枢先有别的内容，中枢以同样的 id 保存它。不认识召回的旧版中枢会返回 404：召回连同游标一起留在设备上，等中枢升级后再发送。

- **只有遗忘记录下行。** 中枢从不把条目或事件发给设备：设备的库只保存它自己的会话、它自己的条目，以及与之相关的遗忘记录。
- **每个条目只有一个裁决者。** 设备应用来自中枢的遗忘记录时，只对中枢还没有收到的条目判断规则 3（不再有可见来源）。对其余条目，中枢持有每一个版本，它的裁决作为这次遗忘覆盖内容的一部分到达，所以设备和中枢对它们都有的条目保持一致。在设备上做出的遗忘或恢复，会立即在设备上按它持有的版本判断；对于中枢已有的条目，随后以中枢的判断为准。如果中枢持有来自另一个库的更新版本，一次恢复可能让设备继续隐藏一个中枢显示的条目（见[待解决的问题](#open-questions)）。
- **游标。** 设备在 `setting` 中为每个中枢 URL 保存三个游标：自己的变更推送到了哪里、中枢的变更拉取到了哪里，以及自己的召回发送到了哪里。每次请求成功后都会保存游标，所以中断的同步会从中断处继续，再次运行则什么也不会发送。
- 在中枢上被遗忘的事件即使被再次推送，也会保持排除，因为排除按事件 id 生效。

### 访问 {#access}

- 发往 `/mcp` 和 `/v1/*` 的每个请求都需要 `Authorization: Bearer <token>`；`/admin` 下的管理界面有自己的登录（见[管理界面](#admin-ui)）。令牌在中枢上创建（`origin token create <name>`），只显示一次，只以 SHA-256 哈希的形式存储，并且可以吊销。每台设备或每个云端 Agent 各用自己的令牌。
- **每个令牌绑定一台设备，即与它同名的设备。** 在复制接口上，令牌只能为这台设备发送和接收数据：它推送的内容都记在令牌名下，请求里指明了其他设备（请求体或查询参数中的 `device`）时会被拒绝并返回 `403`，`origin` 不是这台设备的记录同样会被拒绝。因此设备的库必须与它的令牌同名，`origin hub connect` 会检查这一点（见[从设备使用中枢](#using-a-hub-from-a-device)）。与中枢自身同名的令牌不服务于任何设备；只用于 `/mcp` 的令牌（例如云端 Agent 的令牌）不需要对应设备。被吊销的令牌可以用同一个名称新建一个来替换，所以丢失令牌的设备仍能保留它的名称；有效的令牌必须先吊销。
- 中枢使用明文 HTTP。在 localhost 之外开放之前，请把它放在 TLS（反向代理或 CDN）之后。
- 设备推送上来的条目保留写入时的作者。通过中枢的 `/mcp` 写入的条目，如果调用方在 `X-Origin-Client` 中报上了它的 Agent（设备上的 `origin mcp` 就会这样做），作者记为 `<agent>@<令牌名>`（如 `claude-code@laptop`）；否则只记令牌名（例如云端 Agent 的令牌 `ci`），因为无状态请求不携带 MCP 客户端的名称。作者中的设备部分始终是令牌名：设备上的 `origin mcp` 还会在 `X-Origin-Device` 中报上自己的名称，如果这个请求头指明的是另一台设备，中枢会拒绝请求（`403`），所以任何令牌都不能以另一台设备的身份写入，库名与令牌不一致的设备也会明显地报错。中继上的 `origin mcp` 发送同样的请求头，所以它的 Agent 写入的内容记为 `<agent>@<中继名>`，origin 为中枢；它的 CLI 写入的内容记为 `user@<中继名>`。

### HTTP 接口 {#http-interface}

| 方法与路径 | 用途 |
|---|---|
| `GET /healthz` | `{ "ok": true, "version": … }`，无需鉴权 |
| `POST /mcp` | MCP Streamable HTTP，无状态，JSON 响应；与 stdio server 相同的八个工具 |
| `GET /v1/device` | `{ device, hub }`：令牌所属的设备（即令牌名）和中枢的名称 |
| `GET /v1/cursors?device=<name>` | 令牌所属设备的每个文件在中枢上的字节游标 |
| `POST /v1/ingest` | 追加一个块：JSON `{ device, source, path, relPath, generation, offset, mtimeMs, agentVersion, data }`，其中 `data` 为 base64，`offset` 按镜像未压缩的内容计算（中继发送的是文件的内容，二者相同）；请求体可以使用 gzip 编码。返回 `200 { bytes, eventsAdded, … }`，偏移量不匹配时返回 `409 { bytes }` |
| `POST /v1/entries` | `{ device, entries }`，最多 1,000 个条目，每个为 `{ id, kind, text, confidence, author, project, supersedes, validFrom, validTo, createdAt, origin, sources: [{ eventId, quote }] }`，其 `origin` 必须是令牌所属的设备。按顺序保存；返回 `200 { applied, pending }`，其中 `pending` 为 null，或者是第一个所引用事件或所取代版本尚不在中枢上的条目的 `{ id, missing }`（它之后的条目都不会被保存）。同一个 id 下内容不同时返回 `409` |
| `POST /v1/tombstones` | `{ device, tombstones }`，最多 1,000 条遗忘记录，每条为 `{ id, target, reason, createdAt, origin, author, entries, events }`（`author` 可选），附带它在设备上覆盖的内容，其 `origin` 必须是令牌所属的设备。恢复的目标是一次遗忘的 id，并且不列出任何内容；如果中枢还没有收到它的遗忘，就先保存它，等那次遗忘到达时生效。按[遗忘](#forgetting)中的规则应用；返回 `200 { applied }`，同一个 id 下内容不同时返回 `409` |
| `POST /v1/recalls` | `{ device, recalls }`，最多 1,000 次召回，每次为 `{ id, at, origin, source, sessionId, occasion, project, cwd, promptHash, budget, tokens, items }`，每一项为 `{ rank, layer, kind, ref, score, tokens }`，`origin` 必须是令牌所属的设备。按 id 只保存一次；返回 `200 { applied }`，同一个 id 内容不同时返回 `409` |
| `GET /v1/tombstones?after=<seq>&device=<name>` | `{ tombstones, next, more }`：中枢变更日志中序号大于 `after` 的遗忘与恢复，不含令牌所属设备自己创建的，每条都附带 id、目标、原因、`createdAt`、origin、已知时的作者，对遗忘而言还有它在中枢上覆盖的条目和事件。`more` 为 true 时，用 `after=<next>` 继续 |
| `GET`, `POST /admin/…` | 启用时的管理界面：需要管理员登录的服务器端渲染页面。未启用时返回 404 |
| `GET`, `POST /admin/api/…` | 管理界面的 JSON API：与页面相同的操作、会话和检查 |

中枢会校验每个字段。复制请求总是代表令牌所属的设备：`device` 可以省略，如果请求指明的是另一台设备，会被拒绝并返回 `403`，响应体中附带令牌所属的设备（`{ error, device }`）。设备名必须匹配 `[a-z0-9][a-z0-9._-]{0,62}`，并且不能是中枢自己的名称，来源必须是已知的适配器，`relPath` 必须是相对路径且不含 `..` 段，因此设备永远无法写到它自己的镜像目录之外。

### 从设备使用中枢 {#using-a-hub-from-a-device}

设备以两种模式之一使用中枢，在接入时选定。默认情况下，它是一个**完整的库**：像没有中枢时一样保有自己的记忆，并按上文所述与中枢复制。加上 `--relay` 时，它是一个**中继**：除了游标什么也不保存，直接把 Agent 的记录发送给中枢，所有问题都通过中枢回答（见[中继](#relays)）。除非另有说明，本节其余部分说的都是完整的库。

- `origin hub connect <url> --token <token> [--device <name>] [--relay]` 把连接信息保存在 `<ORIGIN_HOME>/hub.json` 中。设备名就是它的库的名称（见[存储](#storage)），而且必须是这台设备的令牌名：这个命令会向中枢询问令牌属于哪台设备（`GET /v1/device`），如果不是这个库，就拒绝接入并说明如何解决。`--device` 可以给一个还没有写入任何条目或遗忘记录的库改名。`origin hub status` 也做同样的检查。每一次与中枢的同步，无论由哪个命令或 Agent 发起，都会在 `setting` 中记下它完成的时间，失败时则记下时间和原因；`origin status` 和 `origin hub status` 显示上一次同步完成的时间，以及此后失败的那一次同步的错误。`ORIGIN_HUB_URL` 和 `ORIGIN_HUB_TOKEN` 会覆盖保存的连接信息。
- 配置了中枢之后，`origin mcp` 仍然根据设备自己的库提供服务，并合并中枢的回答（见 [MCP server](#mcp-server)）。它在运行中与中枢同步：读取类工具之前最多每 10 秒一次，每次写入后立即同步，记录文件有变化时每分钟同步一次，Agent 离开时再同步一次；等待中枢的时间不会超过超时时限。Agent 的注册无需改动，Agent 也仍然能引用刚刚说过的内容。
- 没有本地记录的云端 Agent 直接用 bearer 令牌注册中枢的 `/mcp` URL。
- CLI 管理命令（`entries`、`show`、`correct`、`forget` 等）作用于设备自己的库。在已接入中枢的设备上，`correct` 和 `forget` 之后会与中枢同步，所以改动会到达中枢；如果是遗忘，还会到达其他每台设备。`origin ui` 同样作用于设备自己的库，并在每次写入后在后台与中枢同步。中枢的管理界面会显示所有设备的条目。

### 中继 {#relays}

中继是一台不保有自己记忆的设备，适用于磁盘空间不多的机器。它运行与其他设备相同的适配器和相同的 `origin mcp`，但不保存原始镜像，也不保存事件：在中枢收到之前，Agent 自己的记录文件就是它的会话唯一的副本。所以中继不是一份完整的记忆：没有中枢，它什么也回答不了；它发送的一切，其溯源都在中枢上解析，原始行保存在中枢的镜像中。

- **选择中继。** `origin hub connect <url> --token <token> --relay` 把库变成中继。只有还没有保存任何内容的库才能成为中继：已有事件、镜像文件、条目或遗忘记录的库会被拒绝，并附上如何新建一个空库的说明，不会删除任何东西。模式保存在库中（`setting`），而不是连接信息中，所以 `ORIGIN_HUB_URL` 和之后的 `origin hub connect` 都不会改变它；中继也会一直是中继：要在那台机器上保有完整的库，请使用新的 `ORIGIN_HOME`。中继不能运行 `origin serve`；没有接入中枢时，它既不发送也不回答任何东西。
- **保存什么。** 每个来源文件一个游标，保存在 `setting` 中：中枢正在接收的代次、中枢已确认收到的该代次的字节数、这些字节最后 4 KB 的 SHA-256、游标最后变化的时间，对压缩文件还有它是否已全部发送；对生成的来源，用它的令牌代替哈希，并保存中枢已确认收到的最后一行，适配器从这一行接着写。游标保存在 `setting` 而不是 `raw_file` 中，因为一行 `raw_file` 代表 `raw/` 下的一个镜像，备份、封存、存储统计和推送都会读取它；而在 `setting` 中，生成的来源的最后一行与它的游标在同一次写入中改变。除了游标，中继还保存它的名称、模式、复制游标和同步日志：每个来源文件几百字节，外加每个生成的来源的最后一行。
- **发送。** `origin sync`，以及运行中的 `origin mcp`，先向中枢查询游标（`GET /v1/cursors`），再从中继的游标之后、直接从 Agent 的文件读取每个来源文件：压缩文件读取解压后的内容，生成的来源则读取适配器在已发送的最后一行之后写出的行。完整的行按块发送到 `POST /v1/ingest`，每块最多 1 MiB（或者单独一个更长的行），与设备发送镜像的方式相同，最旧的文件先发送。中枢用同样的适配器镜像并解析它们，所以它的镜像、事件和事件 id，与一台完整的设备推送同样这些文件的镜像时完全相同。只有中枢确认收到一个块之后，游标才会前移。
- **改写。** 变小了的文件，或者已发送的最后 4 KB 不再匹配的文件，说明它被改写了：中继把它作为下一个代次、从偏移量 0 开始发送，中枢保留旧的代次。生成的来源从不检测改写。
- **中枢的进度。** 当中枢持有的某个文件比中继的游标所说的更多或更少时（途中丢失的回应、中继的另一个进程抢先发送、从备份恢复的中枢、以中枢已知的设备名新建的中继库），只要文件在中枢游标处恰好有一行结束，中继就从中枢的游标继续；生成的来源会向适配器要行，直到到达那个偏移量。否则，它把这个文件作为一个新的代次发送。因偏移量被拒绝的块（`409`）也按同样的方式处理。中枢直接拒绝的文件（`400`、`413`）会被报告并跳过，其他文件照常发送。
- **离线。** 什么也不发送，游标也不移动：新的行留在 Agent 自己的记录文件里。有些 Agent 会删除旧的记录（Claude Code 在 `cleanupPeriodDays` 之后删除，默认 30 天），而中继不保留副本，所以中继必须定期连上它的中枢。Agent 运行期间，它的 `origin mcp` 每分钟发送一次新的行，Agent 离开时再发送一次；`origin status` 按来源显示还有多少字节尚未发送。
- **清理前的警告。** 当仍有完整的行尚未发送的最旧文件，临近它的 Agent 删除它的年龄时，中继会发出警告；年龄按文件的修改时间计算，和 Claude Code 的做法一样。对 Claude Code，是在 `cleanupPeriodDays`（从它配置目录中的 `settings.json` 读取，未设置时为 30 天）之前一周以内，如果它短于两周，则是过了它的一半之后；对保留期限未知的 Agent，是这样的文件已有一周之久，而且中继已有一周没有连上中枢。`origin status` 会显示这个警告，`origin sync` 在没能发送全部内容时也会显示；`origin mcp` 在连不上中枢期间最多每小时检查一次，把警告写入它的日志，并附在工具的错误里，让 Agent 看到。检查在 CLI 中进行；`core` 只给出这样的最旧文件（`relayPending`）。
- **回答与写入。** 中继没有可以据以作答的事件，也没有事件可以用来核对条目所引用的事件，所以每个工具都是中枢的（见 [MCP server](#mcp-server)）。写入按中枢的规则在中枢上进行：中枢检查每个被引用的事件都在它那里存在且可见（不变量 1），应用遗忘（不变量 2），并把作者记为 `<agent>@<中继名>`，origin 为中枢（见[访问](#access)）。CLI 的查询和管理命令（`search`、`timeline`、`show`、`entries`、`correct`、`forget`）同样询问中枢的 `/mcp`，身份是 `user@<中继名>`；`entries --history`、`projects`、`forgotten` 和 `restore` 在中继上不可用，恢复要在中枢的管理界面中进行。
- **复制。** 中继自己不写条目或遗忘记录，中枢的遗忘记录在它那里也找不到需要隐藏的东西，所以它不保存任何遗忘记录；它仍然拉取这些记录，让自己的复制游标像设备的一样前移。它的 Agent 的记忆所对应的条目，由中枢从中继发来的行中派生（见[原生记忆](#native-memories)）。

### 管理界面 {#admin-ui}

中枢可以为它的主人提供一个 Web 界面。它默认关闭；它是同一个库的一个视图，而不是另一套系统：每个页面、每次 JSON 调用都经过 MCP 和 CLI 所用的同一组 core 操作（不变量 5）。`@openlinkos/origin-admin` 包提供一个请求处理函数，由中枢挂载。`origin ui` 在设备上为该设备自己的库提供同样的界面，并有自己的登录方式（见最后两点）。

- **提供方式。** `origin serve --admin` 把界面挂载在中枢端口的 `/admin` 下；`origin serve --admin-listen 127.0.0.1:7078` 则改在一个单独的监听地址上提供，通过 SSH 隧道或 `kubectl port-forward` 访问。如果界面会在非回环地址上提供，除非 `--public-url`（`ORIGIN_PUBLIC_URL`）是 https URL，或者是回环主机上的 http URL（例如发布在 `127.0.0.1` 上的容器端口），否则中枢拒绝启动。没有公开 URL 时，界面只响应发往回环主机名的回环连接，这同时也能防御 DNS 重绑定。界面未启用时，`/admin` 返回 404。
- **登录。** 每个中枢只有一个管理密码，没有用户名。设置了 `ORIGIN_ADMIN_PASSWORD` 时，它就是管理密码，并且优先于其他来源；它至少要有 10 个字符，否则中枢拒绝启动。否则，管理密码在中枢上用 `origin admin password` 设置（在终端中输入两次，或从标准输入读取一行），或用 `origin admin password --generate` 生成。如果中枢在启用管理界面的情况下启动时两者都没有，它会生成一个密码（20 个随机 base32 字符，100 位），保存它的哈希，并在日志中只打印这一次。没有首次访问时的设置向导，所以新建的中枢不会被第一个访问到它的人占用。密码以 scrypt 哈希的形式（N = 2^15、r = 8、p = 3，随机的 16 字节盐）写成 `scrypt$N$r$p$<salt>$<hash>`，保存在只留在中枢上的 `setting` 中；中枢也会保存 `ORIGIN_ADMIN_PASSWORD` 的这种哈希，以便发现它是否变化。校验逐个进行，并以恒定时间比较。管理密码和中枢令牌互不接受：密码不能以 `ogn_` 开头，`/mcp` 和 `/v1/*` 只接受 bearer 令牌，`/admin` 只接受它自己的会话 cookie。
- **会话。** 会话保存在服务器端的 `admin_session` 中，以会话 id 的哈希为键。会话在 30 分钟没有请求或登录满 12 小时后结束；管理密码变化时，所有会话都会结束：用 `origin admin password` 设置新密码时，以及中枢启动时 `ORIGIN_ADMIN_PASSWORD` 与上次不同，或者在它和保存的密码之间切换时。在 https 公开 URL 之后，cookie 是 `__Host-origin-admin`（Secure、HttpOnly、SameSite=Lax）；在回环 http 上，cookie 是 `origin-admin`（HttpOnly、SameSite=Strict，路径 `/admin`）。在 https 公开 URL 之后，普通 cookie 只在回环隧道上有效，所以从兄弟子域名种下的 cookie 无法固定会话。创建或吊销令牌、结束会话，要求最近 10 分钟内输入过密码。遗忘和恢复只需要会话：两者都是记录，可以互相撤销。
- **请求。** 只有 GET 和 POST，所有写操作都是 POST。POST 需要会话的 CSRF 令牌（表单字段 `_csrf` 或请求头 `X-CSRF-Token`），以及与中枢源相同的 `Origin` 请求头；带有 `Sec-Fetch-Site: cross-site` 的请求会被拒绝。请求体上限为 64 KiB。密码校验失败的次数受到限制：每个客户端每 10 分钟 10 次，总计每 10 分钟 100 次（返回 429 和 `Retry-After`）；只有设置了 `ORIGIN_CLIENT_IP_HEADER` 时才从该请求头取客户端地址，否则取连接的地址。在代理或 CDN 之后，必须设置这个请求头：否则所有客户端共用代理的地址和同一个限额，任何人的失败尝试都可能把主人锁在外面。
- **响应。** 页面在服务器端由一个对每个插值都做转义的模板渲染。Agent 的消息按 Markdown 的一小部分（段落、标题、强调、行内代码、围栏代码块、列表、引用块、分隔线、GitHub 的竖线表格和链接）渲染，渲染器位于管理包中，它只识别结构，并让每一段文本都经过同一个模板输出，所以消息中的 HTML 仍然是文本；链接只能指向 `http` 和 `https` URL，在新标签页中以 `rel="noopener noreferrer"` 打开，并显示它们的 URL。一小段脚本提供一些便利，例如就地加载原始行，但没有页面依赖它。每个响应都带有严格的 Content-Security-Policy（没有内联脚本或样式，启用 Trusted Types 且不允许任何策略）、`Cache-Control: no-store, private`、`Vary: Cookie`，以及防止嵌入、类型嗅探、引用来源泄露和被搜索引擎收录的请求头；在 https 之后还带有 HSTS。所有资源，包括设计系统的样式表、字体和图标，都由中枢自己以带内容哈希的文件名提供；每个页面只内联它用到的图标符号，界面从不发起外部请求。
- **能做什么。** 概览（数量统计；近 30 天每天的可见事件数，按来源区分；最近的会话；这段时间事件最多的项目；每个来源的 Agent 最新版本、最近一次归档和 7 天内的解析错误；设备及其最近推送；最新的条目，以及最近的遗忘与恢复，只显示它们的目标 id、原因和数量；存储：数据库、磁盘上的原始镜像，以及存储桶中的帧）、令牌（创建：令牌只显示一次，旁边附有现成的接入命令；吊销）、设备、时间线（按最近活动的日期排列的会话，可以按来源、项目或名称中的词筛选）、按轮次查看的会话（见下文）、带溯源链的事件（原始行按需加载，截断到 4,000 个字符）、检索、条目及其历史、`correct`（未指定时置信度为 1）、从事件页面 `remember`（引用该事件，作者为 `user@` 加中枢的名称），预览之后附上原因的 `forget`：请求带上所展示计划的摘要，如果计划在此期间发生了变化，就不会遗忘任何内容（409）；以及遗忘记录页面，它列出每一次遗忘和恢复，连同时间、origin、作者、原因和覆盖的内容。生效中的遗忘有自己的页面，向主人展示它隐藏的内容——条目的文本和会话事件——并在说明将带回什么之后，附上原因恢复它。
- **按轮次查看会话。** 会话页面把它的事件分成一轮一轮。一轮从一条提示开始：按临时名称的规则（见[检索与时间线](#search-and-timeline)）被认作用户亲手输入的提示的可见用户 `message` 事件，子 Agent 的除外（Claude Code 把它们的线程标记为 `sidechain`）。一轮也可以从一条命令回显（只由元素组成、带有 Claude Code 的 `<command-name>` 的消息）开始，前提是 Agent 在下一条提示或命令之前，以自己的消息或工具调用据此工作；这时命令及其参数就是这一轮的提示，判断这一点对每条命令只需查一次 `(source, session_id, ts)` 索引。Agent 没有据以工作的命令，例如 `/clear` 或 `/model`，不开始新的一轮，而是所在那一轮中的一条备注；临时名称仍然跳过所有命令。一轮包含到下一轮开始之前的所有事件，第一轮之前的内容是第 0 轮。在一轮之中，工具调用按调用 id（`callId`，或 Claude Code 的 `toolUseId`）与它的结果配对；没有 id 的，与更早的、同样没有 id 且还没有结果的第一次调用配对；调用的结果取自其结果的错误标记或状态。Agent 在之后不再调用任何工具的最后一条消息是回复，按 Markdown 渲染；它的调用，以及回复之前说的话，折叠在一行摘要之后；命令回显、它们的输出、注入的上下文和系统事件以备注显示。一页包含 20 轮，如果会超过 1,500 个事件就少一些；更长的一轮分成每部分 1,500 个事件。提示通过 `event_user_message` 读取，这是一个只包含用户消息的部分索引；之后只通过 `(source, session_id, ts)` 索引读取从本页第一条提示到下一页第一条提示之间的事件，所以有数千个事件的会话从不会被整个读取。从某个事件出发的链接（`at=<id>`）打开包含它的那一轮所在的页面。会话的日期索引和时间线里的日期，都以服务器的时区为准。
- **召回。** 「召回」页按从新到旧列出 Agent 拿到的内容（见[召回](#recall)），可以按设备和 Agent 筛选，也可以列出什么都没交出的召回。一次召回的页面显示每一项现在在库中的样子：条目或会话，带链接，或者它之后已被遗忘；还有它的层、分数，以及会话之后是否用上了它，和它回应的提示。条目的页面列出交出过它（任何一个版本）的召回，会话的页面在每次召回所在的那一轮显示它，这是通过检索索引找到的，不读取整个会话。中枢的页面显示每台设备的召回。
- **概览的查询。** 概览上的一切都来自派生表（`session`、`sync_log`、`raw_file`、`raw_chunk`）和索引，从不扫描 `event`。图表和最活跃的项目只通过 `(source, session_id, ts)` 索引统计近 30 天的可见事件，每个事件读一个索引条目（27 万个事件约 100 毫秒），只统计这段时间有活动的会话，再减去通过 `excluded_event` 找到的已遗忘事件；只要日期和每个来源的总数不变，结果就会被保留。Agent 的最新版本取自它最近五个会话的最新事件。有存储桶时，统计磁盘用量需要对每个镜像的帧文件做一次 stat，最多每分钟一次。
- **不能做什么。** 编辑或删除事件、原始镜像、条目或遗忘记录；在隐藏它的那次遗忘的页面之外显示被隐藏内容的任何文本（列表只显示遗忘记录的目标 id、原因和数量；审计日志只保存 id 和数量）；保存没有可见来源的条目；再次显示令牌；修改管理密码或其他安全设置；执行任意查询，或读取可见事件的镜像行以外的任何文件。
- **审计日志。** 来自界面的登录和失败尝试（每个客户端在每个时间窗口内合并为一条记录）、令牌变更、写入的条目、遗忘与恢复和被结束的会话（操作者 `owner`，在 `origin ui` 中为 `local`），来自 CLI 的令牌和密码变更（操作者 `cli`），以及中枢启动时生成或变更的密码（操作者 `hub`），都会连同渠道、客户端地址和 user agent 一起追加到 `audit_log`。详情只含 id 和数量，从不包含文本、原因或密码，因此被隐藏的内容保持隐藏；触发器拒绝任何更新和删除。
- **在设备上：`origin ui`。** CLI 为它所在机器的库（`~/.origin` 或 `$ORIGIN_HOME`）提供同样的页面，只监听 `127.0.0.1`，端口默认为 7079，可用 `--port` 指定；它拒绝其他任何地址。它只响应 `Host` 为 `127.0.0.1:<port>` 或 `localhost:<port>` 的请求，以此防御 DNS 重绑定，并保留上面所说的响应头、请求体上限以及对每个 POST 的检查。这里没有密码，因此也没有要管理的令牌、设备、接入命令或管理会话：这些页面和调用在这里并不存在，中枢上要求最近输入过密码的操作在这里只需要会话。它能写入的与中枢的界面相同（`remember`、`correct`、预览之后的 `forget`，以及 `restore`），作者记为 `user@<device>`，审计日志中的操作者为 `local`。在已接入中枢的设备上，每次写入之后都会在后台与中枢同步，与 `origin correct` 和 `origin forget` 之后一样；概览会显示中枢、设备上次与它完成同步的时间（保存在 `setting` 中），以及 `origin ui` 的上一次同步是否失败。它启动时会在后台归档设备上 Agent 的会话，和 `origin sync --local` 一样，并像 `origin mcp` 那样在各个写事务之间处理请求，让界面显示 Agent 最近写下的内容；停止它时不会等待归档结束，下一次同步会从停下的地方接着做。中继没有可以显示的库，`origin ui` 拒绝在中继上运行。
- **登录 `origin ui`。** 它启动时打印一个带一次性密钥（32 个随机字节）的链接，并用平台自带的方式（`cmd /c start`、`open`、`xdg-open`）在默认浏览器中打开它，除非指定了 `--no-open`。交给浏览器的不是链接本身，而是一个跳转到该链接的文件，这个文件只有它的主人可读，并在退出时删除，因为机器上的其他用户能读到进程的命令行。密钥只能使用一次，须在 5 分钟内使用，并且只在这个进程中有效，进程只保存它的哈希。在它运行的终端里按 Enter，会以同样的方式打印并打开一个新链接，之前的链接无论是否用过都会失效；只有标准输入是终端时才会读取它，从不读取管道或文件。密钥被兑换成一个会话，响应随即重定向到 `/admin/`，所以密钥不会留在地址栏和 referrer 中。会话只存在于这个进程的内存中，从不写入 `admin_session`：它在 `origin ui` 停止、退出登录或满 12 小时后结束，其他任何 server 都不接受它，包括同一个库上中枢的管理界面。它的 cookie 是 `origin-ui`（HttpOnly、SameSite=Lax，路径 `/admin`）：使用自己的名称，因为浏览器在同一主机的各个端口之间共享 cookie；没有 `Secure` 属性或 `__Host-` 前缀，因为 Safari 在纯 http 的回环地址上会丢弃这样的 cookie；用 Lax，因为从文件打开链接算作跨站请求。

## 待解决的问题 {#open-questions}

- **低成本的认知。** 如何在没有专门抽取流水线的情况下，构建并维护一个关于这个人的模型？目前由 Agent 在注意到某些东西时自行写入认知条目。这是否足够，仍是一个悬而未决的问题。
- **与原生记忆互通。** Origin 单向导入 Claude Code、ZCode 和 Grok Build 的记忆（见[原生记忆](#native-memories)）。尚未设计的有：把条目写回 Agent 的记忆文件，以及导入 Codex 的记忆（启用后，它在 `~/.codex/memories/` 下自行合并的摘要）；Cursor 已不再在磁盘上保存记忆。
- **召回的质量与范围。** 召回匹配的是词，所以会漏掉用别的说法或别的语言表达同一件事的条目，也仍会交出一些与提示只有常见词相同的条目（见[召回](#recall)）。如何根据召回记录和 Agent 之后用上了什么来评判召回的内容，还没有设计；在不拖慢 Agent 处理提示的前提下，从中枢召回其他设备写下的条目，也还没有设计。
- **变更通知。** `origin mcp` 在 Agent 运行期间每分钟比较一次文件的大小和时间来查看新的记录行，并在 Agent 离开时再同步一次，所以只要设备上的 Agent 使用 Origin，就不需要定时任务。尚待解决的是：不使用 Origin 的 Agent 写下的行，以及 Agent 直接杀掉 server 之后写下的行，要等到下一个 Agent 或 `origin sync`；改为监听文件而不是每分钟查看可以缩短延迟，但文件监听在某些平台上并不可靠。
- **中继与 Agent 的清理。** 中继不保留尚未发送的内容的副本。如果它的中枢无法连接的时间超过了某个 Agent 保留记录的时间，这些会话就会丢失。中继会在那之前发出警告（见[中继](#relays)），但无法阻止它发生：为面临删除的记录保留副本尚未设计。目前只知道 Claude Code 的保留期限，而且只读取它的用户设置，不读取优先级更高的托管设置；其他 Agent 只在一周没有同步之后才会收到警告。
- **用过时的版本恢复。** 设备按它持有的条目版本判断规则 3。当另一个库在中枢上纠正了设备的某个条目时，一次恢复可能让设备继续隐藏这个条目，而中枢显示它，直到之后又有遗忘或恢复涉及它。把条目下发给设备，或者把中枢的判断与遗忘覆盖的内容分开发送，可以解决这个问题；两者都尚未设计。
- **擦除。** 遗忘是隐藏，恢复会把内容带回，所以原始行仍保留在磁盘上、备份中和中枢的存储桶中。显式擦除被遗忘的内容——有它自己的记录和限制（擦除之后无法恢复）——尚未设计。
- **中枢的存储后端。** 中枢可以把原始镜像中已封存的帧——它的大部分数据——保存在兼容 S3 的存储桶中，其余部分留在自己的磁盘上：开放尾部和 SQLite 数据库。尚未设计的有：把帧从存储桶移回磁盘或移到另一个存储桶，不阻塞中枢的帧传输方式，以及为一块磁盘装不下的中枢改用 PostgreSQL 保存库。
